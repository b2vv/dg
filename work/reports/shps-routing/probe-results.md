## Чесна інтерпретація (НЕ «B виграв якість, A — перф»)

Це ПРОТОТИПИ; читати треба, що саме кожне число доводить, а не ранжувати наївно.

1. **A-by-construction ПІДТВЕРДЖЕНО:** `adminTreeCrossings=0` на ВСІХ схемах — layered-розкладка
   справді дає деревні (in-dept) ребра без перетинів без циклу перебудови (spec §Рішення, N4). Це
   найсильніша теза A, і вона тримається.
2. **Слабкість A — НЕ в layout, а в міждепарт.-РОУТИНГУ мого прототипу:** `routeOrtho` навмисно
   наївний (прямий сегмент через коридор БЕЗ обходу карток/рамок) → 8px-порушення 5/2/7 і
   through-third 3/4. Це НЕ фундаментальна межа конструктиву — це недобудований obstacle-avoidance
   (його треба писати на `polylineHitsBoxInterior` + bounded-резолюція §5). На s4 A дав **3 залишкові
   перетини** (усі ПОЗНАЧЕНІ, §12 чесно) — але це теж наслідок наївного роутера, не доказ
   інфізибельності.
3. **B (ELK) дає чистий роутинг «з коробки»:** 0 перетинів на ВСІХ схемах (вкл. §10.1.4!), 8px
   скрізь, 0 through-third. Зрілий orthogonal-роутер + hierarchical layout. **Важливий наслідок:**
   B дав **0 на s4** → для цієї схеми crossing-free embedding ІСНУЄ; тобто §12-побоювання «0 може
   бути математично недосяжним» для s4 як змодельовано — НЕ підтвердилось (0 досяжний). §12 лишається
   чинним для гірших випадків, але s4 не є таким.
4. **Ціна B:** (a) перф 167мс/500 — промах бюджету §8.4 у 3.3× (тюнінг ELK-опцій невизначений,
   ризик); (b) великий dep elkjs + 4 high-sev audit; (c) async-only (контракт роутера треба async
   або прогрів); (d) координати ELK відносні до LCA — крихка мапа (вже обійдено, але це борг).
5. **Ціна A:** треба ДОБУДУВАТИ obstacle-avoidance + коридор-резолюцію (відоме, на наявних
   примітивах), але 0 нових deps, 31мс, async не треба, тримає dg-стек (Rust row-tree+Pixi).

## Рекомендація owner-а (на захист перед plan-GATE)

Схиляюсь до **A (конструктив)**, але НЕ через «якість» (там мій прототип програв виміру — чесно), а
через: (1) A вже доводить найтвердішу гарантію (tree 0 by construction); (2) слабкість A —
добудовуваний obstacle-avoidance на наявних примітивах, тоді як слабкість B (перф 3.3× бюджету) —
невизначено-тюнінгована й у чужій бібліотеці; (3) 0 нових deps vs великий dep+audit; (4) sync. B
лишається живим fallback, якщо obstacle-avoidance A виявиться дорожчим за очікуване — і B довів, що
0-crossing досяжний (корисний еталон якості для тестів A).

**Рішення НЕ фіналізоване тут** — йде на plan-GATE (plan-critique + plan-defense) + owner. Контрольна
чесність: якби перф B був у бюджеті, рішення було б значно важчим (B якісніший «з коробки»).
