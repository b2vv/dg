Дає ШПС-схемі **читабельні лінії підпорядкування з гарантіями**: ортогональні, **0 перетинів
(включно edge-edge)**, 8px кліренс від карток, коридори/доріжки, вихід/вхід між департаментами
через межі рамок, штрих до керівної орг, підсвітка шляху. Стан світу: dg має орто-**базу**
(`layout/staffEdgeGeometry.ts` `classifyStaffEdgeRoute:293`/`staffEdgePolyline:390`, фарба
`render/StaffEdgesView.ts:82`), але жадібне уникання тільки card-intrusion (`:316`), edge-edge не
рахується, `forced`-фолбек повертає маршрут **без перевірки** (`:380`); 8px нема (хардкод 16/14,
`:90,104`, `spineBusEdges.ts:30`); dept-портів нема; штрих-до-head нема (cross-tier суцільний);
highlight нема взагалі (`#e5491d`/`#c2502a` у репо відсутні; лінії не реагують на selection).
**Виняток:** це заміна GoJS-роутера для ШПС; орг-діаграма (фаза 2) лишається на GoJS і цього
роутера поки не споживає.

## Чому
Замінюємо GoJS на dg (host-інтеграція). GoJS має зрілий layered-роутер; dg-база малює картки 1:1,
**а лінії — гірше за поточний GoJS**: на реальній ШПС (кілька департаментів, міждепарт. зв'язки)
`forced`-маршрути накладаються й перетинаються, бо edge-edge не рахується і `forced` взагалі без
перевірки чистоти (`staffEdgeGeometry.ts:380`). Тобто регрес саме в тому, що найбільше впливає на
читабельність оргструктури. Виміряна корекція власної посилки: спершу я вважав routing «розширенням
EdgeStyle» — ні: вимоги §6 прямо вимагають, щоб **розкладка гарантувала маршрутизовність** і
**перебудовувалась** при перетинах (не «перетин на крайній випадок»). Отже це **layout+routing
разом**, не лише edge-шар; EdgeStyle (color/width/corner/terminator, `render/types.ts:172`) цього
не покриває.

## Рішення
**Детермінований роутер, чия РОЗКЛАДКА crossing-free BY CONSTRUCTION для адмін-дерева, з
ОБМЕЖЕНОЮ монотонною резолюцією міждепарт.-ребер і ЯВНОЮ драбиною деградації; рушій — кандидат A
(конструктивний, розширити dg) vs B (ELK), рішення на GATE після СИМЕТРИЧНИХ проб A і B.**

Ключ (GATE N4): адмін-дерево планарне (кожна посада ≤1 `parentId`, §2) — отже **деревні ребра
0-перетинів by construction** при layered-розкладці; важкого A*+rebuild-loop для них не треба.
Перетини можливі ЛИШЕ в міждепарт./зовнішніх ребрах + порядку доріжок — там і тільки там працює
обмежена резолюція.

Механізм:
1. **Вхід + валідація (B4, §2):** `Position{id,parentId,deptId,collapsed,order}`,
   `Department{id,parentPositionId,order}` (покрито пінованими полями). Роутер **валідує сам і не
   зависає**: цикл `parentId` (A→B→A) → structured-error, схема показує помилку замість лінії (§2);
   невідомий/застарілий `deptId` (нема в `departments`) → трактуємо як посаду поза департаментом
   (§3.3), з діагностикою; `deptId` на згорнутий/прихований dept → ребро й ціль ховаються (§8.1).
   Порядок входу детермінований: сорт за `(parentId, order, id)` — єдине джерело tie-break (N1).
2. **Конструктивна layered-розкладка (N4, §6):** Reingold–Tilford/Walker знизу-вгору — підлеглий
   нижче керівника, сусіди за `order`, міждепарт.-ціль ближче до джерела. Деревні ребра тут
   **0-перетинів by construction**, без циклу перебудови.
3. **Перешкоди (§5.1):** картка+**8px**, `.dn`+4px, чужі рамки (крім джерела/цілі), плашки/кнопки —
   в одиницях схеми (масштабуються, §8.3).
4. **Міждепарт./зовнішні ребра (§3.2–3.3):** детерміноване розведення по коридорах + доріжках
   (крок 8px, §5.4), порти `deptBottom`→коридор→`deptTop`, «крізь третю рамку заборонено».
5. **Обмежена резолюція + драбина деградації (B1, B2):** якщо після конструктиву міждепарт.-ребра
   перетинаються — застосувати перестановки §6.5 **не більше K проходів** (K = f(кількість депів),
   явна межа) з **монотонною мірою**: кількість перетинів мусить СТРОГО спадати щопроходу, інакше
   стоп (гарантія завершення — немає нескінченного «опустити нижче»). Коли 0 недосяжний у межах K —
   **драбина деградації (ПОЛІТИКА — рішення власника, B2):** (i) мінімізувати + ВИДИМО позначити
   залишковий перетин (чесно, не ховати); (ii) послабити найслабше обмеження (довший коридор);
   (iii) крайнє — прийняти обмежену кількість перетинів із діагностикою. 🔴 **Requirement-tension:**
   вимоги §10.4 кажуть «0 перетинів» як acceptance, але для §10.1.4 (два керівники різних депів →
   підлеглі в спільному C) embedding без перетинів може НЕ існувати — **яку саме сходинку драбини
   обрати й чи залишковий перетин прийнятний, вирішує власник** (винесено через Cass 1).
6. **Фарба через host-шов (§7, N2):** колір лінії — з `EdgeStyle`/теми, НЕ хардкод: токен
   `--color-cass-adm-diagram-link` має ДВА значення (`#c2502a` light / `#b35a23` dark,
   `cass-adm-theme.css:56,142`) — single-hex згубив би dark і оминув host-color-шов (`staffEdgeStrokes`
   застосовує `edge.color`). Прямі кути (r≤4px єдиний); штрих-до-head — новий kind `'lead-org'`
   (`#6b6b73`/токен) з міткою; highlight-колір теж через paint/EdgeStyle, не константою.
7. **Публічний контракт (новий):** `highlightPath(ids)` → шлях root→вибране + прямі зв'язки акцент,
   решта opacity 40% (§7). Re-entrancy (B-defense): новий `setData`/ресайз під час маршрутизації
   **скасовує** поточний прогін epoch-гардом (патерн наявного ingest-epoch, `ingestIsCurrent`) —
   паралельної перебудови немає. Детермінізм + **≤50мс/500**, rAF-throttle (§8.3–8.4).
8. **Rollback / kill-switch (B5):** конфіг `staffEdgeRouter: 'legacy' | 'v2'`, **default `legacy`**
   доки v2 не доведено. Будь-який збій v2 (validation-error, перевищення K) → fallback на поточний
   greedy-роутer для ЦЬОГО прогону, ніколи не зависання. Власник/хост може миттєво відкотитись.

**Кандидат A — конструктивний (розширити dg).** Layered-дерево (планарне by construction) +
детерміноване коридор/track-розведення + обмежена резолюція міждепарт.; A* лише як **обмежений
локальний fallback** на одне важке міждепарт.-ребро, НЕ глобальний rebuild-loop. Пасує до Rust
row-tree+Pixi+контурів (`orgBlockLayout.ts`, `StaffZonesView`), нуль нових deps.
**Кандидат B — ELK.js** (`edgeRouting:ORTHOGONAL` + ієрархічні вузли=депи). Менше коду, але б'ється
з наявним layout dg (замінює/дублює), великий dep, детермінізм/8px/порти/перф/SVG-export треба довести.
**Відкинуто:** (1) greedy+«мінімізувати» — суперечить §10.4; (2) **необмежений A*+rebuild-loop — B1,
немає гарантії завершення** (замінено конструктивом + обмеженою резолюцією).

**Рішення A/B — на GATE після СИМЕТРИЧНИХ проб (B3):** обидві проби на §10.1 схемах 2/4/5 міряють
ТІ САМІ критерії — 0 перетинів (деревні) + поведінка на §10.1.4, детермінізм, 8px/порти,
container-constraint «не крізь третю рамку», SVG-export/контур-паритет, highlightPath, ≤50мс/500.
- **B-проба (ELK):** чи тримає staff-layout/контури; решта критеріїв.
- **A-проба (конструктив):** прототип layered+коридори — чи 0 деревних by construction, чи обмежена
  резолюція сходиться, перф.
Жоден кандидат не дефолтиться без власного доказу (спайк B НЕ валідує A — тому окрема A-проба).

Шов монтування: `DiagramRenderer.paintStaffFrameAndEdges` (`:769`) → роутер за прапором
`staffEdgeRouter`; `StaffEdgesView` фарбує; `highlightPath` — публічний метод `OrgHierarchyDiagram`.

## Форма перевірки
- **Чисті шви (юніт):** (1) crossing-detector — пари поліліній «перетин є/нема», включно edge-edge і
  спільний стовбур (НЕ перетин); (2) obstacle-builder — 8px/4px зони з AABB; (3) маршрут на сітці з
  перешкодою — орто, обходить, ≤N поворотів; (4) track-allocator — N ліній у коридорі на доріжки 8px
  без перехрещення, порядок детермінований. Кожен — RED спершу (контрольна проба: вхід, що МУСИТЬ дати
  перетин/порушити 8px).
- **Термінація (B1):** обмежена резолюція на вході, де 0 недосяжний (§10.1.4) → СТОП у межах K проходів
  (не зависання), міра монотонно спадала; контрольна проба — вхід, де монотонність порушилась би →
  loop мусить зупинитись, а не крутитись.
- **Валідація входу (B4):** цикл `parentId` → structured-error (не маршрут, не hang); невідомий
  `deptId` → трактується як поза-dept + діагностика; прихований-dept ціль → ребро сховано. RED: кожен
  кривий вхід спершу дає помилку/краш у наївній версії.
- **Драбина деградації (B2, після owner-політики):** на §10.1.4 (0 недосяжний) → обрана сходинка
  застосована, залишковий перетин ПОЗНАЧЕНО видимо (не схований); контрольна проба — приховування
  замість позначення має провалити тест.
- **Rollback (B5):** збій v2 (validation-error / K-перевищення) → fallback на legacy-роутер для цього
  прогону, щось намальовано; `staffEdgeRouter:'legacy'` → поточна поведінка без змін (регрес).
- **Колір через шов (N2):** `EdgeStyle.color` застосовано (не хардкод); dark-тема дає `#b35a23`, не
  світлий хекс; highlight-колір теж із paint.
- **Компонентні (замокано layout-seam):** тест-схеми §10.1 **+ 0 посад + 1 посада (N6)** як фікстури →
  асерти §10 п.4: 0 перетинів (деревні), ≥8px до картки, жодної лінії під карткою/заголовком. Детермінізм:
  два прогони тих самих даних → **ідентичні** полілінії (tie-break з п.1 входу).
- **Перф-гейт:** 500 посад → ≤50мс (вимір; контрольна проба — штучно важка схема, що МУСИТЬ перевищити).
- **Ручний гейт (екран):** highlight — вибір підсвічує root→X + прямі, решта 40%; контрольна проба —
  вузол БЕЗ зв'язків не підсвічує нічого (а не «все»).
- **GATE перед кодом:** plan-critique + plan-defense (r1 пройдено — нижче); **симетричні A/B-проби**
  (не лише ELK-спайк) як вхід рішення рушія.
