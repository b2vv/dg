# D1 — interaction-store: специфікація (WHAT / WHY)

**Статус:** spec, GATE 1 (shared understanding) — НЕ пройдено. Гілка `feat/d1-interaction-store` @ main `916a036`.
**Джерела:** `work/ROADMAP-extensibility.md` (R1, D1, D1-деталь, «Порядок»); код `state/SelectionStore.ts`,
`interaction/selection.ts`, `render/personInteractions.ts` (near hover), `OrgHierarchyDiagram.ts`. Порядок власника: D3→D1 (D3 зріз 1 злито).
**Гейт якості (наскрізний):** кожне рішення простіше й інтуїтивніше за GoJS (без стрингових DSL, без глобальних мутацій, чисті функції + DI).

## Проблема

Стан взаємодії розмазаний і асиметричний по межі LOD:
- **`selected`** живе в `SelectionStore` (multi-select список `NodeRef`, `onChange`-колбек) — обидва шари його враховують.
- **`hovered` стану НЕ має.** Hover реалізований окремо, DOM-імперативно (`installStaffHoverHighlight`), **лише для
  React near**. Здалеку (Pixi) hover-акценту нема взагалі.
- Наслідок: перехід через LOD (zoom near↔far) губить/не має hover; будь-яка нова hover-залежна фіча (R1 paritet,
  R2/R3) мусить реалізовуватись двічі й розходиться. Немає єдиного джерела, з якого обидва шари рендерять «що юзер торкає».

GoJS тримає сотні мутабельних проперті на глобальному `Diagram`; наша мета — **центральний, малий, типобезпечний
interaction-store**, з якого обидва шари рендерять, без дублювання логіки й без глобальних синглтонів.

## Межа відповідальності (критично, D1-деталь)

| Зріз | Поля | Власник | Лайфцикл | У D1? |
|---|---|---|---|---|
| **Interaction** (що юзер торкає) | `selected`, `hovered` | pointer/keyboard | selection переживає; hovered — транзієнтний | **ТАК** |
| **Emphasis** (що акцентовано/приглушено) | `found`, `highlight` | search / команда хоста | `setData` чистить | **НІ — окремий зріз** |

- `found` (вже `setFoundFocus`) і `highlight` (вже `highlightPath`) **лишаються як є**, окремими власниками. D1 їх **не
  чіпає й не поглинає** (спільний рендер-наслідок приглушення ≠ спільна відповідальність).
- `focused` — **поза D1** (передчасно: a11y/keyboard-навігації в коді нема; семантику визначить майбутня a11y-таска).

## User scenarios

1. **Hover переживає LOD.** Юзер наводить на ноду зблизька (React), віддаляє до Pixi — акцент на тій самій ноді
   консистентний (не зникає, не дублюється, однакове правило приглушення related).
2. **Один store, два підписники.** І React-near, і Pixi-far рендерять акцент hover/selection з ОДНОГО стану; хост-код
   не реалізує hover двічі.
3. **Selection не регресує.** Поточний multi-select (replace/toggle/mods, `onNodeClick`, `onSelectionChange`) працює
   байт-у-байт, як зараз.
4. **Hover як дані, не як DOM-хак.** Near-шар виставляє `hovered` у store (замість прямої DOM-маніпуляції), store
   нотифікує підписників; рендер — наслідок стану.
5. **Простіше за GoJS.** Хост підписується типобезпечною функцією на зміни `{selected, hovered}` і рендерить —
   без стрингових біндінгів, без читання глобального діаграмного об'єкта.

## Acceptance criteria (чернетка — уточнюється acceptance-spec у плані)

- **AC1 (паритет selection):** уся поточна поведінка вибору незмінна (replace/toggle/clear/mods, `primary`, порядок,
  `onSelectionChange`); наявні тести зелені.
- **AC2 (hovered у store):** є єдине джерело `hovered` (одна нода чи null); зміна нотифікує підписників; `setData`/
  видалення ноди, що під hover, коректно скидає hovered.
- **AC3 (обидва шари читають):** і near, і far рендерять hover/selection-акцент зі store; при перетині LOD акцент не
  губиться й не подвоюється (спостережуваний інваріант).
- **AC4 (near hover через store):** near-hover більше не DOM-імперативний в обхід стану — йде через store (наявна
  поведінка підсвітки зберігається візуально).
- **AC5 (emphasis недоторканий):** `found`/`highlight`/`setFoundFocus`/`highlightPath` поведінка незмінна; store D1 їх
  не містить і не дублює.
- **AC6 (0 вартості без змін):** підписка/нотифікація не додає роботи, коли стан не змінюється (нема зайвих repaint).
- **AC7 (публічний API ↔ USAGE):** будь-яка нова публічна поверхня (підписка на interaction, hover-API) описана в
  `docs/USAGE.md`.
- **AC8 (простіше за GoJS):** підписка — чиста типобезпечна функція `(state)=>…`; без стрингових DSL і глобальних мутацій.

## Out of scope

- **Pixi hover hit-test (запис hovered зі far-шару по pointermove)** — це **R1**, спирається на D1, але окремо.
  D1 дає store + читання обома шарами + запис hovered з near; far-запис — наступний пункт.
- **Emphasis** (`found`, `highlight`) — окремий зріз, свій власник.
- **`focused` / a11y / keyboard-навігація** — відкладено.
- **Marquee / shift-range мультивибір (R5)** — під D1, але окремою таскою.
- **Інжекція презентації (D2), зовнішні view-фабрики (R3), зум (R4)** — не тут.

## Рішення GATE 1 (власник, 2026-11-05)

- **Q1+Q3 → новий `InteractionStore`, єдина `subscribe`.** Тонкий `InteractionStore` **композує** наявний
  `SelectionStore` (недоторканий, разом із чистими ops) + поле `hovered`; одна типобезпечна `subscribe(state => …)`,
  на яку підписані **обидва** шари (near + far) і рендерять акцент. Не розширювати SelectionStore (не змішувати
  persist-selection і транзієнтний hovered в одному класі).
- **Q2 → `hovered: NodeRef | null`** (один; множина — складність без замовника).
- **Q4 → міграція near-hover У D1.** near-hover більше не DOM-імперативний в обхід стану: pointer виставляє `hovered`
  у store, обидва шари рендерять зі store (AC4). Інакше `hovered` не єдине джерело й стан двоїться.
- **Q5 → related-dimming = селектор** `f(hovered, mode)` на льоту, НЕ збережене поле store (щоб не десинкати) —
  як D1-деталь для highlight.
- **Q6 → публічне вже в D1.** `subscribe`/hover-API експонуються в `docs/USAGE.md` + барель одразу (хост може
  підписатись у D1).
