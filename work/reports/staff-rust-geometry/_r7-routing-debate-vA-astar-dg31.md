## STEELMAN V-A (порт орто-A* у Rust)

### A. Чому V-A найкраще задовольняє §10 (критерій → гарантія A* → чого бракує detour)

**Ключова теза:** §10 — це не «менше дефектів», а **нуль** по п'яти осях на будь-якій із 9 тестових
схем §10.1. A* + rip-up — єдиний із варіантів, чия структура дає цей нуль **конструктивно**, бо
критерій приймання і цільова функція пошуку — те саме. Мокап це вже демонструє: панель §10.4 =
`stats()` (`shps-links.js:162-172`), той самий код, що зелена плашка «0/0/0/0/0» на скріні
`13.13.11.png` (цит. `_r7-link-rules-spec-to-rust-dg30.md:28`).

| Критерій §10 (`:191-194`) | Як A* гарантує (shps-links.js) | Чого НЕ гарантує наявний detour |
|---|---|---|
| **0 перетинів ліній** (§10.4.1) | штраф 6000 за чуже ребро на слоті + 4000 за чужий вузол (`:150`) робить перетин дорожчим за будь-який обхід; якщо лишилось — rip-up 4 проходи по `stats().bad` (`:158`) | detour **per-edge, stateless** (`staff_routes.rs:10` «Пер-ребро, stateless»), **не бачить інших ліній** — occ-мапа відсутня. Два ребра можуть лягти в один corridorY. Перетини ліній взагалі **не входять** у критерій detour (той рахує лише clearance до карток/рамок). |
| **≥8px від кожної картки** (§10.4.2) | сітка будується по краях±pad(8), A* ходить лише чистими слотами `ok()` (`:134-138`); blocked-матриця mH/mV (`:122-123`) | ✅ частково — clearance-check є (`route_clear_of:290`), АЛЕ лише коли `avoid=true`; при card_pad=0 (content_padding<8) обходу немає зовсім (`staff_layout.rs:1246`, діаг D1 `:48-50`) → лінії ріжуть картки. Це **активний баг**. |
| **0 під карткою/заголовком** (§10.4.3) | `deptOK` (`:92-100`) + blocked-матриця; заголовок = `D.y1+38` заборонена смуга | detour обходить лише **ТІ рамки/картки, що він перевіряє per-edge**; §12-маркер (`staff_routes.rs:614-622`) САМ фіксує, що маршрут МОЖЕ лишитись у чужій рамці (залишок `:481`). Тобто Rust by design допускає «через чужий деп» і лише маркує. |
| **детермінізм** (§10.6) | A* + стабільний сорт ребер (`:156`), фіксована купа — однаковий вхід → однаковий вихід; rip-up детермінований (reverse за парністю) | ✅ detour теж детермінований (тест `avoidance_is_deterministic:969`) — тут паритет. |
| **перебудова на collapse/resize** (§10.5) | `render()` повний перерахунок (`:180-197`), `visible()` фільтрує collapsed (`:60`) | ⚠️ обидва варіанти однакові (перерахунок зовні); не диференціює. |

**Конкретні рядки, яких бракує в staff_routes.rs:**
1. **Немає сітки/матриці прохідності.** Мокап: `mH/mV` (`shps-links.js:121-123`), `ok(i,j,h)`
   (`:134-138`). Rust: нема зовсім — обхід по `lanes`-кандидатах `ry±pad` (`:440`), не по сітці.
2. **Немає occupancy / lane-cost.** Мокап: `occ.{nH,nV,eH,eV}` + `add/rem` (`:124-127`), ваги
   6000/4000/.15 (`:150`). Rust: нема — тому перетини між лініями не мінімізуються.
3. **Немає `aroundTop`-примітиву** (обхід ЗВЕРХУ обох карток). Діагностика: TS мав 951 aroundTop,
   Rust — 0 (`_r7-a4-2b-diag-routing-dg30.md:42-43,57`). Rust уміє лише corridorY-зсув і бічний
   H-V-H. A* природно знаходить і верхній обхід.
4. **Немає групування за керівником + шина в B** (§3.2 «вхід у B один раз, далі шина»). Мокап має
   `det`-дерева з шиною (`by`, `:109,113`); спека §3.2 вимагає; наявний Rust роутить КОЖНЕ ребро
   незалежно (нема спільної шини для кросс-деп). Прогалина зафіксована в дайджесті
   `shps-links-analysis...:105-109`.
5. **turn-penalty відсутній** — Rust не мінімізує повороти (§5.1.2 «мінімум поворотів»); A* має
   штраф 30 (`shps-links.js:150`).

### B. Обсяг порту (що саме з shps-links.js → Rust)

Портувати (нові Rust-модулі/функції, оцінка):
1. **Сітка коридорів** — `wall()`+збірка X/Y (`shps-links.js:116-119`) → ~`build_corridor_grid()`.
   ~60 рядків. Вхід: картки (вже є `EdgeRect`/`CardIndex`), рамки (`FrameRect` вже є).
2. **blocked-матриця** mH/mV + `deptOK` (`:92-100,121-123`) → `grid_blocked()`. ~80 рядків.
   `deptOK` — пряма калька §3.2; роль A/B/null із `member_of` (вже є `staff_routes.rs:227`).
3. **A* ядро** з 3-станами, купою, turn-penalty, Manhattan — `astar()` (`:130-155`) → `astar_route()`.
   ~120 рядків. Купа — можна `BinaryHeap<Reverse<...>>` зі stdlib (ponytail: не писати свою).
4. **occupancy + ваги доріжок** `occ`/`add`/`rem`/`fo`/`ow` (`:124-128,150`) → ~60 рядків.
5. **детектор `stats()`** cross/over/card/near/dept (`:162-172`) → `route_stats()`. ~90 рядків.
   **Це подвійний виграш:** той самий код стає і §10-acceptance-гейтом (golden-тест рахує нулі).
6. **rip-up loop** (`:158`) → ~20 рядків. Класифікація `det` vs `ast` (`:107-112`) → ~40 рядків.

Разом ≈ **470–530 рядків нового Rust** — приблизно обсяг теперішнього implementation-блоку
staff_routes.rs (1–639). Решта файлу (тести) переважно переиспользується.

**§6 (перебудова layout) — ЧЕСНО: у поточному Rust-лейауті НЕ досяжна в рамках V-A-порту.**
- Мокап сам §6 **не робить** — робить rip-up reroute при фіксованих позиціях (`:158`), а не
  перестановку депів. Тобто навіть референс обходиться §6-сурогатом.
- Наявний Rust явно виніс relayout у борг: `staff_routes.rs:4` «НЕ перерозкладає … §6.5 K-loop
  reorder/rebuild = relayout = борг 4a, поза T126».
- **Висновок V-A:** портувати rip-up reroute (мокапний сурогат §6) — досяжно й достатньо для
  §10.4 на тестових схемах §10.1 (мокап дає 0/0/0/0/0 БЕЗ справжнього §6). Повна §6 (перестановка
  депів у `staff_layout.rs`) — окремий майбутній зріз, НЕ блокер V-A. Це чесне обмеження, не діра:
  мокап-еталон його теж не перетинає.

### C. Перф: A* на сітці ≤50мс на ≤500 посад у WASM?

Вихідні дані: мокап **196 мс на 50 зв'язків** у JS (скрін `13.13.11.png`, цит.
`_r7-link-rules-spec-to-rust-dg30.md:28`). §10.4 вимагає **≤50 мс на ≤500 посад** (`:166`).

Аналіз — чому 196мс НЕ є вироком:
1. **Розмір сітки розріджений, не піксельний.** Вузли X/Y = лише краї±pad + середини проміжків
   ±lane (`wall():116`). Для N карток це O(N) координат на вісь, не O(ширина_в_px). Для ~50 карток
   NX,NY ≈ кілька сотень; для 500 — ~кілька тисяч на вісь у найгіршому. Сітка = NX·NY·3 станів.
2. **196мс — це JS, інтерпретований, + 4 проходи rip-up + повний DOM-рендер у `render()`.**
   `performance.now()` міряє `layout()+route()` (`shps-links.js:181`), але route включає 4
   rip-up-проходи по ВСІХ bad (`:158`) і перебудову сітки. Rust/WASM на тому ж алгоритмі —
   консервативно **5–15× швидше** за інтерпретований JS на числодробленні (ПРИПУЩЕННЯ, типовий
   порядок для hot-loop Float64Array↔Rust).
3. **Масштабування:** A* на розрідженій сітці ≈ O(E · V·logV), де V — вузли сітки. 500 посад ≈
   10× ребер проти 50. Якщо лінійно-надлінійно по E і сітка росте ~10× → наївно 196мс·(10·log)
   далеко за 50мс у JS. **Але**: (а) rust-прискорення, (б) A* ходить лише по `det`-доповненню
   (деревні ребра обходять A* зовсім, `:107-112` — більшість int-ребер!), (в) per-edge A*
   обмежений локальним підграфом (евристика відсікає далеке), (г) rip-up зазвичай сходиться за
   1–2 проходи, не 4.
4. **ОБ'ЄКТИВНИЙ РИЗИК:** 50мс на 500 посад у WASM — **НЕ доведено, лише правдоподібно**. Потрібен
   бенчмарк порту на найгіршій схемі §10.1 (п.7 широкий департамент 10+). Це ризик V-A, який
   чесно називаю; мітигації: (а) обмежити A* лише cross/ext-ребрами (int → деревна геометрія,
   вже дешева), (б) кеш сітки між перерахунками (part D), (в) ліміт ітерацій 250k уже є
   (`:144`) як запобіжник зависання.

Вердикт C: правдоподібно вкладається завдяки Rust+розрідженій сітці+A*-лише-для-cross, але це
**єдина теза V-A, що вимагає емпіричної перевірки**, а не лише коду.

### D. Контракт/кеш під edit-mode (§8.3)

§8.3 (`:163`): перерахунок на resize/dates/avatar/collapse/дані. [[staff-geometry-single-truth-and-caching]]:
динаміка → кеш незмінних нод.

- **A* дружній до інкрементальності помірно.** Сітка — функція позицій карток+рамок; при зміні
  ОДНІЄЇ ноди змінюється локальна ділянка сітки, решта стабільна → кеш сітки + інвалідація за bbox
  реально. Per-edge A* природно перераховує лише ребра в зоні зміни (ті, чий `stats().bad` або
  чиї ендпоінти/перешкоди рухались).
- **Контракт НЕ змінюється:** вихід V-A — той самий `StaffEdgeRoute.points` (`types.rs:599`), ті
  самі optional `marked`/`ends_on_dept_top`. Для хоста перехід detour→A* **невидимий** на рівні
  типів — змінюється лише вміст `points`. Це сильний аргумент: V-A не торкає публічний контракт.
- **ПРОТЕ:** rip-up — **глобальний** крок (bad-set залежить від усіх ліній, `stats()` сканує всі
  сегменти, `:165-170` O(сегменти²)). Чистий інкремент «порахувати лише змінене ребро» ЛАМАЄТЬСЯ,
  якщо нове ребро створює перетин з існуючим → треба перемаршрутити й сусіда. Detour (stateless,
  per-edge) тут **структурно простіший** для інкременту — це перевага V-C, чесно (part E).
  Мітигація V-A: інкрементальний rip-up лише в зоні конфлікту (локальний bad-set), не повний.

### E. Найсильніше заперечення проти V-A (чесно)

**E1 (найсильніше — на користь V-C «доробити detour»): V-A викидає вже працюючий, протестований
код.** staff_routes.rs має ~25 unit-тестів (`:752-1626`), A2.1 просторовий індекс (байт-паритет
доведено `card_index_matches_naive:1016`), A2.2/A2.3 ладдер, A2.4 deptTop, §12-маркер — усе зелене
й злите (коміти `75f7d0b`, `e6bc57e`, `976ebfb`). V-C каже: **головний дефект §10 — це card_pad-
гейт (`staff_layout.rs:1246`), однорядковий баг** (діаг D1 «домінантна причина», `:48`). Прибери
гейт — обхід вмикається безумовно (як TS), і більшість «через картки» зникає БЕЗ переписування
470 рядків. V-A ризикує перебудувати те, що лагодиться 1 рядком + дотягуванням clearance-логіки.

**E2: detour вже вирішує 2 з 5 осей §10** (card-clearance §10.4.2, частково dept §10.4.3 через
side_detour+marker). V-A вартий лише заради осей, які detour НЕ закриває — **перетини між лініями**
(§10.4.1) і **повний dept-обхід** (§10.4.3 без залишку). Якщо продукт готовий жити з §12-маркером
(видимий залишок замість 0), приріст V-A над V-C **мінорний** за великої ціни.

**E3: §6/rip-up — найбільша зачіпка.** rip-up глобальний (E-вище, part D), перетинає інваріант
«staff_routes НЕ перерозкладає» (`:4`) й тягне стан (occ-мапи), чого stateless-detour уникав.
Більший blast-radius, важчий інкремент edit-mode.

**E4: перф НЕ доведено** (part C) — 196мс JS → 50мс WASM на 500 посад лише правдоподібно. V-C/V-B
не мають цього ризику взагалі (вони дешевші за конструкцією).

**E5: byte-parity з TS остаточно ламається.** V-A свідомо обирає мокап+§10 за еталон (не TS).
Якщо хост ще десь очікує TS-ідентичні точки (хоча `_r7-link-rules...:32` каже «SDK без споживача,
еталон = мокап/GoJS») — V-A це закриває назавжди. Для адвоката V-A це фіча (§10 важливіший за
TS-паритет), але чесно: це незворотнє рішення.

**Контр-відповідь адвоката V-A на E1–E2:** card_pad-фікс (V-C) прибирає «через картки», але
**НЕ дає 0 перетинів між лініями** — цього в detour немає взагалі (part A, рядок occ відсутній).
§10.4.1 — перший і головний критерій спеки («Головна вимога: лінії не перетинаються»,
`Вимоги...:3`). Жоден варіант, що не моделює взаємодію ліній (occ/rip-up), §10.4.1 на складних
схемах (§10.1 п.4 доріжки, п.5 обхід через рівень) гарантувати не може. Тому V-C — необхідний
швидкий фікс, але НЕ достатній для повного §10. V-A — єдиний повний.

## РЕЗЮМЕ ПОЗИЦІЇ V-A
Портувати орто-A*+rip-up з мокапу — **єдиний варіант, що закриває ВСІ п'ять осей §10**
конструктивно, бо цільова функція пошуку = критерій приймання (той самий `stats()`/детектор).
Наявний detour структурно НЕ моделює перетини ліній (§10.4.1 — головна вимога спеки) і лишає
залишки через чужі рамки (§12-маркер = самовизнання). Обсяг ~470–530 рядків; §6 повна — поза
скоупом (мокап теж обходиться rip-up-сурогатом). Контракт `StaffEdgeRoute.points` НЕ змінюється.
**Чесні слабкості:** (E1) викид робочого коду проти однорядкового card_pad-фіксу V-C; (E3) rip-up
глобальний → важчий edit-mode-інкремент, ніж stateless detour; (E4) перф 50мс/500 у WASM —
правдоподібний, але НЕ доведений, єдина теза, що потребує бенчмарку.
