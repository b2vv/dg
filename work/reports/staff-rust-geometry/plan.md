## 1. R1 — межа Rust/TS (що переходить у Rust, що лишається адаптером)

**ВХОДИ в Rust** (контракт, напрям знання TS→Rust через аргументи виклику):
- розміри кожної ноди (w×h) — **з DOM-виміру змісту** (content-driven, O-16.1); на far/mid, де DOM нема — з кешу/декларованого фолбеку (див. R2);
- дерево: орг-блоки, відділи, namespaces (lead/current/subordinate), належність посад;
- правило порту `edgePort` (`center`|`avatar`, T125) — декларація форми порту (вже існує, `render/types.ts`);
- gaps/padding обгорток, LOD (near/mid/far) — як параметри.

**ВИХОДИ з Rust** (єдине джерело, одна система координат):
- координати нод; пакування відділів і обгорток (з внутрішніми відступами); композиція ярусів + namespaces + вісь; межі обгорток і namespaces; **точки лінків = повні ортогональні маршрути** (Q-3→O-48) per-LOD.

**Що переходить у Rust (сьогодні в TS, підтверджено грепом):**
- `computeOrgRowTreeLayout` (`core/src/lib.rs:20`) — вже Rust, розширюється;
- пост-проходи TS → Rust: перецентрування кореня (`orgBlockLayout.ts`), пакування/зсув регіонів (`staffDeptGrouping.ts`), композиція/зсуви ярусів (`canvasLayout.ts:43` `layoutStaffCanvas`), пост-центрування осі, межі обгорток (`staffZoneBounds.ts`);
- точки лінків: сьогодні рахує рендер per-LOD (`visualEdgeBox.ts`, `staffEdgeGeometry.ts`) → у Rust.

**Що лишається тонким TS-адаптером:** виклик WASM, передача DOM-розмірів, маппінг результату на Pixi/React/SVG. **Rust-стандарт** (нема документованого, маніфест §core): R1 задає мінімум — `cargo fmt`/`clippy -D warnings` вже гейт; додати короткий `packages/core` convention-нот (окрема дрібна задача, не блокує).

## 2. R2 — розрив циклу DOM↔Rust

**Ризик (B1):** content-driven висота ← вимір DOM ← рендер ← лейаут ← висота. Цикл. На 1-му кадрі DOM не змонтовано; на far/mid DOM-карток нема (вид Pixi, підтверджено Dg18 F4: Fit zoom 0.82 = Pixi).

**Рішення (обрати в R2-спеці, рекомендація тут):** **two-pass headless-вимір без позиції**:
1. пас A: виміряти зміст кожної картки headless (прихований DOM-вимірювач, без розкладки) → w×h;
2. пас B: Rust-лейаут із цими розмірами → координати;
3. кеш розмірів за ключем контенту; на far/mid джерело розміру — кеш або декларований фолбек із теми.
**Ключ кешу (N-3):** склад ключа = усі поля контенту, що впливають на розмір (текст заголовка/підзаголовка, к-сть рядків, бейджі, стан). Зміна будь-якого → новий ключ → інвалідація; стала геометрія інакше.
**Гонка (Д3, N-generation):** кожен запуск `layoutStaffCanvas` (async) має **generation-токен**; результат проходу, чий токен застарів, відкидається (**latest-wins**) — свіжий лейаут не перезаписується старим при подвійному Fit / двох вкладках.
**Критерій:** жодного фідбек-ребра layout↔DOM у рантаймі (вимір передує лейауту, не навпаки).

## 3. Reuse-first (маніфест: що переюзуємо / нове / чому)

| Переюзуємо | Чому підходить |
|---|---|
| `computeOrgRowTreeLayout` (Rust) | ядро row-tree вже в Rust; розширюємо, не переписуємо з нуля |
| `edgePort` (T125, `render/types.ts`) | декларація форми порту — готовий вхід у Rust |
| паритет live/SVG точок лінків (обидва через `mapStaffEdgeBoxesForLod`) | зберегти; міграція не має його зламати |
| `ts-rs` канал типів (`types.rs`→`rust-types.ts`) | штатний односторонній канал контракту |
| алгоритм v3 маршрутизації (`shps-routing` spec/design-v3) | приймальна спека R6; конструктивний layered + K-проходи — основа переносу |

| Нове | Чому існуюче не підійшло |
|---|---|
| Rust-пакування відділів/обгорток/осі | сьогодні в TS пост-проходами (`staffDeptGrouping`, `canvasLayout`) у **іншій** системі координат → розсинхрон (проблема spec §1) |
| Rust-межі обгорток як єдиний вихід | live і SVG рахують **різними** формулами (дефект «двох правд», `DiagramRenderer.ts:1220` vs `svgExport`) |
| `/debug` ідентичності canvas=DOM | нема; вимога O-16.2 |
| Rust-маршрути з обходом перешкод | проді-роутер (`v2`) урізаний (нема edge-edge, доріжок, `deptTop/Bottom`) |

**Відкинуте (не ухвалено власником):** «єдиний TS-сайт якоря замість Rust» (Candidate A, арх-аналіз) — власник обрав велику Rust-міграцію (O-15); лишається в спеці лише для порівняння.

## 4. Сайд-ефекти (обов'язково)

- **Ламається форма результату розкладки** `tiers`→`namespaces` — **усі споживачі в одній зміні** (греп підтвердив ≥6: `canvasLayout`, `StaffZonesView`, `staffZoneBounds`, `personInteractions`, `render/types`, тести + `svgExport`, `e2eBridge`, `DiagramRenderer`). Хост SDK `tiers` не споживає (`AGENTS.md`) → публічний API хосту не рветься понад це.
- **WASM-межа навантажується**: пакування/композиція/маршрути тепер через FFI. Перф — A10 (≤2-3с, O-52), вимір R10.
- **Відмова WASM у рантаймі (Д2):** після R7 TS-пост-проходів більше нема → **рантайм-TS-фолбеку немає свідомо**. Поведінка при падінні WASM = **явний стан помилки** (порожня сцена + повідомлення), не старі координати й не білий екран (F7). Запобігання: `build:wasm` — твердий CI-гейт, зламаний модуль у реліз не потрапляє. Прапор §6 — dev-відкат, **не** рантайм-деградація (named: це різні механізми).
- **`staffEdgeRouter:'v2'` + сцена `staff-dept-v2`** — проміжні до R6, потім видаляються (O-41).
- **Стек-нота `AGENTS.md`** («canvas paint is TS») стає неправдивою → оновити в тому ж коміті (R9). ⚠️ `AGENTS.md` каже «contours» у `core`, а `core/src` має лише row-tree → виправити (R9).

## 5. План міграції (обов'язково)

1. **R0 baseline** (= T127a-a0): golden-знімки **нормалізованої геометрії**, інваріантної до імені секції-смуги — `positionNodes` (координати), межі обгорток, `orgCards`, `edges`, ±1px. **НЕ знімати у формі `namespaces`:** до R7 результат має секцію `tiers` (`types.ts:152`), тож «ідентичний до=після» можливий лише на геометрії, не на імені секції. Перейменування `tiers`→`namespaces` (R7) перевіряється **окремо** адаптером (еквівалентність `namespaces`→`tiers`-форма), а не golden-порівнянням. Golden зелений до змін (свідомий виняток із «червоний першим»; мутація ловиться). Захищає I-R1. **[GATE 2 B-1]**
2. **R1/R2 спеки** (цей план + окремі під-спеки) з критиком — GATE 2.
3. Rust поетапно за прапором/паралельною гілкою результату: R3 пакування (+contours/частини відділів, S7; +I-A2) ∥ R4 композиція/namespaces/вісь → R5 межі (єдиний вихід, live+SVG паритет) → R6 маршрути (повні, per-LOD) → R7 TS-адаптер + видалення пост-проходів (ламаємо форму) → R8 `/debug`.
4. **R9 документи** (ADR-0002 вже переписано; стек-нота, SPEC, USAGE якщо чіпає публічне) + **R10 гейти** (без pipe) + перф.

## 7b. Перешкоди маршрутизації на far/mid (N-4)
Джерело набору перешкод (картки, рамки відділів, смуга `.dn`) на **всіх** LOD — **Rust-геометрія**, не DOM: на far/mid DOM-карток нема (Dg18 F4), тож перешкоди беруться з того самого Rust-виходу, що й координати. Це робить маршрути незалежними від LOD-рендеру (вимога R6).

## 7c. Архітектурна перевірка «TS пост-проходів нема» (N-1)
Відсутність TS-пост-проходів після R7 — **не** e2e-спостережуване; перевіряється **грепом/архітестом** (немає викликів видалених функцій пакування/композиції поза Rust-адаптером), а поведінка H1 — збігом зі знімком Rust-виходу.
