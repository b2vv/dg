## АРГУМЕНТ ЗА Варіант 1 (найсильніша чесна версія)

### 1. Узгодження з ціллю «одна істина координат» + негайні вигоди
- **Ціль власника буквально = Rust як ЄДИНА істина.** Варіант 1 — єдиний, що її реалізує негайно й
  без компромісу: baseline просто фіксує те, що Rust реально рахує. Будь-який варіант, де TS лишається
  обчислювачем (гейт matrix на TS, «прийняти layout але не routing»), зберігає паралельний
  TS-калькулятор — те, що ціль прямо наказує усунути.
- **Дія проста й атомарна:** `UPDATE_GOLDEN=1`, один коміт. Не треба переписувати `packages/core` під
  TS-контракт (D2/D3 — свідомо інша логіка; підганяти Rust під TS = заморозити TS-геометрію як вічний
  контракт, що суперечить самій меті переносу).
- **Усуває найтоксичніший борг:** два паралельні геометричні рушії, що «майже збігаються» — це пастка
  (кожна майбутня правка має триматися байт-паритету в двох мовах). Варіант 1 обриває її одним рухом.
- **D2/D3 на боці Варіанта 1 як АРГУМЕНТ, а не баг:** clearance-модель замість interior-перетину і
  corridorY-detour замість aroundTop — це *легітимні інженерні рішення* нового рушія. Вимагати від
  Rust байт-відтворення TS-aroundTop (fixed pad=16) означає канонізувати випадкові константи старого
  TS як специфікацію. Якщо Rust-геометрія візуально коректна — байт-розходження з TS нерелевантне.

### 2. Критичні передумови/ризики (чесно — тут аргумент і ламається)

**(a) Routing стає ПРОДУКТОВОЮ поведінкою — і D1 робить її ВІЗУАЛЬНО ХИБНОЮ, не просто іншою.**
- diag-routing ФАКТ1 (доведено декодуванням + кодом): у staff-tree вертикаль Rust x=92, y∈[500,634]
  проходить ВСЕРЕДИНІ картки pos-lead (x∈[24,160]∋92, y∈[552,708]∩[500,634]=[552,634]). Тобто **лінк
  фізично ріже чужу картку**. TS уникав цього через aroundTop(328); Rust лишив сире.
- Це той самий staff-link-центрування клас багів, що вже в пам'яті (`link-centering-cell-vs-card`) —
  тобто візуальний регрес, який власник уже лічив дефектом раніше.
- Масштаб: ~1129 маршрутів по всіх сценах втратили обхід (aroundTop 951→0, +horizontal 178→10). Це
  НЕ субпіксельний шум, не f32 — це систематичний клас маршрутів, що тепер перетинають геометрію.
- **Присуд по (a):** card_pad-гейт — не «інша логіка», а БАГ (diag-routing D1, висока впевненість:
  TS обходить картки БЕЗУМОВНО, гейта content_padding в TS НЕМАЄ). Rebaseline заморозив би лінки-крізь-
  картки як «істину». Це провал, не вигода.
  ⚠️ ПОПРАВКА до аргументу 1-D2/D3: clearance-vs-interior (D2) і corridorY-vs-aroundTop (D3) справді
  можуть бути легітимно-іншими. Але D1 (card_pad=0 → ЖОДНОГО обходу) — не естетика, а відсутність
  обходу взагалі. Доки D1 не полагоджено, «візуально коректна Rust-геометрія» — хибна передумова.

**(b) matrix-сцени втрачають matrix-розкладку → tree. Це однозначний продуктовий регрес.**
- variant-b/worker (6 вузлів кожна), magnetic (12), staff-1m (633) — усі matrix у TS стають tree у Rust
  (diag-layout, 1:1 мапінг diff). staff-1m: компактна сітка w=7064 → ряд дерева w=135608 (~19×).
- Це не «інша розкладка тієї ж якості» — це ВТРАТА режиму відображення, який продукт свідомо має
  (demo-дані реально несуть gridCell/layoutCoords). Користувач, що бачив компактну матрицю, побачить
  кілометровий горизонтальний ряд.
- **Ключове питання власника з брифу:** «чи можна прийняти Rust як істину, НЕ полагодивши matrix?»
  **Відповідь: НІ.** Matrix у Rust-контракті структурно недосяжний (координат членів немає у
  `StaffLayoutInput`; staff_layout.rs tree-only). Rebaseline зафіксує matrix-сцени як зламані.
  Чистий rebaseline НЕжиттєздатний без окремого фіксу (або Rust приймає координати+matrix, або
  адаптер гейтить matrix на TS — а останнє повертає паралельний TS-шлях, тобто вбиває саму ціль).

### 3. Що треба НЕЗАЛЕЖНО підтвердити ПЕРЕД будь-яким rebaseline (щоб не заморозити дефект)
1. **Візуальний рендер, не лише golden-числа.** Golden — це JSON координат; він НЕ скаже, що лінк
   ріже картку чи що matrix розтягся. Треба відрендерити ≥ staff-tree (routing-регрес) + staff-1m/
   variant-b/magnetic (matrix-регрес) у реальному демо й подивитись очима / скриншотом. ДОСІ НЕ
   ЗРОБЛЕНО (усе дотепер — JSON-diff).
2. **Підтвердити, що D1-вертикалі реально перетинають картки в кількох сценах**, а не лише в одному
   декодованому прикладі (ФАКТ1 — одна точка; потрібна вибірка з ~1129).
3. **Підтвердити, що D2/D3 (clearance/corridorY) НЕ дають власних перетинів** — бо якщо нова
   detour-геометрія теж десь ріже, то «інша але коректна» теж falls.
4. **Рішення по matrix ДО rebaseline:** чи matrix взагалі лишається продуктовою фічею. Якщо так —
   rebaseline без фіксу неприйнятний. Якщо matrix депрекейтиться — це окреме продуктове рішення
   власника, не наслідок wiring.

### 4. За яких умов Варіант 1 ПРАВИЛЬНИЙ / ХИБНИЙ
**Правильний, якщо (усі умови):**
- D1 (card_pad-гейт) спершу полагоджено в Rust так, що обхід карток БЕЗумовний (не залежить від
  content_padding) → лінки не ріжуть картки; І
- matrix або реалізовано в Rust, або свідомо депрекейтнуто власником; І
- проведено візуальну (не лише числову) приймальну перевірку зачеплених сцен; І
- D2/D3-геометрія підтверджена як візуально чиста.
  → Тобто Варіант 1 коректний ТІЛЬКИ ПІСЛЯ фіксів — тоді rebaseline легітимний, бо фіксує
  *коректний* Rust, а не поточний.

**Хибний (поточний стан), якщо:**
- rebaseline роблять ЗАРАЗ, поверх невиправленого Rust → заморожує два доведені дефекти
  (лінки-крізь-картки D1 + matrix→tree) як «істину». Golden стане зеленим, але продукт — гіршим.
  Зелений golden тут = відсутність інформації (асерт під змінений вихід), не доказ коректності.

**Припущення / не доведене:**

- Що D2/D3-геометрія візуально коректна (ніхто не рендерив; «легітимно інша» — гіпотеза).

## ПРИСУД (чесний, не адвокатський)
**Варіант 1 у чистій формі (rebaseline ЗАРАЗ) — ПРОГРАЄ.** Не тому, що ціль хибна — ціль (Rust як
єдина істина) правильна й Варіант 1 єдиний, хто її прямо реалізує. А тому, що ДІЯ передчасна: golden
зафіксував би два доведені дефекти (D1 лінки-крізь-картки; matrix→tree) як канон. Golden числовий і
сліпий до візуального регресу — зелений прогін тут нічого не доводить.

Варіант 1 стає правильним ЛИШЕ як ПІСЛЯ-фіксу крок: полагодити D1 (безумовний обхід) + вирішити
matrix, провести ВІЗУАЛЬНУ приймальну перевірку — і аж тоді rebaseline на *коректний* Rust. У такій
секвенції Варіант 1 фактично зливається з Варіантом 2/3 на вході, а чистим джерелом істини стає на
виході. Пропонувати «rebaseline зараз» як самостійний крок — не можна.
