# СИНТЕЗ — A4.2b parity: діагностика + дебати 3 варіантів (dg30, 2026-10-30)

Оркестраторський синтез (НЕ рубер-стемп). Джерела: finding `_r7-a4-2b-PARITY-FAILURE-dg30.md`,
діагностика D1/D2, дебати V1/V2/V3 (усі 3 повернулись). Усі пивоти спот-чекнуті в коді трьома агентами.

## Що встановлено (факти, доведені кодом)
1. Розходження Rust↔TS має **три роздільні природи** (не враження — роздільні на рівні коду):
   - **Клас 1 — явні БАГИ (об'єктивні):** (a) routing card_pad-гейт `content_padding>=8` без TS-аналога (staff_layout.rs:1246); (b) layout: matrix-координати викинуті в buildStaffLayoutInput.ts:226-231 + відсутній обіцяний matrix-гейт.
   - **Клас 2 — свідомо інша логіка routing:** clearance-vs-interior (eps0.75); detour corridorY/side_detour vs TS aroundTop(pad=16). Rust не має aroundTop-примітиву; A2.2-ладдер сам визнає «behavior change».
   - **Клас 3 — архітектурна ПРОГАЛИНА:** `StaffPositionInput` (types.rs:324) НЕ несе координат → matrix структурно недосяжний у Rust. Rust tree-only.
2. **f32 (Rust) vs f64 (TS): byte-parity недосяжна й не мета** — golden толерує ±1px. Реальний f32-ризик — флип гілки біля порога (не поглинається толерансом).
3. **§5 брифінгу підтверджено: SDK досі НЕ має споживача** (CTO-RESEARCH рядок 266; host на GoJS, grep @org-hierarchy=0). Перша інтеграція = приймання. Pixel-exact картки — host HTML-overlay (рядок 71).

## Конвергенція дебатів (сходяться всі три)
- **Rebaseline ЗАРАЗ (V1 чистий) — програє одноголосно**, навіть власний V1-агент: заморозив би два ДОВЕДЕНІ дефекти як канон (ребро крізь картку pos-lead у staff-tree; matrix→tree 19× на staff-1m). golden числовий і **сліпий до перетинів/розтягу** → зелений ≠ коректність.
- **matrix-прогалина робить зміну вхідного контракту неминучою в БУДЬ-ЯКОМУ варіанті** (V2 і V3 незалежно): Rust не може бути істиною, не отримавши координат членів. V2-висновок: раз контракт все одно зміниться — логічніше спроєктувати КРАЩИЙ контракт, ніж консервувати TS.
- **V2 (усе під TS-паритет) ризикує законсервувати слабку TS-логіку** (fixed pad=16, квірки ладдера) як постійний Rust-контракт — заради паритету, якого НІХТО сьогодні не споживає (§5).
- **V3 судить КЛАС, не множину:** клас1→фікс (об'єктивно); клас2→тимчасово привести до TS, вердикт «чи Rust кращий» у чергу з вимогою ЗОВНІШНЬОГО якоря (ADR/візуальний еталон); клас3→одне продуктове рішення.

## MATRIX — семантика від власника (dg30) + розмежування в коді
Власник розписав дві матриці:
- **#1 matrix у СТРУКТУРІ ОРГАНІЗАЦІЇ (працює зараз, лишається):** діти-ноди → matrix коли ВСІ collapsed; будь-яка розкрита → tree; майбутній режim «short» (одна розкрита + картка з лічильником прихованих, hover розсуває). **Код:** це ОРГ-діаграма — `collapsedSiblingGrid.ts`/`matrixGrid.ts`/`orgMode.ts`/`ploeg_layout.rs` (T113 локальне per-sibling-set). **Окремий шлях — вже Rust (`computeOrgRowTreeLayoutWasm`), A4.2b НЕ чіпає. Безпечно.**
- **#2 matrix ПОСАД у staff-канві (ШПС):** користувач переставляє посади вільно; **зараз це «дерево»**, matrix — майбутнє (з фіксуванням рівнів тощо). **Код:** `orgBlockLayout.ts` tree/matrix/hybrid, тригер `positionHasCoords`. **Саме це чіпає A4.2b.**

→ staff-golden сцени (variant-b/staff-1m/magnetic) рендеряться position-matrix у старому TS = кейс #2 = «tree now / matrix future». Відкрите питання власнику: чи Rust tree-only для staff ЗАРАЗ = бажана поведінка (matrix→tree не регрес, а конвергенція до «staff=tree»), а staff-matrix відкласти до майбутнього разом із розширенням Rust-контракту.

## Єдине справжнє рішення, що потребує власника (MIN-2)
**matrix:** (A) прокинути координати членів у Rust-контракт + написати matrix-режим у Rust (одна істина, більший core-обсяг) — АБО — (B) тимчасовий документований seam: адаптер гейтить саме matrix-сцени на TS-layout, решта — Rust (дві істини тимчасово, ADR + умова закриття).
→ Власник пише опис матриць (де живуть, що вмикає, як мають розкладатись, де мають рахуватись, чи TS-поведінка правильна). Це прямо обирає A vs B.

## ✅ РІШЕННЯ ВЛАСНИКА (dg30): Staff = дерево зараз, matrix відкласти (варіант A)
- Rust tree-only для staff = ПРАВИЛЬНА поточна поведінка. `matrix→tree` у golden-сценах (variant-b/staff-1m/magnetic) — бажана конвергенція, **НЕ регрес**.
- staff-matrix (orgBlockLayout matrix/hybrid) → майбутня задача (A4.x+) з розширенням Rust-контракту (координати членів). Не будувати зараз.
- Демо-сцени: лишити tree АБО зняти з них координати (деталь реалізації).
- Наслідок: **node-layout-блок знято** (окрім перевірки, що tree-вихід сам коректний — staff-1m широке дерево; gojs detached — див. нижче).

### Що ЛИШАЄТЬСЯ блокером A4.2b після цього рішення (усе про ROUTING + detached, НЕ matrix):
1. **D1 card_pad-гейт — БАГ:** Rust не обходить картки при content_padding<8 → лінки РІЖУТЬ картки (доведено staff-tree pos-lead). Фікс у Rust core (безумовний обхід). Обов'язково перед будь-яким rebaseline.
2. **D2/D3 routing-геометрія (clearance/detour):** але з «staff=tree» + §5 (нема споживача) ЦІЛЬ routing = **візуальна КОРЕКТНІСТЬ**, а не byte-паритет до TS-евристик. Тобто Rust-detour приймається, ЯКЩО візуально чистий; не треба портувати TS aroundTop заради паритету. Клас-2 здебільшого РОЗЧИНЯЄТЬСЯ.
3. **gojs detached-inference:** tree-mode розходження (pos-sup/pos-vac TS=detached side-column, Rust=tree), корінь не доведено до рядка. Треба допильнувати й вирішити (ймовірно Rust-баг).
4. **golden сліпий до перетинів** → ВІЗУАЛЬНА приймальна перевірка обов'язкова перед rebaseline.

## Рекомендація (ФІНАЛ, після рішення варіант A)
matrix знято → ціль спростилась до «Rust-геометрія КОРЕКТНА, не паритетна до TS-евристик» (§5: нема споживача; staff=tree). Шлях = V1-як-фінальний-крок, де-ризикований:
- **R1 (Rust core):** полагодити card_pad-гейт (staff_layout.rs:1246) — безумовний обхід карток. БАГ, об'єктивно.
- **R2 (діагностика→фікс):** допильнувати gojs detached-inference до рядка; якщо Rust-баг — полагодити (tree-mode, не matrix).
- **R3 (візуальний гейт):** побудувати/прогнати ВІЗУАЛЬНУ приймальну перевірку зачеплених сцен (golden сліпий до перетинів). Еталон коректності — GoJS-рушій хоста, не TS.
- **R4 (rebaseline):** коли R1+R2 зелені й R3 візуально чистий → rebaseline golden на Rust-вихід (приймаючи matrix→tree як staff=tree + Rust-routing/detour як коректний). Єдина істина досягнута.
- **R5 (черга A4.x):** staff-matrix у Rust (контракт+режим); вердикт clearance/detour лише якщо R3 покаже проблему.
Обсяг: R1-R2 — Rust core (не лише wiring) → A4.2b розширюється в core. Потребує «го» власника на scope.
