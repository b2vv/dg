# СИНТЕЗ — дебата підходу до correct-link-routing у Rust (dg31, 2026-10-30)

Оркестраторський синтез (НЕ рубер-стемп). Джерела: 3 адвокат-файли V-A/V-B/V-C (усі 3 повернулись),
ledger `_r7-routing-debate-LEDGER-dg31.md`. Усі пивоти — з path:line в адвокат-файлах.
Питання: ЯК реалізувати коректний link-routing ШПС у Rust під §3–§10. Еталон = мокап + скріни + §10.

## Де три варіанти СХОДЯТЬСЯ (конвергенція, зняти з дебати)
1. **card_pad-гейт (`staff_layout.rs:1246`) — об'єктивний БАГ, 1 рядок.** Усі три згодні: обхід карток
   лише при content_padding≥8, спека §5.1.3 вимагає безумовно (dg30 D1: саме це дало aroundTop 951→0
   у TS). Лагодиться НЕЗАЛЕЖНО від обраного варіанта, блокує будь-який rebaseline (вже в черзі dg30 R1).
2. **§10.1 «0 перетинів ліній» — ГЛОБАЛЬНА властивість.** Наявний detour `stateless, per-edge`
   (`staff_routes.rs:10`) її структурно НЕ моделює (нема occupancy-мапи) → на crossing-важких сценах
   (дві лінії на тій самій corridorY; два side_detour з одного боку; крос-деп bi/ib зі скріна 13.13.11)
   дасть перетини. Це визнають і V-C, і V-A.
3. **АЛЕ мокап-A* теж НЕ ГАРАНТУЄ crossing-free** (V-C і V-A незалежно): occ-штраф (`shps-links.js:150`)
   + 4 re-route паси (`:158`) + звіт лишку (`:171 fail`). «0» на панелі = емпірика на фіксованих сценах,
   не доказ. Різниця detour↔A* = **RATE, не гарантія**. Спека §5.3.4/§6.5 офлодить тверді перетини в
   §6-relayout для ВСІХ варіантів.
4. **§6 layout-rebuild не реалізований у ЖОДНОМУ варіанті** — спільний борг (`staff_routes.rs:4`), не
   дискримінатор між варіантами.
5. **Контракт `StaffEdgeRoute.points` (`types.rs:599`) НЕ змінюється** ні у V-A, ні у V-C — перехід
   detour↔A* невидимий для хоста.
6. **Детектор `stats()` з мокапу (`shps-links.js:162-172`)** — подвійний виграш: це той самий детектор,
   що дає панель §10.4 (0/0/0/0/0) на скріні-еталоні. Корисний УСІМ варіантам як §10-acceptance-гейт
   (та сама верифікаційна діра R3 з dg30). Його варто портувати ПЕРШИМ, незалежно від вибору.

## V-B — знято з рантайму (але є salvage)
- §9 спеки ПОІМЕННО дозволяє ELK (`спека:182`, «якщо задовольняє §5–§7») — єдиний прямий текст за V-B.
- Але роутинг УЖЕ в Rust (`staffLiveGeometry.ts:97 computeStaffGeometryWasm` → `adaptStaffGeometry:105,113`);
  V-B = **демонтаж уже реалізованого**, пряме зіткнення з мандатом O-33/O-48 («маршрути рахує Rust, одна
  правда»; Q-3 закрито як «ПОВНІ МАРШРУТИ»). JS-роутер = друга система = та «дві правди», яку лікує T126.
- Вага ~1.5MB GWT-JS, async-воркер, batch-перерахунок → погано лягає на edit-mode (рішення dg30 #4).
- **Salvage:** ELK + `stats()` як ОФЛАЙН-ОРАКУЛ коректності в тестах (не рантайм) — використати §9-дозвіл
  і зрілість орто-роутингу як доказ, що задача розв'язна, + тестовий оракул. Рантайм лишається Rust.

## V-A vs V-C — це НЕ «або/або», а ПОСЛІДОВНІСТЬ (ключовий висновок синтезу)
Обидва адвокати, знявши адвокатську позу, зійшлися на одному шляху:
- **V-C:** card_pad + header+4px + track-пост-пас §5.4 → виміряти візуально → ескалація до occ-pathfinding
  лише якщо лишаться open-canvas перетини. «V-C = найдешевший спосіб дізнатись, чи V-A взагалі потрібен».
- **V-A:** визнає, що card_pad-фікс (V-C) прибирає «через картки», але не дає 0 перетинів ліній; V-C
  **необхідний, але не достатній**; §6 поза скоупом; перф A* **не доведено**; rip-up глобальний → важчий
  edit-mode-інкремент.
- **~Половина 486 рядків** (спільна геометрія/clearance/CardIndex) потрібна В ОБОХ — A* будується ПОВЕРХ
  неї, не з нуля. «Виграш 486 рядків» V-C тане до «виграш ~половини» лише якщо дійде до повної заміни ядра.

→ Отже оптимальний план = **staged V-C → (візуальний гейт) → V-A-шар за потреби**, з детектором `stats()`
наперед як гейтом. Він: лагодить об'єктивний баг зараз; зберігає 486 рядків + ~25 тестів; поважає
edit-mode (старт stateless, глобальний пас додається обмежено); лишається в Rust (знімає V-B); робить
вердикт «A* чи ні» ДОКАЗОВИМ (візуальний вимір), а не платить ~500 рядків A* наперед під недоведений перф
і crossing-free-гарантію, якої навіть мокап не дає.

## Справжня РОЗВИЛКА, що належить власнику (не агенту)
Усе зводиться до **планки приймання §10.1**:
- **(Бар-1) Візуально чисто на ВІДОМИХ staff-сценах** (мокап-подібні, ~фіксовані позиції, еталон = GoJS/мокап):
  → staged V-C-first ймовірно достатній; A*-шар може не знадобитись. Узгоджено зі «staff=tree now» + §5
  (нема споживача) + edit-mode-пріоритетом.
- **(Бар-2) Гарантовано низький rate перетинів на ДОВІЛЬНИХ open-canvas даних** (користувач вільно
  переставляє посади): → occ-pathfinding (V-A-шар) зрештою потрібен; detour структурно недостатній.

Вторинні рішення власника:
- Чи портувати `stats()`-детектор зараз як §10-acceptance-гейт (рекомендація: ТАК — спільний виграш,
  розблоковує візуальний гейт R3).
- Підтвердити: мандат O-33/O-48 лишається в силі для МАРШРУТІВ (не лише якорів) тепер, коли §5 каже «нема
  споживача»? «Так» → V-B мертвий як рантайм (очікувано); ELK лишається тестовим оракулом.

## РЕКОМЕНДАЦІЯ ОРКЕСТРАТОРА (не рішення — на «го» власника)
**Staged-підхід, Бар-1 за замовчуванням:**
1. Портувати `stats()`-детектор §10 у Rust/тести — acceptance-гейт (спільний, розблоковує R3).
2. card_pad-гейт `staff_layout.rs:1246` — безумовний обхід (об'єктивний баг).
3. header+4px як окрема перешкода + track-allocation пост-пас §5.4 (закриває коридорні перетини).
4. **Візуальний гейт** проти скрінів/мокапу на зачеплених сценах.
5. Якщо лишаються перетини на сценах, що мають значення → додати occ/rip-up шар (V-A) ПОВЕРХ наявної
   геометрії, НЕ переписуванням з нуля; перф-бенчмарк на найгіршій схемі §10.1 п.7.
Чому не V-A одразу: платити ~500 рядків A* + важчий edit-mode-інкремент наперед, під недоведений перф і
гарантію, якої й мокап не дає — коли §5 (нема споживача) + staff=tree дають простір виміряти дешевше.
Чому не V-C як фінал: detour структурно не дає §10.1 на довільних сценах — тому Бар-2 ⇒ A*-шар неминучий.

Відкрито власнику: Бар-1 vs Бар-2; порт `stats()` зараз (так/ні); підтвердження O-33/O-48 для маршрутів.

## ✅ РІШЕННЯ ВЛАСНИКА (dg31, через інструмент вибору — явне, не інтерпретація)
1. **Бар-2 → A* зараз (V-A повністю).** Планка §10.1 = гарантовано низький rate перетинів на ДОВІЛЬНИХ
   open-canvas даних (вільна перестановка посад). Порт occ-pathfinding + rip-up + сітка коридорів/доріжок
   у Rust (~470-530 рядків ПОВЕРХ спільної геометрії, не з нуля). Приймаються: бенчмарк перф §8.4
   ОБОВ'ЯЗКОВИЙ (найгірша схема §10.1 п.7); важчий edit-mode-інкремент; виносимо ~25 detour-специфічних
   тестів (спільна геометрія/clearance/CardIndex лишається).
2. **Порт детектора `stats()` §10 у Rust/тести ЗАРАЗ** — acceptance-гейт (0 перетинів/накладань/через
   картки/8px/чужі деп). Розблоковує візуальний гейт R3.
3. **Мандат O-33/O-48 лишається в силі для МАРШРУТІВ** (не лише якорів). V-B мертвий як рантайм; ELK/stats
   лишається ЛИШЕ офлайн-тестовим оракулом; routing повністю в Rust = одна правда.

### Наслідок для плану
Це НЕ «латка», а суттєвий зріз (A*-орто-роутер із §10-гарантіями в Rust core) — кандидат на spec-flow/власну
задачу (як і флагував `_r7-link-rules-spec-to-rust-dg30.md`). card_pad-гейт лишається першим об'єктивним
фіксом усередині цього зрізу. Код — лише після «го» на scope + R6 (критик перед зрізом → red-first →
незалежний ревʼю).
