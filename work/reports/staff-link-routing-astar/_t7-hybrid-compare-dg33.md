### Перф-арифметика (ключове для осі 2)
- Детектор `route_stats_detailed` (staff_router.rs:170-243): line-vs-line O(E²·seg²) + line-vs-card O(E·cards) + line-vs-frame O(E·frames). Для 500 ребер E²=250k × seg²≈9-16 ≈ 2-4М порівнянь-сегментів/прохід.
- **Цей детектор УЖЕ в пайплайні** route_scene (:967), ганяється щопрохід rip-up (1 initial + ≤4), і вже рахує `bad` ВКЛЮЧНО з int — а потім викидає int через `.filter(!is_int)` (:968).
- Отже **O(E²)-детектор — спільна БАЗА обох варіантів**, не дельта вар.1. Він платиться вже зараз через cross/ext rip-up.

## РІШЕННЯ (аналіз 6 осей)

**1. Коректність щільної рамки.**
- ВАР.1 (A*): повний обхід по сітці — гне в БУДЬ-ЯКОМУ напрямі, зокрема вертикально навколо картки, що перекриває порт-колонку. Best-effort + rip-up; гарантії §10=0 на довільних даних НЕ дає (Q1: marked-залишок), але покриває максимум маршрутовних.
- ВАР.2 (lane-scan): corridorY зсуває ЛИШЕ горизонтальну шину; вертикальні ноги лишаються на ax/bx. side_detour бере X-доріжки ЛИШЕ з РАМОК (staff_routes.rs:464), НЕ з карток. → якщо ОКРЕМА КАРТКА перекриває порт-колонку (дитина глибше, перешкода на вертикалі) — ні lane-scan, ні side_detour не рятують → ЗАЛИШОК. Це вже зафіксовано тестом `avoidance_leaves_unresolvable_block_as_remnant` (staff_routes.rs:950). **Вар.1 строго домінує тут.**

**2. Перформанс (AC9 ≤50мс/500).**
- Спільна база обох: детектор O(E²·seg²) щопрохід (уже платиться).
- ВАР.1 дельта: лише ДОДАТКОВІ A*-reroute для БРУДНИХ int (release→astar→occupy). У щільному дереві брудних int може бути багато → багато A* (кожен — пошук по розрідженій сітці O(nodes·log) з ITER_CAP 250k). Але на канон+tidy-layout брудних int ≈ 0 → дельта ≈ 0.
- ВАР.2 дельта: lane-scan per int-edge O(lanes·cards), lanes=2·obstacles, БЕЗ A*, БЕЗ додаткових детектор-проходів. Дешевше за A* на ребро.
- **Теза власника «елбоу+hybrid повільно» — частково невірна:** сам lane-scan (вар.2) ДЕШЕВШИЙ за A*-reroute на ребро. АЛЕ: домінанта вартості — не int-механізм, а O(E²) детектор + cross/ext A*, які однакові в обох. На tidy-layout вар.1 майже не додає (брудних int мало). На справді щільному — вар.1 дорожчий per-dirty-edge, зате вар.2 там лишає залишки (вісь 1). Жоден не «вбиває» 500-посад сам по собі; домінанта спільна.

**3. Складність / reuse.**
- ВАР.1: прибрати `!is_int`-фільтр на staff_router.rs:968 — reroute-гілка (:975-984) уже вміє будь-яке ребро через astar_route(e.start,e.target); int-ребра вже мають EdgeSpec і occupied на фазі1. Реально мале (~1 рядок фільтра + зняття FIXED-семантики + тест). Reuse наявного A*.
- ВАР.2: detour-логіка приватна в staff_routes.rs (інший модуль, ніж route_scene у staff_router.rs). Щоб вставити в A*-пайплайн — витягти `detour_edge`+`route_clear_of`+lane-gen через межу модуля АБО дублювати. І це **прямо суперечить T12**, який цей detour ВИДАЛЯЄ. Вар.2 воскрешає код, призначений на зняття, і в неправильному модулі. **Вар.1 набагато простіший і не конфліктує з планом.**

**4. Детермінізм (AC8) / контракт.**
- Обидва детерміновані: вар.1 — seq-tiebreak + фіксований routing_order + фіксовані 4 проходи (AC8 тримався в T4-T6); вар.2 — сортування доріжок детерміноване (staff_routes.rs:446-451).
- Форма `StaffEdgeRoute.points` НЕ змінюється в жодному (список орто-точок). Контракт цілий.

**5. Паритет мокапу / §6.**
- Мокап НЕ гне int узагалі (прямий елбоу, ніколи не rip-up-иться). ОБИДВА варіанти — дивергенція. Але вар.1 ближчий ДУХУ §10 (detector-driven, той самий rip-up-механізм, що мокап застосовує до cross/ext — просто розширений на int). Вар.2 винаходить окремий механізм поза мокапом.
- §6-натяк СИЛЬНИЙ: і спека (spec.md:66-68), і мокап кладуть щільність на LAYOUT, не на роутер. Мокап тримає int чистими саме розставленням. → справжній «гібрид» у референсі = layout дає піддереву місце, а не роутер гне int.

**6. Чи потрібен гібрид ЗАРАЗ (YAGNI).**
- Канон (9 схем): лише S3 має 1 int-ребро → щільна-рамка-колізія НЕ збуджується. AC10=0/0/0/0/0 вже досягнуто БЕЗ гібриду (tasks.md:56 «AC10 зелений БЕЗ rip_up»).
- Tidy-layout Бар-1 (T126): розставляє сиблінгів з зазором → int-елбоу чисті by construction (як мокап).
- Збуджується лише на вільних позиціях (Бар-2, ВІДКЛАДЕНО) / реально щільних продакшн-департаментах. І там прийнятий контракт (Q1) = best-effort + marked, НЕ нуль.
- **Висновок осі: гібрид ЗАРАЗ — не вимога приймання. Це страховка під Бар-2 / реальні дані.**
