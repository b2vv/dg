# spec.md — T128 staff link-routing: коректний орто-роутер ліній ШПС із §10-гарантіями

**Статус:** 🟡 specify (крок 2 spec-flow) · **Поріг:** повний цикл ON (нова підсистема `packages/core` +
межа WASM↔TS + Rust&TS) · **Під парасолькою:** T126 · **Рішення підходу:** власник dg31 — V-A (повний
A*-роутер у Rust), синтез `work/reports/staff-rust-geometry/_r7-routing-debate-SYNTHESIS-dg31.md`.

> Цей документ — рівень НАМІРУ (ЩО/ЧОМУ). Як саме (A*, сітка, модулі Rust) — у `plan.md`. Канон
> поведінки — зовнішня спека `Вимоги - Лінії зв'язку ШПС.md` §3–§10 + мокап `shps-links.js` + 3 скріни.

## Проблема
Лінії підпорядкування між картками посад на схемі ШПС зараз рахує Rust-роутер `staff_routes.rs`
(per-edge, stateless) — він НЕ моделює взаємодію ліній між собою й має card_pad-гейт-баг (обхід карток
лише при content_padding≥8, проти спеки §5.1.3). Наслідок: лінії ріжуть картки й перетинаються між
собою на нетривіальних схемах. Головна вимога продукту (§3, рядок 3 канону): **лінії не перетинаються
між собою, не накладаються на картки й не проходять під ними.** Поточний рушій цього не гарантує.

**Чому зараз / чому в Rust:** мандат власника O-9/O-33/O-48 — точки й маршрути лінків рахує Rust, одна
система координат, одна правда. Байт-паритет до TS НЕ ціль (TS сам мав баги центрування, ADR-0002; §5
брифінгу — SDK ще без споживача). Еталон коректності — мокап A* + скріни + §10, не TS.

## Користувацькі сценарії
1. Користувач відкриває ШПС-схему організації → бачить орто-дерево підпорядкувань: внутрішні зв'язки
   всередині рамок департаментів, міждеп-лінії коридорами полотна (вихід знизу A → вхід зверху B один
   раз → шина всередині B), штрихову лінію від керівної організації.
2. Міждеп-лінія до **голови** департаменту B входить у верхній центр рамки B (порт `deptTop`); до
   не-голови — у верхній центр картки (`top`).
3. Користувач згортає гілку керівника → підлеглі та їхні лінії зникають, місце стискається, лінії
   перебудовуються без артефактів.
4. Користувач наводить/вибирає картку → її лінії до керівника й прямих підлеглих підсвічуються,
   решта приглушується.
5. Користувач ресайзить вікно / вмикає дати / міняє розмір аватарки → лінії перераховуються (≤1/кадр).
6. **(Бар-2 — ВІДКЛАДЕНО з edit-mode, рішення власника GATE 2 dg31)** Користувач вільно переставляє посади
   (довільні позиції) → той самий A*-роутер дає коректні лінії й на довільних конфігураціях. **У ЦЬОМУ
   зрізі не реалізується й не тестується:** контракт `StaffPositionInput` не несе x/y (позиції рахує Rust),
   вхід довільних позицій приходить із edit-mode (Q5). Зріз будує A* як ФУНДАМЕНТ, валідований на Бар-1
   (сценарії 1–5 + межі); A* position-agnostic за побудовою (маршрутизує по сітці з наданих прямокутників),
   тож інвестиція повністю переноситься на Бар-2, коли edit-mode подаватиме позиції. Контракт-шов під
   майбутній x/y закладається адитивно (optional-поле), але НЕ будується тут.

## Acceptance criteria (канон §10 + §8.4; вимірювані)
Детектор `stats()` §10 (порт із `shps-links.js:162-172`) рахує кожен критерій на кожній тестовій схемі:
- **AC1 §10.4.1** — жодна лінія не перетинає іншу (перетин = горизонталь однієї перетинає вертикаль
  іншої в точці, що не є спільною точкою їхнього дерева; стовбур+шина одного керівника — не перетин).
- **AC2 §10.4.2** — жодна лінія не ближче ніж 8px до будь-якої картки.
- **AC3 §10.4.3** — жодна лінія не проходить під карткою чи заголовком департаменту (заголовок +4px).
- **AC4 §10.1** — внутрішні зв'язки = орто-дерево, не виходять за рамку департаменту.
- **AC5 §10.2** — міждеп-лінія A→B виходить з A знизу, входить у B зверху, не крізь третій департамент
  (перетин рамки рівно двічі: один вихід A, один вхід B).
- **AC6 §10.3** — посади поза департаментами з'єднані за тими самими правилами.
- **AC7 §10.5** — згортання/розгортання, ресайз, перемикання дат/аватарки перебудовують лінії без
  артефактів.
- **AC8 §10.6** — детермінізм: однакові дані → однакова схема.
- **AC9 §8.4** — повний перерахунок для ≤500 посад ≤50мс; ресайз throttle ≤1/кадр (rAF).
- **AC10** — усі 9 тестових схем §10.1 проходять AC1–AC3 (детектор показує 0/0/0/0/0).
- **AC11** — card_pad-гейт прибрано: обхід карток безумовний (§5.1.3), перший фікс усередині зрізу.

Форма ліній (§5.1): лише ортогональні сегменти; min поворотів (внутр ≤2, міждеп ≤4). Контракт
`StaffEdgeRoute.points` НЕ змінюється (рішення власника) — вихід лишається списком орто-точок.

## Out of scope
- **Бар-2 вільні позиції в рантаймі — ВІДКЛАДЕНО з edit-mode (Q5).** Зріз = A*-фундамент на Бар-1;
  контракт форму не змінює; шов під x/y закладається адитивно, не будується. (Рішення GATE 2 dg31.)
- **Бус для НЕ-голови §3.2** (один керівник із ≥2 підлеглими в одному чужому депі → один вхід + шина) —
  **не збуджується 9 канон-схемами** (§10.1 п.4 = ДВА РІЗНИХ керівники, це доріжки §5.4, не бус; збіг зі
  `shps-links-analysis §4a`). Поза скоупом; кандидат у майбутнє, коли дані це збудять.
- **§6 повна перебудова layout** (переставляння департаментів / опускання рівня для зняття перетину) —
  мокап сам цього не робить, обходиться rip-up при фіксованих позиціях; наявний Rust виніс relayout у
  борг. A*-роутер працює на ДАНИХ позиціях; окрема майбутня задача, якщо rip-up недостатній.
- **staff-matrix** (orgBlockLayout matrix/hybrid) — відкладено (dg30, staff=tree now).
- **§11.1 подвійне підпорядкування** (у даних не підтримується, §2).
- **§11.3 висхідні (зворотні) зв'язки.**
- **§11.4 індикатор цілі за межами видимості.**
- **Байт-паритет до TS-роутера** — свідомо НЕ ціль.
- **ELK/JS-роутер у рантаймі** — знято (V-B мертвий; ELK/stats лише офлайн-тестовий оракул).

## Відкриті питання → ✅ ЗАКРИТО на GATE 1 (власник підтвердив усе, dg31)
1. **§11.5 / Бар-2 — межа «довільних позицій»:** → **(а) best-effort + видимий `stats()`-fail.** Якщо
   дані роблять схему немаршрутовною (нема коридору), роутер веде найкращу можливу лінію, детектор рахує
   порушення як `fail` (видимо через панель/`/debug`), але це НЕ падіння. §6-relayout лишається out of
   scope; «розширити коридор» (§6.5.2) — кандидат на пізніше, якщо вимір покаже часту причину fail. На
   9 канон-схемах §10.1 (маршрутовні за побудовою) детектор МУСИТЬ давати 0/0/0/0/0 (AC10).
2. **Планка перф-бенчмарку AC9:** → найгірша комбінація §10.1 п.7 (широкий деп 10+) × п.4 (спільний
   коридор доріжками), масштабована до ~500 посад. Окремий таск-гейт; >50мс → звузити A* до cross/ext,
   int-ребра прямим деревом, повторний вимір.
3. **§11.2 стиль міждеп-ліній:** → дефолт **як внутрішні** (суцільна, `--line`, §7). Штрих лише для §3.4
   (керівна організація→організація). Окремий стиль — косметичний перемикач пізніше.
4. **Детектор `stats()`:** → **тестовий гейт зараз (обов'язковий `cargo test`, AC1–AC3 × 9 схем) +
   рантайм за прапором `/debug`** (той самий код, у гарячому шляху вимкнено). Корисно для візуального гейта R3.
5. **Edit-mode інкрементальність (§8.3):** → **повний перерахунок зараз** (≤50мс = бюджет на повний),
   інкремент — окрема майбутня задача (власник dg31: «зараз не пріоритет»). Контракт проєктуємо так, щоб
   інкремент можна було додати, але не будувати тут.

**GATE 1 (спільне розуміння) — ПРОЙДЕНО** (grilling-раунд 1, власник підтвердив усі рекомендації, dg31).
