## Крок 1 — у якій системі координат `listTestAnchors`

**Відповідь: у сценових, і це видно з імені поля.**

```ts
export interface TestAnchorCandidate {
  testId: string;
  kind: NodeKind;
  ref: NodeRef;
  world: { x: number; y: number; width: number; height: number };
}
```
`packages/sdk/src/interaction/nodeTestId.ts:84-89`

Поле називається `world`, і воно справді світове: `listTestAnchors` бере бокси прямо зі сцени
(`OrgHierarchyDiagram.ts:1409-1428` → `DiagramRenderer.listNodeBoxes()` →
`scene.listBoxes()`), без жодного перетворення.

Хосту потрібні **viewport-пікселі**, щоб `page.mouse.click` влучив у точку на канві
(`T115` §«Що сказав хост»). Тобто **невідповідність підтверджена**, і підозра сесії 2026-09-06
була правильною.

### Але перетворення в SDK **вже є** і воно публічне

```ts
export function worldBoxToScreen(box: WorldBox, viewport: ViewportTransform): ScreenRect {
  return {
    left: box.x * viewport.scale + viewport.x,
    top: box.y * viewport.scale + viewport.y,
    width: box.width * viewport.scale,
    height: box.height * viewport.scale,
  };
}
```
`packages/sdk/src/render/promoteMath.ts:48-55`, експортується з кореня (`index.ts:118`).

Разом із `getViewport()` і `getCanvas()` цього досить, щоб хост дістав viewport-піксель сам:
`clientX = canvasRect.left + rect.left + rect.width / 2`.

### 🔑 І головне: копіювати міст хоста взагалі не треба

Хост будує `window.__orgHierarchy` тому, що **в нього немає DOM на вузол**. У SDK на це вже є
відповідь, і вона краща за координати:

```ts
import { createTestAnchorOverlay } from '@org-hierarchy/sdk/react';
const anchors = createTestAnchorOverlay({ diagram, mount: el, interactive: true });
```

`packages/sdk/src/react/createTestAnchorOverlay.ts` вішає на кожен видимий вузол невидиму
`<button data-testid="node-<testId>">`, позиціоновану вже **в CSS-пікселях** відносно `mount`
(той самий `worldBoxToScreen`, рядок 58), і пересинхронізовує її на кожен promote-tick.

Наслідок для міграції: сценарії хоста переходять із `page.mouse.click(x, y)` на
`page.getByTestId('node-…').click()` — тобто **не відтворюють міст, а позбуваються його**.
Playwright сам скролить, чекає на стабільність і б'є в центр елемента; арифметика координат
зникає з тестів разом із класом помилок «влучив у сусідню картку».

⚠️ Оверлей уже згаданий у `docs/USAGE.md` §13 — **одним рядком у прикладі**, без жодного
зв'язку з e2e-міграцією. Тобто відповідь на найдорожчу статтю міграції хоста в нас формально
задокументована так, що знайти її можна лише знаючи, що шукаєш.

## Крок 2 — чи є еквівалент `expanderCenter`

**Відповідь: ні, і хост не може його обчислити.**

Хосту принципова окрема точка експандера: «Expander != node-click», інакше клік фантомно
відкриває сайдбар. У нас експандер — це Pixi-контейнер усередині картки, і його зсув
**залежить від варіанта chrome**. Варіантів три, всі в `packages/sdk/src/render/orgNodeChrome.ts`:

| Варіант | Де кнопка | Рядки |
|---|---|---|
| `gojsTree` | центр `(cardWidth − 13, cardHeight − 13)`, діаметр 26 — **низ-право** | `:42-48` |
| дерево, звичайне | `x = cardWidth − 26`, `y = 4` — **верх-право** | `:95-106` |
| штат (chevron ▲/▼) | той самий верхньо-правий слот | `:107-117` |

Перемикає їх опція `gojsTree` (`:84`), тобто **та сама картка** має експандер у двох різних
кутах залежно від конфігурації сцени. Хост, маючи лише бокс вузла, вивести цю точку не може:
потрібне знання, яке живе в рендері.

Ще одна деталь на користь «не координатами»: кнопки вже мають імена —
`btn.label = 'org-expand'`, `menuButton.label = 'org-menu'` (`:72`, `:101`, `:121`). Але це **Pixi**-мітки,
для DOM-тестів недосяжні.

**Отже це не документування, а нова поверхня.** Мінімальна чесна форма — віддавати бокс
експандера поруч із боксом вузла в тому ж `listTestAnchors` (або окремим методом), у тих самих
`world`-координатах, і дати оверлею вішати на нього другий якір
`data-testid="node-<testId>-expander"`. Це **ламальна зміна типу** `TestAnchorCandidate`, якщо
поле обов'язкове, і не ламальна, якщо необов'язкове.
