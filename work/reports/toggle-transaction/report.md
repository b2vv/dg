## 1. Що зроблено

`toggleStaffOrgExpand` мутував `staffExpandedOrgIds` і кликав `render()`. Між цими двома
рядками не було нічого: ні `try`, ні відкоту. Рендер, що впав, лишав сет із одним станом, а
екран — з іншим.

Три зміни, усі в `packages/sdk/src/OrgHierarchyDiagram.ts`:

| Що | Де |
|---|---|
| `lastDrawnStaffOrgIds` — знімок сету, зроблений у мить, коли кадр іде в рендерер | поле поруч із `lastDrawnData`; пишеться в `renderNow`, фіксується в `reportIfRenderFails` |
| відкат сету в `catch` спільного `drawOrRestore` | `drawOrRestore` |
| `toggleStaffOrgExpand` іде через `drawOrRestore(this.data)`, а не через `render()` | `toggleStaffOrgExpand` |

Плюс тест: `packages/sdk/src/render/staffOrgExpand.interactions.test.ts`, три випадки.

## 2. Протестовані сценарії

Приймальні критерії задачі — розділ «Готово, коли» T109; усі три позначені там.

| Сценарій | Як перевірено | Результат |
|---|---|---|
| Розгортання, чий кадр відмовив, не стирає **чужу** намальовану картку | юніт: `c1` розгорнуто по-справжньому, далі рендер ламається на `c2` | до фіксу `['c2']`, після — `['c1']` |
| Згортання, чий кадр відмовив, лишає картку розгорнутою | юніт: рендер ламається на згортанні `c1` | до фіксу `[]`, після — `['c1']` |
| Робочий шлях і стеля в одну картку не змінились | юніт: розгорнути → згорнути → розгорнути другу | зелений **до і після** — саме тому він і потрібен |
| Нічого не зламалось | `npx rstest run --root packages/sdk` | **974 / 0** (база 971 + три нові) |
| — | `npx rstest run --root packages/demo` | **104 / 0** |
| — | `npm run typecheck`, `npm run lint`, `npm run check:docs` | зелені |
| — | `npm run test:e2e` | **78 / 0** (56 с) |

🔴 **Тут стояла неправда, і вона протрималась три коміти.** Перша редакція цього рядка писала
«72 / 0» і будувала на цьому висновок, що локальний e2e вміє **тихо недорахувати** тести й
лишитись зеленим. Не вміє. Той прогін дав **шість падінь**, а обидва сигнали про них знищила
моя ж команда: `npm run test:e2e 2>&1 | tail -6`.

- `| tail -6` відрізав заголовок `6 failed` і три з шести імен; три, що лишились, я прочитав як
  «повільні тести», бо Playwright друкує імена невдах **над** рядком `72 passed`, з відступом;
- пайплайн підмінив код виходу: статус пайплайна — це статус **`tail`**. Перевірено:
  `false | tail -1; echo $?` → **0**.

72 + 6 = 78. Нічого не зникало. Розбір і 15 контрольних прогонів —
[`work/reports/e2e-silent-under-run/report.md`](../e2e-silent-under-run/report.md).

⚠️ **Що з тих прогонів лишається твердим:** 3 падіння з 15, три **різні** тести, усі під
навантаженням — `staff-1m` «panning past the edge» (двічі), `flat-orgs` T113 (раз). Тобто флак

## 3. Неочевидне

**Похідність тут неможлива, а не незручна.** Задача формулювала вибір як «знімок або зробити
сет похідним», і другий варіант виглядав чистішим — механізм уже є, `drawOrRestore` перевисіває
`staffExpandedPositionIds` із `position.expanded`. Але цей шлях **не чіпає `this.data` взагалі**:
перевисівання з незмінених даних відновило б рівно нічого. Щоб було з чого сіяти, розгорнутість
довелося б записати в `DiagramOrganization` — публічний тип, який хост дає й отримує назад, і
який **уже несе `collapsed`** з іншим значенням (деревна видимість, `media/diagramMedia.ts:34`).
Тобто ціна похідності — новий публічний контракт плюс два схожі поля про «розгорнутість» на
одному типі.

**Знімок «до виклику» був би другою помилкою.** Перший начерк робив `new Set(...)` перед
мутацією. Коментар на `lastDrawnData` (`:244-251`) уже описує, чому це хибно для даних: два
мутатори в польоті знімають стани, що вже містять правки один одного, і відкат «мого» в порядку
`catch` лишає ранішу правку застосованою й ненамальованою. Для сету діє те саме, тож знімок
робиться там само, де й для даних — у `renderNow`, поруч із `const drawing = this.data`.

**Відкат сету свідомо не гейтується на `this.data === next`.** Гейт даних означає «зверху
написав інший мутатор, його кадр і буде на екрані». Для view-стану це нічого не каже: мутатор
даних сету не торкався, а ціль відкату — намальований сет у будь-якому разі. Єдина умова —
що намальований кадр узагалі був.

**Дві гілки ламаються по-різному, і гірша — не та, що очевидна.** «Згорнути» втрачає один id.
«Розгорнути» робить `clear()` перед `add()` — тобто відмовлений кадр стирає id, який поставило
**попереднє, намальоване** розгортання. Тест на одну гілку пропустив би саме її; у T104 така
економія вже одного разу коштувала пропущеного дефекту (звіт T104 §6 п.3).

**`ViewStateStore.toggleStaffOrgExpanded` і `setStaffOrgExpanded` не має жодного викликача**
у продакшн-коді — лише тест `ViewStateStore.test.ts:15-17`. `OrgHierarchyDiagram` мутує сет
напряму, бо стеля «одна картка» вимагає `clear()`, якого в методі стора немає. Не чіпав: видалення
двох методів — окрема зміна з окремим питанням «а хто мав би бути викликачем», і вона не належить
до відкату.

## 4. Скріни

Немає, і це не пропуск: зміна не має видимого стану. Її предмет — розходження між сетом і
екраном **після відмовленого кадру**, а відмовлений кадр за визначенням нічого не малює.
Доказ — числа в §2, не картинка.

## 5. Проходка по user flow

Хост зі штатною сценою: користувач клікає chevron на картці підрозділу → `toggleStaffOrgExpand`.

- **Кадр намалювався.** Поведінка не змінилась ні на крок: сет той самий, повернене значення те
  саме, колбеків цей шлях не шле й раніше (тому T104 його й не зачепив).
- **Кадр не намалювався.** Раніше: екран показує стару картку, `getStaffExpandedOrgIds()` каже
  нову, і розійтись вони могли надовго — наступний рендер малює те, що в сеті, тобто **закріплює**
  неправду замість виправити її. Тепер: сет повертається до намальованого, помилка летить далі,
  як і раніше (`reportIfRenderFails` уже кличе `onRenderFailed`).
- **Два кліки поспіль, перший кадр відмовив.** Відкат ставить сет у **намальований**, а не в
  «той, що був до першого кліку», тож стан, якого на екрані не існувало, не відтворюється.

## 6. Ризики й обмеження

1. **`focusStaffOrg` лишається без відкоту — свідомо.** Він чистить той самий сет і **додатково**
   рухає `staffCurrentOrgId`. Закрити його тим самим механізмом не можна без відповіді на
   контрактне питання: `setStaffFocus()` — публічний метод, який міняє фокус **без** рендера,
   тобто намір хоста легально випереджає кадр, і відкат «до намальованого» мовчки його скасував би.
   Виніс у [T121](../../tasks/T121-staff-focus-outruns-the-frame.md).
2. **Гонка двох тоглів у польоті перевірена міркуванням, не тестом.** Аргумент — у §3; тесту на
   два одночасні тогли з різними наслідками кадру немає. Найдешевший спосіб його написати —
   `createRenderCoalesce` напряму, як це зробив T104 (`renderCoalesce.t104.test.ts`), а не через
   повну діаграму.
3. **`lastDrawnStaffOrgIds` — третє поле, що описує «останній кадр».** Разом із `lastDrawnData` і
   `lastRenderFailure` їх уже три, і жодне не зобов'язане іншим бути в тому самому кадрі. Поки
   всі три пишуться в одному `reportIfRenderFails`, вони узгоджені; четверте таке поле — привід
   зробити з них один об'єкт, а не додати ще одне.
4. ~~**Локальний e2e один раз тихо не виконав шість тестів**~~ — **знято 2026-09-10: цього не
   було.** Шість тестів упали, а сховала їх моя команда виміру (§2). Ризик лишається, але інший
   і вужчий: **тестову команду не можна проганяти через `| tail`, `| head` чи `| grep`** — зріз
   хвоста ковтає підсумковий блок, а пайплайн ковтає код виходу. Писати в файл і читати файл.
