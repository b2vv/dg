## 🔴 К3, блокуюче — `promoted.has(box.id)` розходиться з тим, як реєстр вирішує те саме

`OrgHierarchyDiagram.listTestAnchors` порівнює **точно**:

```ts
...(box.expander && !promoted.has(box.id) ? { expander: box.expander } : {}),
```

`SceneRegistry` для того самого питання має власний предикат (`:154-157`):

```ts
private isPromoted(key: string): boolean {
  if (this.promoted.has(key)) return true;
  return promoteIdMatches(this.promoted, key);   // голий ↔ типізований, в обидва боки
}
```

`promoteIdMatches` (`promoteMath.ts:27-45`) існує саме тому, що id приходять у двох формах.
А `setPromotedNodeIds` — **публічний метод** (`OrgHierarchyDiagram.ts:1572`), тобто голий id
приходить не гіпотетично, а найкоротшим шляхом хоста.

**Доведено прогоном** (тимчасовий тест, видалений після виміру):

```
promoteIdMatches(new Set(['root']), 'organization:root')  →  true      // в'юха схована
diagram.setPromotedNodeIds(['root'])
listTestAnchors().find(a => a.testId === 'root').expander →  {"x":206,"y":36,"width":22,"height":22}
```

Тобто **в'юха схована, а якір і далі показує на кнопку, якої на екрані немає** — рівно той
випадок, заради якого Д4 існує. Ваше власне побоювання було правильне; перевірка «обидва боки
говорять типізованим ключем» тримається лише для **внутрішнього** React-оверлея й не тримається
для публічного сеттера.

**Що зробити:** порівнювати тим самим предикатом —
`promoteIdMatches(promoted, box.id, box.kind)` (функція вже експортована), або віддати
`scene.isPromoted` назовні. І тест мусить класти **голий** id: із типізованим ключем цей дефект
невидимий за побудовою — саме тому ваш нинішній тест його не спіймав.

## 🔧 К2 — штатна пара полів обіцяє те, чого правило не передбачає

У штатній сцені картка отримує `hasChildren: (card.positionCount ?? 0) > 0`
(`DiagramRenderer.ts:890`), але `expander` там **не** передається — бокс штатного chevron'а
рахується (К1, `orgNodeChrome.ts:168`) і нікуди не їде.

Хост читає пару за правилом із §14: `hasChildren === true` + бокса немає ⇒ «кнопка є в моделі,
кадр її не показує» ⇒ **підведи камеру**. У штатній сцені це неправда двічі: chevron **на
екрані**, а камера ні до чого. Жодна з задокументованих причин відсутності (лист, далекий LOD,
`orgTreeChrome: false`, promote) сюди не підходить.

Тобто поле чесне **саме по собі** й хибне **в парі** — а хост читає пару, бо саме заради пари
все й будувалось.

**Що зробити** — ваше питання, і моя відповідь: **не заповнювати `hasChildren` у штатному
шляху**, поки обсяг циклу — лише дерево. Тоді штатний org-якір не має жодного з двох полів, і це
читається як «не покрито», а не як хибна діагностика. Альтернатива (віддавати й бокс) виходить за
обсяг, який хост підтвердив виміром.

## Ваші три питання — відповіді

**1. Штатний `hasChildren`.** Див. вище: прибрати. Не тому, що «не обіцяй зайвого», а тому, що
нинішня пара **активно** веде хоста в хибний висновок.

**2. `hasChildren` лише для org.** ✅ Перевірив: поле проставляють рівно два місця, обидва —
org-бокси (`DiagramRenderer.ts:890` штат, `:1068` дерево). Бокси персон і посад
(`personInteractions.ts:148` і сусіди) його не несуть, тож `box.hasChildren === undefined`
справді дає відсутнє поле для інших `kind`. Умова написана через `=== undefined`, а не через
істинність — і це правильно, бо `false` мусить доїхати.

**3. `expander` через спред.** ✅ Заперечень немає. Мотив реальний: `JSON.stringify` не бачить
відсутнього ключа, але бачить `undefined`-поле інакше, ніж його немає. Надмірним не вважаю.
