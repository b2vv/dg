## РІШЕННЯ: Варіант 1 (коміт SDK + build dist + пінг Cass зараз; демо — окремим комітом)

Причини:
1. Коміт SDK самодостатній і зелений (#1–#3): відокремлення зміни бібліотеки від міграції
   її споживача — стандартна чиста практика; змішування ~260-рядкового перепису демо +
   churn тесту в API-коміт ПСУЄ рев'юбельність, а не покращує атомарність.
2. Контракт, проти якого лінкується Cass, доведено НЕЗАЛЕЖНО від демо (#5). Пінг зараз не
   відкриває Cass недоведену поверхню; розблокування реального хоста на dist — найдорожча
   річ у черзі, її не варто тримати за великий консумер-рефактор.
3. Демо-доказ НЕ втрачається — він стається наступним комітом ДО оголошення Б2 повністю
   закритим. Ізоляція дає зробити його test-first, акуратно, з власним рев'ю (пам'ять:
   «assert-true-without-feature» — поспішний green-перепис тесту = втрата інформації).
4. Реверсивність V1 вища: демо живе на власному шляху; якщо міграція щось виявить — SDK-коміт
   стоїть або дістає адитивний follow-up. V2 же ризикує роздутим, важко-рев'юбельним
   одно-комітом і дрейфом розкладу Cass.

ГОЛОВНИЙ РИЗИК V1 (назвати чесно): оголосити API «поставленим» і пінгувати Cass ДО того, як
реальний консумер його спожив — відкладає ЕРГОНОМІКА-доказ. Демо-реорд (geom лише ПІСЛЯ
рендеру, foundId поза SDK-типом) може виявити, що таймінг/ергономіка фасаду незручні для
реального споживача — і Cass вперлася б у те саме.
ЯК ЗНЯТИ: перед комітом+пінгом (не повна міграція!) зроби швидкий ергоном-смоук — підтверди
послідовність виклику (create → render → getStaffChromeGeometry) як обов'язкову для консумера
й прийнятність сплітів (foundId окремо). Інспектор уже зафіксував null-до-рендеру контракт
(`_inspector-i2-i3.md:16`), тож ризик уже низький; смоук закриває залишок. Пінг Cass супроводь
нотаткою «geom доступна лише post-render; foundId консумер тримає сам».

ЩО ЗМІНИЛО Б РЕКОМЕНДАЦІЮ НА V2:
- Якби `worldTransform`/рендер-контракт БЕ був неперевіреним інспектором, або якби non-scaling-stroke
  вимагав ЗМІНИ ФОРМИ `PromoteBackdropProps` (а не демо-DOM) — тоді демо-рендер є обов'язковою
  частиною доказу контракту → V2.
- Якби демо-міграція могла вимагати ЗЛАМНОЇ зміни публічного типу (не адитивної) → атомарність
  з Cass-пінгом стає критичною → V2.
- Якби норма репо явно вимагала референс-консумер-проходу в Definition of Done ДО «API поставлено»
  (не знайшов такої жорсткої норми; «доказ» тут покривається SDK-тестами + інспектором) → V2.
