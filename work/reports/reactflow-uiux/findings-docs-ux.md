## 1. Фактаж, з якого все випливає

**Шар нод рухається одним трансформом, поза React.** `packages/react/src/container/Viewport/index.tsx`
читає початковий transform у `useState` (щоб **не підписуватись**), далі через `store.subscribe`
пише прямо в DOM: `translate(${t[0]}px,${t[1]}px) scale(${t[2]})`. Коментар авторів: *transform
змінюється щокадру, тож пишемо в DOM напряму, щоб тримати React поза гарячим шляхом.*

**Позиція ноди — у світових координатах** всередині трансформованого контейнера
(`NodeWrapper`, `transform: translate(x,y)` у координатах графа). Наслідок: **під час пана й
зуму жодна нода не перераховується взагалі**.

**Дебаунсу під час руху камери немає.** `xypanzoom/eventhandler.ts:201` — `onTransformChange`
синхронно на кожен d3-івент. Єдиний таймер — `setTimeout(…, 150)` у pan-on-scroll, і він
**синтезує** відсутній у d3 івент «кінець», а не відкладає роботу.

**`onlyRenderVisibleElements` — лінійний скан без просторового індексу.**
`getNodesInside` (`system/src/utils/graph.ts:265`) — `for (const node of nodes.values())`, O(N)
по всіх нодах, усередині zustand-селектора, який переобчислюється на кожну зміну стора.
Тобто **O(N) скан щокадру пана**; від ре-рендера рятує лише `shallow` по масиву id.

**`will-change` у їхній кодовій базі немає взагалі** — композитний шар отримують самим `transform`.

## 2. Дві знахідки, які міняють наш план

### 2.1 🔴 Нода в «особливому» стані не має депромоутитись

`getNodesInside:299` — `if (isVisible || node.dragging)`. Ноду, яку тягнуть, лишають у DOM,
навіть коли вона виїхала за екран.

**У нас цього немає, і це клас реальних багів:** користувач поставив фокус в інпут усередині
картки, трохи посунув камеру — картка депромоутилась, фокус і незбережений ввід зникли.
Список винятків для нас: **фокус усередині картки · виділення · відкритий поповер/меню ·
активний ввід**. Такий вузол не депромоутиться на зупинці камери.

### 2.2 🔴 `pad` у нас має бути похідним від дебаунсу, а не константою

У них rect — рівно екран, `pad` нуль. Це працює **тільки тому**, що перерахунок синхронний
щокадру. У нас перерахунок відкладений на зупинку → між початком флінгу й стопом шар їде, і з
малим запасом буде видима **порожня смуга по ходу руху**.

Сьогодні `screenRectInView` має `pad = 32` (`promoteMath.ts`). Це число не виводилось із
швидкості камери — його треба або обґрунтувати, або порахувати від максимальної швидкості
флінгу за час дебаунсу.

### 2.3 Гістерезис на межі

`getNodesInside` — чистий предикат «перетинається / ні», без гістерезису. Їм це не шкодить, бо
перезапиту в них немає. У нас дрижання камери біля межі дасть промоут↔депромоут по колу.
Потрібні **два пороги**: розширювати при виході за `pad_in`, звужувати лише за `pad_out > pad_in`.

## 3. Розвилка, яку треба винести користувачу

**Світові координати картки замість екранних.** У React Flow картка позиціонована у світових
координатах під `translate+scale`, тому перерахунок позицій **не потрібен ніколи** — на зупинці
змінюється лише *членство множини*, не геометрія.

| | Екранні координати (наш поточний план) | Світові координати (як у React Flow) |
|---|---|---|
| Перерахунок позицій | на зупинці камери | **ніколи** |
| Розмір картки при зумі | сталий у пікселях | **масштабується разом зі сценою** |
| Збіг із канвасною карткою | розходиться на різних зумах | збігається — Pixi теж масштабує |

⚠️ Це справжня розвилка, не рекомендація. Ціна «сталого розміру картки» — перерахунок
геометрії; React Flow цієї ціни не платить, бо погодився на масштабування.

Аргумент **за** світові координати, якого в звіті агента немає, а в нас є: **картки на канвасі
теж масштабуються зумом**, бо їх малює Pixi. Тобто світові координати дають *геометричний*
збіг DOM-картки з канвасною безкоштовно, а екранні — гарантують розходження.

## 4. Чого React Flow не вирішує взагалі — наші сліпі зони

Кожен пункт агент підтверджував як «немає», а не «не знайшов»:

1. **Пошуку ноди немає** — лише програмні примітиви (`fitView({nodes})`, `setCenter`), UI на хості.
2. **Індикаторів «є щось за краєм» немає** — ані компонента, ані API.
3. **Хлібних крихт немає.**
4. **Підвантаження графа, більшого за завантажений, немає** — весь граф завжди в `nodeLookup`.
   Для `T88` брати нема чого: **вікна даних у них не існує**.
5. **Що показувати під час перебудови — не адресовано.** Механіка є (`visibility:hidden` до
   вимірювання, `useNodesInitialized`), UX-відповіді немає.
6. **Орієнтація після згортання/розгортання не вирішена** — Pro-приклад релейаутить дерево
   без анімації й без re-fit: камера лишається, а граф під нею переїхав.
7. **Error boundary на ноду немає** — org-wide пошук `componentDidCatch` дав нуль. Одна кинута
   нода валить усе дерево. (У нас це вже `T87.5`, і тепер воно має зовнішнє підтвердження.)
8. **Просторового індексу немає** — при 1M їхній підхід не масштабується в принципі.
9. **Читаних бенчмарків немає** — ані fps, ані «до N нод».

## 5. Межі, названі числом

- Їхній власний **Stress Test — 450 нод** (15×30), і він **не вмикає** `onlyRenderVisibleElements`.
  Тобто їхня демонстраційна стеля ≈ наша поточна сцена (639) — і в них вона без віртуалізації.
- **150 мс** — їхня константа «камера стала» для pan-on-scroll. Прецедент для стартового
  значення нашого дебаунсу.
- **Поріг зуму 1.5** у прикладі Contextual Zoom — того ж порядку, що наш 1.2. Але у них поріг
  перемикає *вміст* уже змонтованої DOM-ноди, у нас — *рендерер*.
- Мейнтейнер у discussion #3003: *React Flow не призначений для такого масштабу… canvas-підхід
  буде кращим*. Тобто **вони самі рекомендують наш підхід** для нашого масштабу.

## 7. Чого агент підтвердити не зміг

- **Числових бенчмарків React Flow не існує** публічно. Будь-яке «тримає N нод» було б здогадом.
- **Чому вони не ставлять `will-change`** — ніде не пояснено; гіпотеза лишається гіпотезою.
- Точний код прикладу Contextual Zoom у v12 — репо сайту закрите; поріг 1.5 узятий з
  опублікованого v9-коду тієї самої демки.
