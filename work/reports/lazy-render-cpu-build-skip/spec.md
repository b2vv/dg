добудовувала на pan. Це option (B) з research §5, але правильно наведений: **власник SDK, не host.**

## Рішення власника (2026-11-04)
- **Контракт API = «host дає повні дані, SDK вікнує сам».** Host віддає весь датасет один раз;
  SDK внутрішньо матеріалізує лише вьюпорт-вікно(+reserve) і добудовує на pan. SDK стає власником
  повної моделі + індексу. Публічний API змінюється (threshold спрацював однозначно).

## Рішення власника (2026-11-04, продовження)
- **Уніфікація = узагальнити staff-модель.** Камера-driven in-place вікнування (`viewportWindow.ts`:
  range+reserve+rebase+RebuildScheduler) — єдиний seam SDK; org стає його споживачем (замість reload).
- **spliceData = ТАК, відразу.** Причина: **режим редагування ШПС** потребує динамічного
  **add/edit/delete** сутностей у рантаймі — і це **вже в спеці** (власник). Отже spliceData — не
  оптимізація вікна, а **спільний delta-API** для (а) слайду вікна і (б) live-редагування ШПС.
  «Повний setData щоразу» неприйнятний для редагування (скидав би selection, перебудовував index).

## 🔺 РОЗШИРЕННЯ СКОУПУ — це підсистема, не одна фіча
spliceData для ШПС-edit стикається з **інкрементальною геометрією**: live add/edit/delete →
**Rust-геометрія мусить кешувати незмінні ноди** (пам'ять `staff-edit-mode-and-incremental-geometry`,
`staff-geometry-single-truth-and-caching`). Тобто фіча зачіпає **межу WASM↔TS** (раніше вважав —
ні; це стосувалося лише вибору вікна, а не delta-застосування геометрії). Мусить узгодитися з
**наявною спекою ШПС-edit** (add/edit/delete) — її треба знайти й прочитати перед планом.

## Крукс-рішення, що лишаються на Gate 1
- **Межа staff↔org:** два різні вікнувальники (T88 staff vs org getScaleWindowStart) — об'єднати
  в один seam чи два?
- **Rust vs TS:** вибір вікна й rebuild — де рахується; чи зачіпає межу WASM↔TS.
- **Сумісність:** host'и, що вже вікнують самі (як demo), не мають зламатись — міграційний шлях.

## Problem

`DiagramRenderer.render()` робить `scene.clear()` + **повну перебудову ВСІХ нод** + перерахунок
геометрії (Rust `computeStaffLiveGeometry`) — незалежно від того, що у вьюпорті (`:863/:920/:1009`).
На великій сцені це дорогий **initial render** (CPU + Rust), навіть якщо видно малу частину.

**Ключовий факт (research §5):** pan у межах LOD **НЕ** тригерить `render()` — сцена персистить
між рендерами, pan лише рухає трансформ. Тобто якщо на initial render побудувати лише visible
ноди, то при pan у небудовану зону там буде **порожнеча**, доки щось не викличе добудову.

## Фундаментальна розвилка (визначає, що це за фіча)

- **(A) Прогресивний/staggered initial build:** намалювати visible(+margin) ноди **першим кадром**
  (швидкий time-to-first-paint), а решту добудувати **фоново** (chunked / `requestIdleCallback`)
  одразу після. Pan-модель **не змінюється** (зрештою все побудовано → pan лишається rebuild-free).
  Виграш: швидший перший кадр. Ризик: низький. Пасує «забути велике дерево».
- **(B) Справжня віртуалізація:** будувати **лише** visible, добудова **інкрементально на pan**.
  Виграш: пам'ять/CPU на дуже великих сценах. Але це **змінює pan-модель** (pan стає build-on-demand)
  і фактично **= відкладена робота «велике дерево»** (spatial index тощо).

## Передумова initial-камери (критична)

Якщо host робить **fit-to-whole** на старті (demo так і робить — `fitView`), то на initial render
**нічого немає off-screen** → build-skip не дає нічого. Виграш 1-A матеріалізується лише коли
початковий кадр **зумнутий** на частину великого дерева. `create()` сам auto-fit НЕ робить
(research §5) — рішення за host.

## User scenarios (чернетка — залежить від розвилки)

1. Великий org, host відкриває зумнутим на корінь → перший кадр швидкий (видно корінь), решта
   дерева готова за мить (A) / добудовується на pan (B).
2. Host fit-to-whole → без змін (нема off-screen) — обидва варіанти.

## Out of scope

- Ось 1-B (GPU paint culling) — **вже зроблено** (merged).
- Spatial index (quadtree) для 100k+ — відкладено (це територія (B), якщо підемо туди).

## Open questions (Gate 1 — крукс)

- **OQ-A: яка це фіча — (A) прогресивний initial build чи (B) справжня віртуалізація?** Від цього
  залежить усе: pan-модель, складність, чи це «велике дерево».
- **OQ-B: яка передумова про initial-камеру?** Чи є реальний host-сценарій із зумнутим стартом на
  великій сцені — інакше виграш нульовий. (Треба факт від власника про те, як host відкриває діаграму.)
- **OQ-C: що саме дороге на initial render** — TS-побудова Pixi-об'єктів чи Rust-геометрія
  (`computeStaffLiveGeometry`)? Якщо Rust — skip TS-побудови не прибере Rust-кошт; треба виміряти.
