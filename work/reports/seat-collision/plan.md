# plan — як має працювати drop у зайняту клітину (T111)

**Спека:** [`spec.md`](./spec.md) · **Гілка:** `t111-seat-collision` · **База:** `main` @ `6de2ff3`
**Поріг:** вище — `movePersonToCell` у `docs/USAGE.md`.

---

## 1. Одна функція, два споживачі — це головне рішення плану

Сьогодні перетяг і коміт рахують різне: `ContourPainter.previewDrag` (`:373`) переставляє **лише**
перетягувану посаду, а `movePositionToCell` (`:50`) не перевіряє нічого. Якщо лікувати їх окремо,
користувач побачить одне, а отримає інше — найгірший можливий результат такої фічі.

Тому вводиться **одна чиста функція**, яку питають обидва:

Дім — **наявний** `interaction/positionMove.ts`, де вже живуть `snapToGrid`,
`movePositionToCell` і `shiftPositionBlock`. Новий файл під одну функцію був би шаром без другого
клієнта (reuse-first, знахідка критика).

```ts
// interaction/positionMove.ts — без стану, без I/O, без рендера
export type SeatDrop =
  | { kind: 'free' }
  | { kind: 'push'; occupantId: string; to: GridCell }
  | { kind: 'swap'; occupantId: string }
  | { kind: 'ask'; occupantId: string; pushTargets: GridCell[] };

export function resolveSeatDrop(input: {
  positions: DiagramPosition[];
  positionId: string;
  target: GridCell;
  from: GridCell | undefined;
}): SeatDrop;
```

Чотири входи — тому **options object**, а не позиційні параметри:
`work/CODING_STANDARDS.md` §1 «≤ 3 параметри; більше → options object з іменованими полями»
(те саме в `work/SPEC.md` §13.2). Заодно `from` не плутається з `target` на місці виклику.

Розбір `SeatDrop` у обох споживачах — `switch` по дискримінованому об'єднанню з
`default: assertNever(x)` (`CODING_STANDARDS.md` §1b), інакше новий варіант мовчки випаде з
однієї з двох гілок — рівно та розбіжність, яку §1 і закриває.

- **проєкція** малює результат ще під час перетягу;
- **коміт** застосовує той самий результат на drop.

Розбіжність між тим, що видно, і тим, що станеться, стає **структурно неможливою**, а не
«перевіреною тестом».

## 2. Правило вирішення

| Умова | Результат |
|---|---|
| у цільовій клітині нікого немає | `free` |
| напрямок визначений, клітина **за** сусідом вільна і в межах блоку | `push` — сусід їде туди |
| напрямок визначений, посунути **нікуди** (зайнято або за межами блоку) | `swap` — міняються місцями |
| напрямок **невизначений** (діагональ) | `ask` — питаємо на drop |

**Напрямок** = `sign(target − from)` по осях. Рівно одна ненульова вісь → напрямок визначений;
дві ненульові (діагональ) → `ask`; **нуль ненульових** (`target === from`) — це не «невизначений
напрямок», а відсутність руху: `free` no-op, див. граничні входи нижче.

🔴 **`from` береться з даних, а не з жесту — інакше §1 не виконується.** Через межу рендера
проходить **лише ціль**: `onPersonDragEnd(positionId, col, row)`
(`personInteractions.ts:40,281` → `OrgHierarchyDiagram.ts:788`). Напрямку там немає. Тому обидва
споживачі беруть `from` з **авторської `gridCell` посади в `this.data`**, а не зі стану перетягу —
тоді проєкція й коміт рахують те саме за побудовою. Якби превʼю рахувало від жесту, а коміт від
даних, «структурно неможлива» розбіжність стала б можливою на першому ж L-подібному перетягу.

| Граничний вхід | Результат |
|---|---|
| `from === undefined` (посада без `gridCell`) | напрямку немає → `ask`; посада входить у сітку вперше |
| `target === from` (відпустили там, де взяли) | **`free` як no-op** — не `ask`. Інакше «передумав» відкриває модалку |
| у цільовій клітині **двоє** (легасі-накладання) | `ask` — кого саме сунути, автомат вирішувати не має права |

**Ланцюга немає.** Якщо клітині за сусідом теж зайнято — це `swap`, а не «штовхаємо далі». Так
вирішено свідомо: ланцюг робить результат непередбачуваним, а користувач бачить лише перший крок.

**Зайнятість — у межах org-блоку.** `orgBlockLayout.ts:205-226` порівнює лише посади одного блоку
(`orgId` — параметр), тож і `resolveSeatDrop` дивиться лише на посади того самого блоку.

## 3. Проєкція під час перетягу

`previewDrag` перестає бути «перестав одну посаду» і стає «покажи вирішений стан»:

| `SeatDrop` | Що малює проєкція |
|---|---|
| `free` | як зараз — картка в новій клітині |
| `push` | картка в новій клітині **і сусід у своїй новій** |
| | ⚠️ **це шар спрайтів, не лише контур.** `previewDrag` сьогодні переставляє **тільки** модель контуру (`ContourPainter.ts:373` — `session.inputs` + `memberBoxesByDept`); картки живуть у `personInteractions`. Без правки шару спрайтів сусідова картка стоятиме на місці, поїде лише кільце — тобто С1 не виконано |
| `swap` | обидві картки на місцях одна одної |
| `ask` | **`swap`** як безпечний показ; вибір буде на drop |

⚠️ `ask` у проєкції показує `swap` навмисно: питати посеред перетягу неможливо, а показувати
перекриття — саме той дефект, який лікуємо. Обраний показ — той, який точно застосовний.

**Ціна названа:** для `ask` проєкція показує **не** остаточний результат. Користувач може
відпустити палець саме тому, що побачений `swap` його влаштовує, — і отримати модалку. Тому A9
звужено до `free`/`push`/`swap`, а поведінку `ask` описує `docs/USAGE.md` (К6).

`restoreAfterFailedDrag` мусить повернути **обидві** картки: сьогодні йому нема чого відновлювати,
крім однієї.

## 4. Коміт

`movePersonToCell` застосовує той самий `SeatDrop`:

- `free` → як сьогодні;
- `push` / `swap` → **дві** посади в **одному** `commitDataChange` (правило T104: або обидві на
  екрані, або жодної);
- `ask` → запит хосту; без відповіді або без обробника — **відмова**, дані не змінені.

🔴 **Після `await` на модалку рішення переобчислюється.** Поки вона відкрита, дані можуть
змінитись (інший `setData`, інший перетяг), і застосування `swap` по застарілому `occupantId`
відтворило б рівно той дефект, який лікуємо, — «правильним» шляхом. Тому: після відповіді
**повторний `resolveSeatDrop`**; якщо результат інший — відмова. Другий перетяг, поки модалка
відкрита, блокується.

⚠️ **Мовчазну відмову прибрати.** `OrgHierarchyDiagram.ts:1686-1692` гасить `InteractionError`
беззвучно («say nothing»). Після гвардії це перетворило б видимий баг на невидимий: користувач
тягне — і не бачить нічого. Відмова мусить бути помітною.

## 5. Публічний контракт

Два додатки, обидва — зміна `docs/USAGE.md`:

1. **`LayoutPatch`** несе того, кого зачепило. Прецедент поруч: `matrix-cell` несе `ejectedOrgId`
   (`callbacks.ts:9`). Тут — `displacedPositionId` на `position-move`.

   ✅ **Хост підтвердив, що це обов'язково** (п.14), і причина твердіша за очікувану: він зберігає
   **строго поштучно**, послідовним реплеєм по одній команді, без bulk-ендпоінта
   (`use-positions-edit-actions.ts:274-283`) — це записане рішення, ADR-0001 «sequential commit,
   **no batch**». Жодна його мутація не приймає двох id, тож «поміняти місцями» він не виразить
   однією операцією: потрібні **два адресовані патчі**.

   🔴 **Зустрічне обмеження, яке ми мало не порушили** (п.15): одиниця undo в хості — **подія**,
   не мутація. Якщо swap прилетить **двома незалежними патчами у двох тактах**, користувач
   дістане **два кроки undo на одну дію**, і половинний відкат лишить структуру в стані, якого
   він не просив. Отже swap віддається **однією подією** — один виклик колбека з двома
   адресатами, а не два виклики. Це в наших руках, не в хостових.

   ⚠️ **Атомарності на боці хоста немає й не буде**: два патчі підуть на сервер послідовно й
   можуть частково впасти (ADR-0001, чесний partial-persist). SDK не має її припускати.
2. **Запит вибору.** Патерн «SDK питає — хост малює» вже є (`onContextMenu` → `MenuItem[]`), але
   меню не має «скасувати» окремим результатом і не вміє чекати. Потрібен окремий колбек:
   `onSeatCollision?(request): Promise<SeatDropChoice | null>`; `null` = відмова.

   ✅ **Форма підтверджена хостом** (`../host-integration/questions.md` п.12): модальний сервіс у
   нього вже **promise-based** — `withModal` дає статичний `showModal(props): Promise<TResult>`,
   а дисміс типізований (`ModalDismiss.Closed/.Cancelled`). Реалізація ляже буквально як
   `async (collision) => SeatCollisionModal.showModal(collision)`, без адаптерів.

   🔴 **Колбек мусить бути НЕобов'язковим** (п.13): у хості діє no-batch і оптимістична чернетка
   з undo, тож нормальний спосіб «спитати» там — **зробити й дати відкотити**, а модалка на
   кожному перетягу в режимі масового редагування «швидко стане ненависною». Не передали →
   діє **дефолтна політика SDK**, названа в `docs/USAGE.md`; передали → вирішує хост.

   ⚠️ **Не нативний `confirm()`** — у хості записана гоча про конфлікт нативних діалогів із канвою.

⚠️ **Дві семантики drop'у в одному продукті — свідомо**; розбір і причина — у
[`spec.md` §Рішення](./spec.md#рішення-продукт-2026-09-06). Для плану з цього випливає рівно одне:
різницю з `matrix-cell` називає **К6** у `docs/USAGE.md`, і це перевіряється машинно (A8).

## 6. Порядок робіт

Кожен крок лишає продукт у робочому стані.

🔴 **Тести — перед кодом кроку, і кожен крок має обидві половини: success і failure**
(`work/TDD.md` §2). Крок без failure-тесту не вважається зробленим.

| # | Крок | Тест success (спершу червоний) | Тест failure | Закриває |
|---|---|---|---|---|
| **К1** | `resolveSeatDrop` у `positionMove.ts` | чотири напрямки → `push` у клітину, протилежну до сторони заходу | `from === undefined` → `ask`; `target === from` → `free` no-op; двоє в клітині → `ask`; за межами блоку → `swap` | A2, A4 |
| **К2** | гвардія в `movePositionToCell` **і** помітна відмова. ⚠️ **Тимчасово відмовляємо на будь-яку зайняту клітину** — `push`/`swap` ще не комітяться; це свідомий проміжний стан, записаний як такий | drop у вільну клітину працює як раніше | drop у зайняту → `InteractionError`, дані не змінені, відмова **видима** (не мовчазний catch) | A1, A7 — **недоробка `SPEC.md:202`** |
| **К3** | `push`/`swap` як одна транзакція + `displacedPositionId` | обидві посади в даних після одного `commitDataChange`; патч несе `displacedPositionId` | спостереження **всередині** вікна: жодного кадру з накладанням (правило T103); падіння посеред коміту не лишає одну посаду переміщеною | A3 |
| **К4** | проєкція малює вирішений стан (**контур і спрайти**); `restoreAfterFailedDrag` повертає обох | знімок посеред перетягу: два member-бокси в різних клітинах, спрайт сусіда зрушено | скасований перетяг → **обидві** картки на місці, `session.inputs` байт у байт як до перетягу | A9, A10 |
| **К5** | `onSeatCollision` + гілка `ask` | хост відповідає `swap` → застосовано; повторний `resolveSeatDrop` після `await` дає той самий результат | хост відповідає `null`, хоста немає, або дані змінились під час `await` → **відмова**, `onLayoutChange` не викликано | A5, A6 |
| **К6** | `docs/USAGE.md` + CHANGELOG + перевірка **окремим модулем** `scripts/*.mjs`, який `check-docs.mjs` **імпортує** (патерн `scripts/barrelSurface.mjs` — `check-docs.mjs:27`; сам `check-docs.mjs` імпортувати не можна: виконується на верхньому рівні й завершується `process.exit`) | `npm run check:docs` зелений на описаному API | `docs/USAGE.md` без `onSeatCollision`/`displacedPositionId` → `check:docs` **червоний**; тест на сам модуль у `npm run test:scripts` | A8 |

🔴 **Коміт (К3) стоїть перед проєкцією (К4) — навмисно, і саме тут план мало не порушив
власний §1.** Якби проєкція навчилась показувати `push`/`swap` раніше, ніж коміт навчився їх
застосовувати, у вікні між кроками превʼю обіцяло б одне, а drop відмовляв — рівно та розбіжність,
яку §1 називає найгіршим результатом. Тому спершу коміт уміє, потім проєкція показує. Номер кроку
= порядок виконання; читати їх як «спершу превʼю, потім коміт» — помилка, яка вже раз трапилась.

**К1–К3 закривають те, що видно на записі користувача.** К4 знімає артефакт у превʼю;
К5–К6 — надбудова.

## 7. Сайд-ефекти

1. **Демо-вкладка, де це відтворюється, стоїть у списку на видалення** (`Staff · Magnetic`, T112).
   `staffBrigade.ts` **не має жодного `gridCell`**, тож на `Staff · Brigade` колізію не показати.
   `scaleStaff.ts` (Staff · 1M) `gridCell` має — але це фікстура масштабу, не демонстрація.
   **Рішення потрібне до T112**, інакше фіча лишиться без сцени.
2. **Гвардія змінює поведінку публічного методу** — хост, який сьогодні кладе дві посади в одну
   клітину програмно, після цього отримає відмову. Це і є мета, але це ламальна зміна.
3. `previewDrag` тепер рухає більше однієї картки — вартість кадру росте; на 1M-фікстурі перевірити.

## 8. Rollback

`git revert` гілки цілком. Незворотного немає: ні міграцій, ні зовнішніх ефектів. Після К2
повернення старої поведінки означає повернення дефекту, тож відкат має сенс лише цілком.

2. ~~**Чи показувати в проєкції `ask` як `swap`**~~ — ✅ **вирішено:** показуємо `swap`, ціна
