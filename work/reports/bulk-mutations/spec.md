## Проблема

Гуртове меню існує (`interaction/contextMenu.ts:38`) і містить чотири дії:
`bulk-expand` · `bulk-collapse` · `bulk-copy-ids` · `bulk-clear`. **Жодна не змінює дані** —
розгорнути, згорнути, скопіювати id, очистити вибір.

Тобто мультивибір у SDK є, гуртове меню є, а **гуртових мутацій немає**. Це остання незакрита
умова рішення «власність виділення лишається в SDK»: без них хост, що тримає на множині
редагування й видалення, не може перейти.

### Дві межі, які задають форму, і обидві вже записані в репо

1. 🔴 **SDK нікуди не пише.** `docs/USAGE.md:434`: «`onLayoutChange` — **єдиний** канал
   персистентності. SDK нікуди не пише.» Отже «гуртове видалення» в SDK **не видаляє дані** — воно
   повідомляє намір і чекає, що зробить хост.
2. 🟡 **Прецедент «спитати хост і дочекатись» є — але він одноразовий, і черга це НОВИЙ протокол.**
   `onSeatCollision(request): Promise<SeatDropChoice | null>` (`callbacks.ts:147`) підтверджує
   форму «спитати й дочекатись». **І тільки її.** Перевірено після GATE 1:
   `SeatDropChoice = { kind: 'swap' } | { kind: 'push'; to: GridCell }` — члена «далі не треба»
   там **немає**, а `null` означає «скасувати **цей** дроп», бо іншого дропа в тому виклику й
   немає. Більше того, його власний докстрінг (`:144-145`) каже: *«One question at a time: a
   second colliding drop while this promise is pending is **refused** rather than queued.»*

   🔴 **Отже моя перша редакція спеки посилалась на прецедент, якого немає.** Черга питань —
   нова форма, не різновид наявної, і це треба було назвати, а не сховати за словом «прецедент».

⚠️ **І ще одна межа:** у `LayoutPatch` **шість** різновидів (`block-shift`, `matrix-cell`,
`matrix-reorder`, `position-expand`, `position-move`, `position-reparent`) і **жодного
видалення**. Тобто видалення — не новий випадок наявного патча, а нова сутність у контракті
персистентності.

## Що означає «по черзі» — і що воно вже вирішує

Власник продукту сказав **по черзі**, а не одним діалогом. Це відповідає на три речі:

| | «Одним діалогом» дало б | «По черзі» дає |
|---|---|---|
| скільком подіям | одна подія з переліком | **одна подія на елемент** |
| хто вирішує по кожному | хост вирішує за всю пачку наперед | хост вирішує **щоразу** |
| часткова відмова | уся пачка або нічого | природно **часткова**, і це очікувано |

🔑 **Тому SDK не обирає між «стати» і «продовжити» — він питає, і словник відповідей несе
обидва.** Але сам цей словник — **наш**, а не успадкований: у `SeatDropChoice` його немає (див.
межу 2 вище), тож його треба визначити явно, інакше A4 неможливо спростувати — не можна
перевірити значення, якого не існує.

## Словник відповідей — визначений тут, бо прецедент його не дає

```ts
/** Що хост зробив із одним елементом пачки. Дискримінований союз, як `SeatDropChoice`. */
export type BulkStepChoice =
  /** Хост змінив дані у себе. SDK перемалює те, що хост віддасть наступним `setData`. */
  | { kind: 'applied' }
  /** Свідоме рішення хоста пропустити саме цей елемент. Решту пачки це НЕ спиняє. */
  | { kind: 'skipped'; reason?: string }
  /** Далі не питати. SDK не звертається про k+1 і закриває пачку як перервану. */
  | { kind: 'abort' };
```

**`null` не приймається навмисно.** У `onSeatCollision` він означав «скасувати цей дроп», бо
іншого дропа не було; тут «пропустити цей елемент» уже має ім'я, і другий спосіб сказати те
саме створив би питання «чим вони різняться».

## Підсумок пачки — чотири категорії, не три

```ts
export interface BulkRunSummary {
  /** Id дії меню, яку викликали: `'bulk-delete'`, `'bulk-edit'`. */
  action: string;
  applied: readonly string[];
  /** Пропущено РІШЕННЯМ хоста. */
  skipped: readonly string[];
  /** Пропущено, бо обробник хоста КИНУВ. Несе й місце, і причину. */
  failed: readonly { id: string; error: unknown }[];
  /** Чи обхід перервано відповіддю `abort` — і на якому елементі. */
  abortedAt?: string;
}
```

🔴 **Чому `failed` окремо від `skipped`, а не разом (знахідка GATE 1).** Перша редакція давала
три категорії — зроблено / пропущено / перервано — і тим робила **помилку в обробнику хоста
невідрізненною від його свідомого рішення**. Хост, що бачить «пропущено: 4», не міг би сказати,
чи це його вибір, чи його баг. Це та сама форма, що `Tier1 skipped` без переліку id: агрегат
ховає причину, і падіння стає мовчазним не тому, що його немає, а тому, що воно **невідрізненне
від норми**.

## Користувацькі сценарії

Кінцевий користувач — людина в застосунку хоста; **споживач контракту** — хост-розробник.

1. **Видалити пачку.** Людина виділяє shift-кліком п'ять посад, викликає меню, обирає «Видалити
   5». SDK питає хоста **про кожну по черзі**; хост показує підтвердження, видаляє у себе й
   відповідає. Людина бачить, як пачка зникає **поелементно**, а не одним стрибком.
2. **Часткова відмова видна, а не схована.** Третя посада не видаляється (немає прав, є
   підлеглі). Хост відповідає «пропустити». Решта дві видаляються, і в кінці людина знає **що
   саме** не вийшло — не «сталася помилка».
3. **Перервати пачку.** На третій людина розуміє, що обрала не те. Хост відповідає «далі не
   треба», і SDK **не питає** про четверту й п'яту.
4. **Редагувати пачку.** Те саме, але хост відкриває власний редактор на кожному елементі й
   повертає, чи щось змінилось.

## Acceptance criteria

| # | Критерій | Чим спростовується |
|---|---|---|
| A1 | Гуртова дія викликає колбек **рівно один раз на елемент** виділення | двома елементами колбек викликано один раз або тричі |
| A2 | Порядок обходу **названий у контракті й стабільний** | два прогони на тому самому виділенні дали різний порядок |
| A3 | Відповідь «пропустити» на елементі k **не спиняє** решту | після пропуску наступних елементів не питали |
| A4 | Відповідь «далі не треба» на елементі k спиняє обхід: про k+1 **не питають** | колбек викликано для k+1 |
| A5a | Виняток із колбека хоста **не спиняє** обхід: про k+1 питають | після винятку наступних елементів не питали |
| A5b | Виняток **не з'їдає** елемент безслідно: k потрапляє у `failed` з причиною | k зник із підсумку, або ліг у `skipped` разом із рішеннями хоста |
| A6 | Підсумок розрізняє **чотири** стани: `applied`, `skipped` (рішенням), `failed` (винятком, із місцем), `abortedAt` | помилка обробника невідрізненна від свідомого пропуску |
| A7 | SDK **нічого не видаляє й не редагує сам** — дані змінює хост, а SDK лише перемальовує з того, що хост віддав | після гуртової дії дані в SDK змінились без `setData`/`appendData` від хоста |
| A8 | Пункти меню з'являються лише коли виділення **однорідне** за `kind` і непорожнє, і напис несе число | меню показує «Видалити 0», або показує дію на **змішаному** наборі `position` + `organization`, який у штатній сцені досяжний shift-кліком |
| **A12** | Shift-клік по картці org у **штатній** сцені **не** додає її у виділення; у **деревній** сцені додає, як раніше | після правки набір штатної сцени містить `organization`, або деревна сцена перестала виділяти org |
| **A13** | Одинарний тап по картці org у штатній сцені **і далі** розгортає на місці або занурюється | правка виділення зламала `onSingleTap` |
| A11 | SDK **не малює** жодного підтвердження: на «Видалити 5» одразу починається обхід, і перше, що бачить хост, — питання про **перший елемент** | між викликом дії і першим питанням про елемент з'явився діалог SDK |
| A9 | Наявні чотири гуртові дії не змінили поведінки | набір тестів `bulkContextMenu`, зелений до зміни, впав після |
| A10 | Обидві дії описані в `docs/USAGE.md` разом із **порядком обходу** й **семантикою відмови** | доку прочитано, і з неї не видно, що станеться на відмові третього елемента |

## Out of scope

- **Що саме означає «редагувати»** всередині хоста — які поля, який діалог. SDK не знає й не
  повинен: він питає про елемент і приймає відповідь.
- **Undo пачки.** Ані `LayoutPatch`, ані `onLayoutChange` сьогодні не мають зворотної операції;
  додавати її разом із гуртовими діями означало б два рішення в одному циклі.
- **Marquee-вибір** (T67 Phase 2) — інший спосіб набрати виділення, не інша дія над ним.
- **Режим редагування як окремий стан діаграми.** Питання надіслано хосту 2026-09-13 (як там
  працює редагування посад, чим вони виключають маніпуляції з тим, що маніпулювати не можна, і чи
  є в них гуртові дії). До відповіді нічого не проєктуємо: у нас гуртові мутації доступні через
  меню без окремого режиму, і вводити режим наосліп означало б вигадати хостову модель за хоста.
- **`multiSelect: boolean` на інстанс** — відкрите питання з обговорення власності: друга
  діаграма хоста однозначна. Воно про **набір** виділення, не про дії над ним.
- **Видалення як різновид `LayoutPatch`.** Тут SDK лише **питає** хоста; чи з'явиться
  `type: 'delete'` у патчі персистентності — окреме рішення, бо патч описує те, що SDK **зробив**
  зі сценою, а видалення робить хост.

## Рішення власника продукту 2026-09-13 — обидва питання закриті

**1. ✅ Підтвердження цілком хостове.** SDK не показує «Видалити 5?» і не має власного
`confirm`. Прецедент на боці хоста: його дескриптор меню вже несе `confirm` для руйнівних дій, а
меню SDK — лише дефолтне. Отже SDK питає про **елемент**, а не про **пачку**, і жодного
підтвердження не малює.

**2. ✅ Правило вже реалізоване й задокументоване — потрібне посилання, не рішення (GATE 1).**
`interaction/contextMenu.ts:33-36`, докстрінг дослівно: *«Organization-only sets also get
expand/collapse; **mixed sets keep the kind-agnostic items**»*. Тобто гуртові мутації просто йдуть
тією самою гілкою `selection.every((n) => n.kind === 'organization')`, і на змішаному наборі не
показуються. Питання знято з людини.

⚠️ **Але спостереження, через яке я його ставив, лишається чинним і потрібно окремо:
змішаний набір у нас ДОСЯЖНИЙ.** Рішення власника «організації окремо на діаграмі організацій,
посади окремо на діаграмі з посадами» правдиве для **застосунку хоста** й **не** для нашої
штатної сцени.

Перевірено в коді, і це знахідка, а не уточнення:

`bindOrgCardInteractions` (`render/orgCardInteractions.ts:43-59`) — **один** обробник для двох
сцен, і його гілка на модифікатор безумовна:

```ts
if (isSelectionToggleModifier(mods)) {
  doubleTap.reset();
  handlers.onOrgClick?.(orgId, mods);   // → handleNodeSelect → у набір
  return;
}
```

Цей обробник прив'язується і до карток деревної сцени (`DiagramRenderer.ts:1091`), і до
**карток org ярусу 3 штатної сцени** (`:919`). У штатній сцені йому додано `onSingleTap`
(«розгорнути на місці або зануритись») — але це **додаткова** дія, а не заміна: у коді
`onSingleTap?.(orgId)` і `handlers.onOrgClick?.(orgId, mods)` стоять **поруч**, обидва
виконуються.

🔴 **Наслідок:** у штатній сцені можна shift-клікнути посаду, потім shift-клікнути картку
організації — і отримати **змішаний набір** `position` + `organization` в одному виділенні.
Тобто стан, для якого в моделі хоста немає назви, у нас **досяжний уже сьогодні**.

**Тобто наявне правило меню виконує рішення власника, а не дублює його:** сцена однорідності не
гарантує, а меню її вимагає — і вимагало ще до цієї спеки.

🔴 **І власник продукту закрив це рішенням, яке робить знахідку ДЕФЕКТОМ, а не спостереженням**
(2026-09-13): *«картки організацій і посади малюються разом, але там маніпулювати можна **тільки
посадами**»*.

Тобто картка org у штатній сцені **не має** потрапляти у виділення взагалі. Сьогодні потрапляє —
через безумовну гілку `isSelectionToggleModifier` у спільному обробнику. Це не «нерозв'язане
питання дизайну», а розходження з тим, як сцена **має** працювати.

**Наслідок для скоупу:** правило однорідності меню лишається як **гард**, але перестає бути тим,
що тримає коректність — бо змішаний набір узагалі не мусить виникати. Обидва потрібні: гард
захищає від того, чого не мало статись, а виправлення прибирає причину.

⚠️ **Це зміна НАЯВНОЇ публічної поведінки** (shift-клік по картці org у штатній сцені сьогодні
виділяє, після правки — ні), тож вона має власні приймальні рядки й власний ризик, а не
доїжджає тихо разом із гуртовими мутаціями.
