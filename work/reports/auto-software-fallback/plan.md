## 3. Кроки

### К1. Модуль детекту — два експорти, не шість

```ts
export type RendererDetector = () => 'software' | 'unknown';
export function createSoftwareRendererDetector(
  readUnmaskedRenderer: () => string | null,
): RendererDetector;            // мемоїзоване замикання
export function readUnmaskedRendererFromDom(): string | null;   // єдине місце з DOM/GL
```

Усередині файлу, **не** експортовано: `SOFTWARE_RENDERER_MARKERS` (рядок + причина поруч) і
зіставлення. Продакшн тримає один детектор у модулі:
`const detectRenderer = createSoftwareRendererDetector(readUnmaskedRendererFromDom)`.

**Мемоізація — замиканням, не «кешем».** Пробник захоплюється у фабриці, а не приймається в
метод, тож спитати той самий детектор двома різними пробниками неможливо; слово «кеш» не
запрошує `set`/`clear`. Тест створює власний детектор — публічного `reset` не з'являється.

⚠️ Обґрунтування Р-4 першої редакції («інакше в барелі з'явиться третій `*ForTests`») було
**хибним на фактах**: у SDK п'ять модульних `*ForTests` (`worker-bridge.ts:40`, `bridge.ts:106,112`,
`wasm-init.ts:28`, `searchWorker.ts:57`), а в барелі — **два** (`index.ts:53-54`). Модульний стан
барель не забруднює сам собою; T105 — про ре-експорт. Форма обрана не заради барелю, а тому що
замикання простіше за фабрику об'єкта.

**Правила зіставлення** (закриває blocking про форму маркерів): підрядок, **без урахування
регістру**, по нормалізованому рядку — реальні значення майже завжди загорнуті
(`ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)…))`,
`ANGLE (Microsoft, Microsoft Basic Render Driver Direct3D11 vs_5_0 ps_5_0)`,
`Mesa/X.org, llvmpipe (LLVM 15.0.7, 256 bits)`).

Маркери: `swiftshader`, `llvmpipe`, `softpipe`, `microsoft basic render`, `software rasterizer`,
**`warp`**, **`software adapter`**, **`apple software renderer`**. Останні три додані на GATE 2:
`WARP` і `Software Adapter` — це рівно RDP-сесії й тонкі клієнти на Windows, тобто заявлена
аудиторія, і їх у першій редакції не було.

**Таблиця рішень — повна, без недовизначених гілок:**

| Вхід | Вердикт |
|---|---|
| рядок містить маркер | `software` |
| рядок є, маркера немає | `unknown` |
| рядок `null` / порожній | `unknown` |
| розширення `WEBGL_debug_renderer_info` немає | `unknown` |
| `getContext` віддав `null` | `unknown` |
| читання кинуло | `unknown` (виняток не виходить назовні) |

`unknown` завжди означає **поточну поведінку**. Гілки «не знаю → здогад» у дизайні немає.

### К2. Читання рядка з DOM

`readUnmaskedRendererFromDom()`: від'єднаний `<canvas>` (у DOM не потрапляє),
`getContext('webgl2') ?? getContext('webgl')`, розширення `WEBGL_debug_renderer_info` →
`getParameter(UNMASKED_RENDERER_WEBGL)`. Контекст звільняється через `WEBGL_lose_context`, якщо
розширення є. Уся функція в `try`.

⚠️ Якщо `WEBGL_lose_context` відсутній, контекст живе до GC. Це **записане обмеження**, а не
«звільнено»: A8 сформульований так, щоб не стверджувати недоказовного.

Це синхронно й дешево: один `getContext` + один `getParameter`, без малювання. Верхньої межі
часу не потрібно — вимірювання в дизайні немає.

### К3. Вплітання у вибір

```ts
export function resolveRendererPreference(
  value?: unknown,
  detect: RendererDetector = detectRenderer,
): ResolvedRendererPreference
```

Порядок:

1. `'canvas'` / `'webgl'` → повертається **як зараз**, `detect` не викликається (A5);
2. невідоме значення → діагностика як зараз, далі як `auto`;
3. `auto` → `detect()`; `unknown` ⇒ **байт у байт** поточний результат (A3);
   `software` ⇒ `{ preference: ['canvas'], failIfMajorPerformanceCaveat: false }`.

Дефолт другого параметра — той самий екземпляр детектора, тож обидва наявні виклики резолвера
(`OrgHierarchyDiagram.ts:412` і `PixiHost.ts:225`) бачать **один** вердикт: мемоізація робить
другий виклик безкоштовним і тотожним. Дуплікацію виклику навмисно **не** прибираємо — вона
наявна, мемоізація робить її нешкідливою, і прибирання розширило б дифф на фасад без потреби (KISS).

⚠️ **Тестовий шлях до `PixiHost.init`.** `init:225` викликає резолвер без другого аргументу, а
`PixiHostOptions` не має куди детектор прокласти. Щоб тести, які йдуть через `PixiHost.create`,
не ходили в модульний детектор, `PixiHostOptions` отримує **внутрішнє, не документоване**
поле `detectRenderer?: RendererDetector` — воно не потрапляє в `docs/USAGE.md` і тому не стає
публічним API за визначенням порога. Без нього `twoDiagrams.contract.test.ts` зафіксував би
вердикт модуля на весь файл.

### К4. Діагностика

Коли й тільки коли детект змінив вибір, `diagnostic` називає впізнаний рушій. Нічого не змінив —
рядка немає (A9).

### К5. Документація

`docs/USAGE.md` § `renderer`: дві сходинки, список за іменами, і прямо — **це не гарантія** (A10).
Рядок `:149` («не покладайтесь на `'auto'`») переписати: порада передавати `'canvas'` явно для
парку терміналів лишається, але тепер як **визначеність**, а не як «інакше буде погано».

§ обмежень (`:496-503`) — уточнити конкретно (перевірено по коду Pixi, не припущено):
`isWebGLSupported.js:7-9` кешує вердикт при першому виклику й **ігнорує** переданий далі
`failIfMajorPerformanceCaveat`; `autoDetectRenderer.js:27,41` іде по `preference` по порядку, і
гілка `canvas` безумовна. Отже коли ми віддаємо `['canvas']`, `isWebGLSupported` **не
викликається взагалі** — демотована `auto`-діаграма більше не засіває глобальний кеш Pixi, і
описаний там недетермінізм для сусіда **зменшується**.

⚠️ `check:docs` цього кроку не перевіряє: `check-docs.mjs:104-113` звіряє лише **імена** публічних
методів `OrgHierarchyDiagram` проти тексту `USAGE.md`, а ця зміна нових методів не додає. Крок
верифікує рев'ю, і так він і записаний в A10.

## 5. Сайд-ефекти

1. **`auto` тепер може обрати canvas там, де раніше обирав webgl** — мета зміни, але це зміна
   дефолту для всіх хостів. Хто хоче старе — `renderer: 'webgl'` (уже існує).
2. **Один зайвий GL-контекст на сторінку** — створюється й одразу звільняється, один раз завдяки
   мемоізації. Pixi робить рівно те саме у `isWebGLSupported`.
3. **Затримки виміру немає.** Один `getContext` + один `getParameter`, без малювання — тому
   стелі часу в дизайні не існує (на відміну від знятої проби).
4. **Недетермінізм із `USAGE.md:496-503` зменшується**, а не зростає — перевірено по коду Pixi,
   див. К5.
5. **Експорт не зачіпається окремо:** PNG/PDF знімаються з живого канвасу, тож вони вже слідують
   за рушієм — це той самий шлях, що при явному `'canvas'`.
6. **`AbortSignal` на публічному шляху не прокидається:** `OrgHierarchyDiagram.ts:414` не передає
   `signal` у `PixiHost.create`. Для цієї зміни ціна скасованого монтування — один `getContext`,
   тобто мізер; названо, щоб не виводилось читачем.

## 6. План міграції

Міграції даних немає. Для хостів це зміна поведінки, не API: жодна публічна сигнатура не
міняється, нових документованих опцій не з'являється.

Порядок: К1 → К2 → К3 → К4 → К5 → К6, за TDD, кожен крок лишає сюїту зеленою.

## 7. Rollback

1. **Хост сам:** `renderer: 'webgl'` фіксує WebGL уже сьогодні, без релізу SDK.
2. **`git revert`** гілки: дифф ізольований у двох файлах `render/` + `docs/USAGE.md`, спільного
   стану з рештою немає.

Рівень «прапорець компіляції» з першої редакції **викреслено**: у JS це не механізм, а в коді
воно лишало б мертву гілку, яку доведеться тримати зеленою, і дешевшим за `revert` не було б
ні для кого.

## 9. GATE 2 — що зробили зі знахідками
