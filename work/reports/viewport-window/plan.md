## 2. Reuse-first

Звірено з кодом і CRG-графом (`code-review-graph`), плюс тайп-граф `ttsc-graph` по межі пакетів.

### Переюзуємо

| Механізм | Де | Для чого тут |
|---|---|---|
| `mergePartial` / `mergeById` | `data/mergeData.ts:15,27` | половина `spliceData` — додавання — уже написана |
| `SearchIndexService.append` | `interaction/SearchIndexService.ts:61` | зливає індекс замість перебудови |

| нотифікатор зміни в'юпорту | `OrgHierarchyDiagram.ts:294-303` | **узагальнюємо, а не дублюємо** — див. нижче |
| ліс із кількома коренями (T65) | `layout/` | 100k після зняття переприв'язки — це ліс фрагментів |

### Нове — і чому наявне не підійшло

| Нове | Чому не переюзали |
|---|---|
| публічний колбек камери в `callbacks.ts` | у контракті **немає нічого** про камеру; `subscribePromoteSync` спрацьовує на потрібне, але його ім'я заявляє промоут. Тому: **перейменувати внутрішній нотифікатор у нейтральний і підписати на нього промоут**, а не заводити другий поряд. Один нотифікатор, два споживачі |
| `spliceData({ add, removeIds })` | `mergePartial` уміє лише додавати; `SearchIndexService` має `append`, але **не має видалення**. Половини механізму просто не існує |
| шар скелетонів | у репо **немає жодного** placeholder-рендера, крім медійних заглушок (це про картинки, не про вузли) |
| колбек пошуку поза вікном | `diagram.search()` шукає лише завантажене й **мовчить** про це |
| генератор 100k без переприв'язки | наявний свідомо будує зв'язне піддерево (`scaleOrgs.ts:73-78`); саме це й ламає суванння |

### 🔴 Дві величини на ім'я «pad» — іменуються по-різному

T88 попереджає прямо, і попередження виконується: у промоуті `pad` — це **екранні пікселі**
навколо в'юпорта для DOM-карток. Наша величина — **запас у екранах** для матеріалізації даних.
Різні одиниці, різний зміст. Наша називається **`reserveScreens`**, і слово `pad` у ній не
з'являється.

## 3. Кроки (порядок Р8: скелет наскрізь → м'ясо)

### Етап 1 — наскрізна смуга на `staff-1m`

1. **Узагальнити нотифікатор.** `notifyPromoteSync`/`subscribePromoteSync` →
   нейтральне ім'я (`notifyViewChanged`/`subscribeViewChanged`). Промоут стає одним із
   підписників. Чисте перейменування, поведінка не змінюється.
2. **Публічний колбек.** `onViewportChange?(t: ViewportTransform, meta: { settled: boolean })`
   у `callbacks.ts`. Кадрово скоалесцений (як `requestPaint`); `settled` стає `true` після
   періоду спокою. Хост рахує арифметику на кожній події (вона дешева) і матеріалізує на
   `settled` **або** коли з'їдено запас.
3. **`spliceData`.** `{ add?: TRaw; removeIds?: Partial<Record<keyof DiagramData, readonly string[]>> }`.
   Ключована форма, а не пласкій список: id унікальні лише всередині колекції.
   Потрібен `removeByIds` у `mergeData.ts` і `remove` у `SearchIndexService`.
4. **Скелетони.** `setSkeletonBoxes(boxes: readonly WorldBox[])` — SDK малює прямокутники й
   **не знає, що вони означають**. Окремий Pixi-шар під шаром вузлів.
5. **Вікно в демо.** Підписка на колбек → `resolveStaffWindowStart` → `spliceData`.
6. **Виміри — і вони визначають решту:** `reserveScreens`, поріг перебудови, ціна перебудови в мс.

### Етап 2 — пошук

7. `searchBeyondWindow?(query, page): Promise<{ hits, hasMore }>` у контракті; `diagram.search()
   ` питає хоста, коли власний індекс порожній. Демо відповідає арифметикою конгруенцій.

### Етап 3 — blur

8. Двостановий blur за швидкістю камери з гістерезисом (Р2). **Не робиться, поки етап 1 не дав
   вимір** — можливо, з готовим запасом він не потрібен.

### Етап 4 — 100k

9. Зняти переприв'язку в `buildScaleOrgsWindow`; вікно = ліс фрагментів.
10. Те саме суванння в matrix і row-tree.

## 4. Сайд-ефекти

| Ефект | Кого зачіпає | Пом'якшення |
|---|---|---|
| три нові члени публічного API | усіх хостів | **усі опційні** — наявний хост не помічає зміни |
| перейменування `subscribePromoteSync` | хости, що його викликають | метод **не в `docs/USAGE.md`** і не експортований у типах — але промоут-оверлей у SDK його вживає. Лишаємо старе ім'я як делегат на один реліз |
| `diagram.search()` стає асинхронно ширшим | хости з вікном | без колбека поведінка **не змінюється** |
| демо 100k показує ліс замість зв'язного піддерева | видима зміна демо | названо в звіті й на екрані; це прийняте рішення Р7 |
| пам'ять при суванні | `staff-1m`, `scale-100k` | виселення робить профіль **сталим**; без нього ріс би до 1M |
| скелетони малюються щокадру, поки вікно не готове | кадр під час перебудови | шар — прості прямокутники без тексту; ціна входить у вимір етапу 1 |

## 5. План міграції

Міграції даних немає — жодна схема не змінюється. Міграція **API**, і вона адитивна:

1. Нові колбеки й `spliceData` виходять як додавання; жоден наявний виклик не ламається.
2. `docs/USAGE.md` оновлюється **тим самим комітом**, що й сигнатура (Конституція).
3. `subscribePromoteSync` лишається як тонкий делегат із поміткою про заміну — прибирається
   окремою задачею, не цією.
4. Демо переходить на новий шлях повністю: старий перехід по `pos-N` і по кліку **лишається**
   (він і далі потрібен для стрибка), суванння додається поряд.

## 6. Rollback

| Крок | Як відкотити | Що rollback НЕ поверне |
|---|---|---|
| 1–4 (SDK) | revert комітів; API адитивне, споживачів поза демо немає | — |
| 5–6 (вікно в демо) | revert; демо повертається до `pos-N` + клік | — |
| 9–10 (генератор 100k) | revert | **нічого незворотного**: генератор синтетичний, даних користувача немає |

Незворотних ефектів немає взагалі: ні міграції даних, ні зовнішніх викликів, ні записів
у сховище. Найгірший наслідок відкату — демо повертається до сьогоднішньої поведінки.
