# 📋 Report — рев'ю коміту `0b772b3` (CI паралельної сесії)

**Date:** 2026-08-26 · **Діф:** `4dbb5f8...0b772b3` · **Осі:** Standards (`sonnet`, після падіння `fable`), Spec (`sonnet`)
**Привід:** коміт залито в `main` без рев'ю — 279 рядків CI, які вирішують, що вважати «перевіреним».

## 1. Що зроблено

Виправлено чотири знахідки, по одній правці кожна:

1. **Гейт `ai-review` став чесним.** Було: перевірка ключа на рівні **кроку**, тож без
   `ANTHROPIC_API_KEY` job проходив `success` — на PR це зелена галочка «рев'ю пройдено», за якою
   нічого немає. Стало: job `preflight` рахує наявність ключа й віддає `outputs.has_key`, обидва
   рев'ю-job'и — `needs: preflight` + `if:`, тобто без ключа вони **skipped** (сірі). Кроки-заглушки
   прибрано: тепер про причину каже сам `preflight`.
2. **`id-token: write`** прибрано — жоден крок не використовує OIDC.
3. **Адреса Pages** жила у трьох місцях; лишилась одна — дефолт у `playwright.prod.config.ts`,
   workflow передає порожній `PROD_URL`, коли користувач не задав свій.
4. **`prod-smoke` більше не біжить у локальній сюїті.** Кореневий `playwright.config.ts` брав увесь
   `./e2e`, тож три prod-тести йшли і проти локального preview. `testIgnore` це закрив:
   локально **40** тестів, `test:prod` бачить свої **3**.

## 2. Протестовані сценарії

Приймальної таблиці в цієї роботи немає — вона прийшла без циклу `spec-flow`. Тому перелічую, що
саме перевірено, а не збираю таблицю заднім числом.

| Перевірка | Результат |
|---|---|
| `npx playwright test --list` (кореневий конфіг) | 46 тестів у 10 файлах, `prod-smoke` **відсутній** |
| `npx playwright test --config playwright.prod.config.ts --list` | 3 тести, лише `prod-smoke` |
| Локальна сюїта без скріншотних | 40 passed |
| `npm run typecheck` | чисто |
| Форма workflow після правки | `preflight` → два job'и з `needs` + `if`; `HAS_KEY` лишився тільки в `preflight` |

**Не перевірено:** сам прогін `ai-review` і `post-deploy` у GitHub — потребує ключа в секретах і
реального деплою. Це межа перевіреного, а не «має працювати».

## 3. Неочевидне

- **Гейт, що зеленіє, нічого не зробивши** (`ai-review.yml:36-45` до правки). Автор **знав** про
  обмеження — у коментарі було написано, що `secrets` недоступні в job-level `if`. Але наслідок
  лишався: conclusion job'а — агрегат по кроках, тож пропущений крок при успішних checkout і echo
  дає `success`. Маніфест при цьому стверджував протилежне (`.claude/standards.md`).
- **Дві мої підозри не підтвердились**, і це варте запису не менше за знахідки: тригер
  `post-deploy.yml` **не** мертвий (`workflows: ['Deploy demo (GitHub Pages)']` дослівно збігається
  з `name:` у `pages.yml`), а `ai-review` дає **два справді незалежні** проходи — різні промти,
  різні `fetch-depth`, різні `--allowedTools`.
- **Я сам не помітив дубля prod-smoke**, хоча бачив його наслідок: після rebase локальний прогін
  показав 44 тести замість 41, і я записав це як «у гілку приїхав prod-smoke», не спитавши, чому
  він там біжить.
- **Опис мого ж коміту неповний.** `0b772b3` заявляв правки в `standards.md` як «рядки машинних
  гейтів + нотатка про Pages», але діф ніс іще секцію «Rust і TS — один репо», переписаний рядок
  про WASM-межу й секцію «Життєвий цикл задачі»; `AGENTS.md` — ще й секцію «Pipeline». Історію не
  переписую (коміт у `main`), тож пропуск зафіксовано тут.

## 4. Скріни

Не застосовно, бо зміна не має екранного вияву: CI-конфіги й розподіл тестів між двома
playwright-конфігами.

## 5. Проходка по user flow

Користувач тут — розробник, що відкриває PR:

1. Відкриває PR → у списку чеків бачить `AI review / API key present?`, а два рев'ю-проходи
   **сірі (skipped)**, поки в репо немає `ANTHROPIC_API_KEY`. Раніше на цьому місці були дві зелені
   галочки, які нічого не перевіряли.
2. Додає секрет (`gh secret set ANTHROPIC_API_KEY`) → на наступному пуші обидва проходи стають
   активними й пишуть рев'ю в PR.
3. Запускає `npm test` / `npm run test:e2e` локально → prod-smoke не заважає, бо йому потрібен
   живий деплой.
4. Після деплою Pages → `post-deploy.yml` тригериться сам і ганяє `npm run test:prod`.

Кроки 1 і 3 пройдено фактично (`--list`, локальний прогін); кроки 2 і 4 — ні, див. §2 «не перевірено».

## 6. Ризики й обмеження

- **`prod-smoke` не має failure-кейсів** (`work/TDD.md` §2 діє на весь репо). Свідомо не додавав:
  для smoke по живому продакшену природний фейл — це недоступний або зламаний деплой, а штучні
  падіння тут перевіряли б Playwright, не продукт. Якщо вимога буквальна — це окремий таск.
- **Дублювання між двома рев'ю-job'ами** лишилось (кожен має свій `checkout` + виклик дії).
  Прибирати в composite/reusable workflow зараз — абстракція під два виклики; лишаю до третього.
- **Ключ у секретах не встановлений**, тож обидва проходи будуть `skipped` — тепер це видно
  чесно, але рев'ю на PR фактично не працює, доки ключ не додадуть.
