ФАКТ (BLOCKING, Q7 — внутрішня суперечність плану): §1 плану малює ланцюг як реюз РЕАЛЬНИХ id
членів (parent → a → d → g, ніяких нових id). Але §7 («Межа WASM↔TS») прямо каже: «у WASM їдуть id,
яких немає в даних хоста (ланки ланцюгів)... синтетичні id мають префікс, не перетинаються з
реальними... розгортання прибирає їх до повернення» — а tasks.md К2 явно вимагає тест «синтетичний
id не збігається з реальним, навіть на сцені де org так названо». Це два різні механізми:
(а) ланцюг = реальні id, переприв'язані parentOrgId (як у §1, синтетичних id взагалі нема, unflatten
нічого не «прибирає», бо нема що прибирати) чи
(б) ланцюг вводить справжні нові (синтетичні) вузли-ланки, які треба виявляти й вирізати з
raw.nodes/raw.edges перед поверненням.
План не каже, який з двох це насправді, а від відповіді залежить: чи є в raw.nodes зайві вузли, які
не мають зʼявитися у фінальному результаті (і як їх відрізнити — по префіксу? по флагу?), і чи
`OrgLayoutNode.id` (не тільки orgId) для члена сітки лишається реальним increment по всьому
пайплайну, від чого залежить рендер/хіттестінг/контекстне меню, що керуються `id`. Без вибору
одного з двох варіантів К2 і К4 неможливо коректно імплементувати одночасно.
