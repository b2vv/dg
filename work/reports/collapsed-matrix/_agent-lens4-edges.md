## Знахідки за темами

### 1. Числа n

**BLOCKING** · n = 0 (немає дітей у вузла)

Коли вузол немає дітей (n = 0), критерій A1 каже «n>1» — не повинна стати сіткою.
Але як алгоритм обробляє порожній набір? `resolveMatrixDimensions(0, ...)` дає:
- `cols = max(1, ceil(√0)) = 1`
- `rows = max(1, ceil(0/1)) = 1`
Це 1×1 сітка з нулем елементів. Критерій A1 каже «≥2 братів» — 0 не входить, норм.
Але коли набір братів **порожній** від початку, `planCollapsedSiblingGrids` викликаються на пустій масив?
Якщо правило є для набору на лінії 45 spec.md: "набір братів, **усі** згорнуті й **>1**" —
тоді на нулю це не спрацює. **Але в коді цей випадок має бути обробленим явно, не випадково.**

**non-blocking** · n = 2 (два брати)

spec.md §Межа вже документує: `n=2 → ceil(√2)=2 → 1 ряд на 2 колонки = візуально those-op`.
Критерій A1 каже "ceil(√n)" — він правильний математично, але A2 каже "рівно 1 → не сітка".
`n=2` це не "рівно 1", це 2. Відповідь: `cols=2, rows=1, bounded=false` — це сітка 2×1.
Видима: лівий-правий два вузла у сітці 2×1 = той же ряд як і раніше.
**Критерій записаний вірно, випадок названий, але є ризик запитання "чому 2×1 це сітка".**
Відповідь в spec.md знайдена, код мав би це дублювати у коментарі К1.

### 2. matrixOrder — порядок у сітці

**BLOCKING** · часткове заповнення matrixOrder (не у всіх членів)

план §3.1 дірка (Q2): "matrixOrder, коли він є в **усіх** членів набору; інакше порядок з даних цілком".
Критерій A7 каже те саме. Але як К1 перевіряє це правило?
`planCollapsedSiblingGrids` повинна:
1. Якщо `matrixOrder` є в **кожного** члена набору й спільна база (не NaN, не дублюється) → юз його
2. Інакше → порядок з `organizations` array (як вони прийшли)

Проблема: що таке "порядок з даних"? Чи це ordre of вхідного array, чи щось інше?
**На відміну від глобальної матриці (matrixGrid.ts лінія 51 `sortOrgs`)** що має fallback до `a.id.localeCompare(b.id)`,
для row-tree сітки порядок повинен бути **стабільний**, але де сорт?

**BLOCKING** · matrixOrder від'ємні числа

`matrixGrid.sortOrgs` на лінії 51 робить `(a, b) => (a.matrixOrder ?? 0) - (b.matrixOrder ?? 0)`.
Якщо `matrixOrder = -5, -3, -1` → сорт нормальний. Але якщо `-1, -1, 1` → дублікати!
**Тест К2 це перевіряє?** План каже "дублікати → порядок детермінований", але без прикладу як вирішити дублікат.

**BLOCKING** · matrixOrder не ціле число

`matrixRow/matrixCol` у вхідних даних теоретично можуть бути `0.5` (т.з. "фліп" під час drag).
matrixGrid.ts лінія 63 має `normalizeCell` що робить `Math.floor()`.
**Але matrixOrder — це не координата, це порядок. Чи може хост прислати 0.5?**
Якщо так — `sortOrgs` буде компарувати 0.5 < 1, що коректно. Тест мав би перевірити.

**non-blocking** · matrixOrder величезне число (тип Number.MAX_SAFE_INTEGER)

sortOrgs робить арифметику `a.matrixOrder ?? 0 - b.matrixOrder ?? 0`. 
Якщо обидва числа близьки до MAX_SAFE_INTEGER, різниця може переплутати JS. Але це крайній edge case.

### 3. Дані про org: батьки й цикли

**BLOCKING** · батько не існує в payload (missing parent)

`toOrgFlatInput` (rowTreeLayout.ts лінія 23) вже робить це:
```ts
parentOrgId: o.parentOrgId && ids.has(o.parentOrgId) ? o.parentOrgId : null,
```
Якщо батьків немає — вони стають `null`. Отже "висячий батько" **не можливий** для row-tree.
Але для **матриці схлопнутих сиблінгів** — чи це важливо?
Коли K1 будує набір "діти батька X", а X не у даних:
- rowTreeLayout.ts вже видалив ці дітей перед дзвінком до `computeOrgRowTreeLayoutWasm`? Ні.
- `visibleOrgsForRowTree` фільтрує за `expanded`, не за наявність батька.
**Отже набір братів може містити org без валідного батька, якщо батько не розгорнутий.**
К1 запускається **до** rowTreeLayout, тому **К1 має обробити цей випадок явно**.

**BLOCKING** · сам-собі-батько (самовідсилання parentOrgId)

`findExpandedRootIds` (orgMode.ts лінія 76) вже ловить цикл: `if (seen.has(id)) return Infinity`.
Але це у логіці **пошуку коренів**, не у побудові набору братів.
К1 будує набір як: "знайти всіх org.parentOrgId === X".
**Якщо X = себе сам, він не буде у своїх ж дітей.** Проблема вирішена архітектурою, але коментар пояснює чому.

**BLOCKING** · два кореня (forest) в одній компоненті графу

plan.md §4 п.1 і 3.1: взаємодія з forest-гілкою (T78-L3).
computeOrgLayout найчастіше вже розбивається:
```ts
const rootIds = findExpandedRootIds(organizations);
if (rootIds.length === 0) → matrix
if (rootIds.length === 1) → single tree
if (rootIds.length > 1) → forest (Promise.all)
```
**К1 запускається всередині `computeOrgRowTreeLayout`**, який отримує один `expandedRootId`.
Отже К1 завжди бачить **дерево з одного кореня**, не forest.
**Норм, але тест К4/К5 мав би перевірити рекурсію на forest (два набори на різних рівнях, нижче двох corenів).**

### 4. Взаємодія з глибиною й forest

**BLOCKING** · ланцюги додають rows-1 рівнів до глибини (план §4 п.1)

plan.md §3.1 дірка 1: трансформація **до** vs **після** гвардії.
- Трансформувати **до** → гвардія міряє роздуту глибину й кидає помилку, де справжнє дерево нормально.
- Трансформувати **після** → гвардія міряє правду, але WASM їде дерево на `rows−1` глибше.
  За ~4500 глибини на вході Ploeg **вбиває WASM-модуль** (вся SDK впала).

Рішення в плані: гвардія **двічі** — на `realDepth` і на `realDepth + maxChainExtra`.
**К3 мав би перевірити обидві перевірки:** 
- Дерево глибини 2500 + 100 дітей сітка (rows=10, cols=10) → 2500+9 = 2509 → error "grid depth"
- Але гвардія мусить сказати, що це **сітка** спричинила помилку, не вхідне дерево.

Питання: який text повідомлення мав би бути? Мав би бути **окремий error**, не переписувати існуючий.

**non-blocking** · forest із двома рівнями сіток

С5 spec.md: два набори на різних рівнях можуть мати різні режими (один сітка, інший ряд).
Це рекурсивне. **Але К1 повинна бути чиста функція і не чіпати forest.**
Коли `computeOrgLayout` викликає `computeOrgRowTreeLayout` на кожен корінь, К1/К2 **незалежно** трансформує вхід кожного.
Гарна новина: К1/К2 не мають знати про forest, це работа К3 (вплетення).

### 5. Undefined collapse & вироджені сцени

**BLOCKING** · isOrgCollapsed(org) з undefined

orgMode.ts лінія 5: `org.collapsed !== false` → **true** (collapsed).
Отже `undefined` це загальна поведінка, **collapse=undefined = collapsed=true**.
К1 повинна це дотримуватися: `undefined` → "це член набору для сітки".
Критерій A2 забороняє сітку на 1 членові, але не розрізняє `undefined` vs `true`.
**Норм.**

**BLOCKING** · нема дітей (всередину вузла 0 дітей)

Якщо org розгорнутий & немає дітей — це листок у видимому дереві.
К1 запускається на **набір братів одного батька**.
Якщо у батька **немає дітей** — набір порожній, К1 не спрацьовує.
Норм, але К1 тест мав би явно назвати: empty set → не сітка.

**non-blocking** · всі org згорнуті (глобальна матриця)

С6 spec.md: "Collapse all" дає те саме 24 картки, А8 гарантує.
К1/К2/К3 не мають менти глобальну матрицю (`detectOrgMode` лишається як є).
Тест К8 це перевіряє (A8) — має зелений без правок.

### 6. Критерії, які неможливо виміряти як записано

**BLOCKING** · A5 — критерій "накладання як дельта"

spec.md A5: "множина пар вузлів із перетином AABB після ⊆ до".
**Але як записати тест на це формально?**
План говорить про "AABB intersection before & after", але:
1. Потрібна фікстура, де було накладання **до** К3 → неправдоподібно (вже lay-out 4 братів в 1 ряд)
2. Потрібна фікстура, де **немає** накладання після К3
3. Тест записує AABB'ы усіх вузлів до К3, потім після К3, чи багаторазово на проміжних кроках

**Проблема:** якщо К3 інтегрується раптово, не виходить закреплені AABB'ы до К3.
**Рішення:** К3 має свій тест з примусовою сценою, готовою до промірок.

**BLOCKING** · A6 — шляхи, які "досяжні" vs "мають кінець у AABB"

spec.md A6: "для кожного члена існує шлях, його кінець лежить у AABB члена".
Це значить **будь-яка SVG-лінія (path) має завершитися всередину AABB члена, не на його межі**.
**Як це перевіряється?** Спинебусдгес будує на основі розкладених вузлів, не членів сітки.
Тест К4 мав би:
1. Розкласти сцену → nodes
2. Виділити membres сітки (matrixRow/matrixCol != undefined)
3. Для кожного члена: знайти path, що йде до його AABB
4. Перевірити, що path закінчується **всередину**, не на межі

**non-blocking** · A9 — критерій "нечитаний" (machine check)

docs/USAGE.md повинна казати режим **чого** вона називає.
Вариант (а) від GATE 1: лишити значення як є (глобальний режим), додати уточнення.
Тест К5 мав би запустити `npm run check:docs` і перевірити, що гейт пройшов.
**Але А9 залежить від А1-А4 уже здійсненим, тому К5 одна з останніх.**

## Резюме непокритих edge cases

**КРИТИЧНІ (BLOCKING) — мають потребувати явного тесту в К1–К6:**

1. **n=0 (порожній набір братів)** — K1 не спрацьовує, але код має явно сказати це
2. **n=1 (один брат)** — A2 забороняє, К1 тест "failure: single sibling"
3. **matrixOrder дублікати** — К2 тест на дублякати [1,1,2,2] → юз дані цілком
4. **matrixOrder частково заповнено** — К2 тест: один з них має, решта нема → юз дані цілком
5. **Батько не у payload** — К1 обробляє, але тест з missing parentId
6. **Глубина + сітка (rows>1)** — К3 гвардія **двічі**: на реальній глубині, на реальній+rows-1
7. **Гвардія повідомлення** — другий error має казати що сітка спричинила, не дерево
8. **parentId розгортання** — К3 синтетичні nodes мають справжній parentId після К3
9. **matrixRow/matrixCol** — К3 повинна заповнити для членів сітки
10. **A5 AABB накладання** — К3 тест з готовою сценою до/після
11. **A6 шляхи** — К4 тест що path закінчується **всередину** AABB, не на межі

## Додаткові критичні edge cases (Фокус 1–6)

### Фокус 1: Синтетичні id'ы й границі між К2 і К3

**BLOCKING** · К1 неправильно каже "це сітка" на n=1

План К1 обов'язково має відкинути `n≤1`. Якщо К1 помилково повернула сітку 1×1:
- К2 створить ланцюг: `parent → synthetic-0`
- К4 будує хребет на основі synthetic id'ів, які не існують в справжніх даних
- **Тест К1 має явно гарантувати:** `n < 2 ⇒ не сітка`, з назвою case "n=1"

### Фокус 2: Глибина + сітка (план §3.1 дірка 1)

**BLOCKING** · двічі перевірка гвардії з правильними повідомленнями

Ланцюг з `rows=15` членів додає 14 нових рівнів.
- Дерево глубины 2486 + 14 = 2500 ✓ OK
- Дерево глубины 2487 + 14 = 2501 ✗ ERROR про сітку, не про дерево
- **К3 тест:** перевірити обидва пороги окремо й з правильними повідомленнями

### Фокус 3: matrixOrder дублікати

**BLOCKING** · часткові або дублікатні matrixOrder → юз дані цілком

Якщо `matrixOrder = [1, 1, 2, 2, 3]` на 5 членах:
- К1 повинна виявити це і позначити "без порядку"
- К2 повинна юзати глобальний порядок (як вони прийшли в array)
- **Тест К2:** Дублікати + часткові заповнення + один без

### Фокус 4: parentId розгортання (план §3.1 дірка 2)

**BLOCKING** · після розгортання К3 синтетичні вузли мають справжній parentId

- Ploeg бачить ланцюги з ланцюговим parentId під час розкладки
- Результат К3 мусить повернути справжній parentId для **всіх** членів сітки
- **Цей parentId однаковий для всіх членів сітки** (сам батько, не ланцюговий)
- Поля `matrixRow` і `matrixCol` **мають бути заповнені** для членів сітки

### Фокус 5: Валідація input К1

**non-blocking** · К1 повинна припустити що input можна мати

- org'и з missing parentId (батько не у payload) → К1 обробляє
- org'и з різними collapsed значеннями → К1 перевіряє "усі=="
- пустий набір братів (n=0) → К1 не спрацьовує

### Фокус 6: A5 & A6 — вимірювання

**BLOCKING** · A5: накладання як дельта потребує готової фікстури

Тест К3 потребує:
1. Сцена де 4 брати роблять сітку 2×2
2. Знімок AABB'ів до розкладки
3. Знімок AABB'ів після
4. Перевірка: набір перетинів після ⊆ набору перетинів до

**BLOCKING** · A6: шляхи мають кінець у AABB члена сітки

Тест К4 повинен:
1. Розкласти сцену
2. Виділити nodes з `matrixRow/matrixCol !== undefined`
3. Для кожного: перевірити що path **завершується всередину** його AABB

## Висновок

На глави К1–К6 плану дві **гвардії дірки вже названі в плані** (§3.1):
1. Гвардія глубины — проверить **двічі** з окремими повідомленнями
2. parentId розгортання — відновити справжнього батька, не ланцюговий

Але **11 edge cases над критеріями A1–A10** потребують явних тестів, щоб гарантувати что критерії не проскочать мовчки:

- **Граничні числа n** — 0, 1, 2, точні квадрати
- **matrixOrder правила** — дублікати, часткова заповнення, фіксована лінія A7
- **AABB & геометрія** — накладання як дельта (A5), path'ы закінчуються в AABB (A6)
- **Синтетичні id'ы** — не виходять за межі К3, на вході К4 вже справжні parentId

Критерій **A9 залежний від А1–А4** й гейт машинний — К5 залежна від К3 успішної.
Критерій **A8 гарантує що глобальна матриця не змінилась** — тест на Collapse All.
