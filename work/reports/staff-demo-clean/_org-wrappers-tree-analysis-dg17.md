# Аналіз: обгортка-card організації в ШПС + деревоподібні рівні (департаменти vs підпорядковані орг)

**Джерело:** вимога власника (Dg17, після мапи обгорток). **Статус:** аналіз для критика й дискусії, НЕ спека, НЕ код.

## 1. Вимога власника (дослівно, структуровано)

**А. Обгортка-card для ОРГАНІЗАЦІЇ в ШПС — одна база, три варіанти:**
1. **база + фон = lead** (керівна організація)
2. **база + чіп = current organisation** (поточна)
3. **база = subordinate organisation** (підпорядкована)

**Б. Структурне правило:** «База має відокремлювати зʼєднання»: департаменти та підпорядковані
організації — на **різних рівнях**; підпорядковані — на рівень **нижче**, бо вони **поза скоупом внутрішнього
дерева current organisation**. Але все одно **департаменти і підпорядковані орг мають бути побудовані
деревоподібно**.

## 2. Що це міняє у вже прийнятому (чесно)
- **S2 переозначено.** Було (Q5, Dg17): «Lead = ОКРЕМА обгортка; Current = база+чіп». Тепер:
  **Lead = база + ФОН** (модифікатор, не окремий тип); Current = база+чіп; Subordinate = база. Усі три —
  одна обгортка-база з модифікаторами → прибирається «окремий band для Lead». Нюанс: у мокапі Lead має ще й чіп
  «Керівна організація · …» (`_HANDOFF-dg16`); тепер власник каже «фон». Чи чіп Lead лишається — питання.
- Перегук із S7 (card+blob unify) і мапою обгорток: ця вимога — про **org-рівень** (`StaffZonesView`),
  не про department-рівень (`card|blob`). Дві різні осі, не змішувати.

## 3. Поточний стан у коді (факти, `path:line`)
- **Ярус 3 = ряд org-карток, від лівого margin, не дерево.** `canvasLayout.ts:172-218`: `cardX = opts.margin`,
  далі `cardX += columnWidth + horizontalGap` — картки підпорядкованих у ряд зліва, **без центрування під
  віссю поточної орг** (та сама дірка осі, що S6/Dg15; ярус-3 прямо названий у ADR-0002 як непокритий).
- **Зв'язок підпорядкованих — від ГОЛОВИ поточної орг, не від обгортки.** `canvasLayout.ts:246-250`:
  `edges.push({ fromId: curHead, toId: card.orgId, kind: 'cross-tier' })`. Тобто seat→org-card, ребро виходить
  із картки голови, що лежить ВСЕРЕДИНІ ярусу 2 (серед відділів).
- **Маршрутизація cross-tier:** `staffEdgeGeometry.ts:367-376` — спершу пряма вертикаль від голови донизу, якщо
  не зачіпає чужі картки/рамки, інакше «around»-драбина. Для ШПС вертикаль від голови (ряд «Рада директорів»)
  до ярусу 3 проходить крізь/повз рамки відділів → ребро або ламаний обхід, або «сідає» на чужу рамку.
- **Зона ярусу 3 за замовчуванням НЕ малюється:** `StaffZonesView.ts:72,96` — `includeOrgCardsBand`
  default false, `org-cards` tier пропускається. Підпорядковані не мають обгортки взагалі — лише голі
  `OrganizationNode`-картки (`mockupStyles.ts:20-53`, 234×110).
- **Обгортка Lead/Current зараз — не база+модифікатори:** `staffZoneAccent.ts` має лише `currentOrgChipAccent`
  / `resolveZoneBandStyle(style, role)`; `role:'leading'` стиль не резолвить (критик T125 N1).
- **SPEC §2.2 (`work/SPEC.md:76-97`):** ярус 3 — «підпорядковані org / групи org зі своїми посадами»; SPEC
  називає його оглядовим («важка штатка — лише в focus (ярус 2)», рядок 259). Власник тепер додає: ярус 3 має
  бути **деревом**, а не рядом, і ребра мають бути **відокремлені** від внутрішніх ребер ярусу 2.
- **Є готова машинерія дерева орг:** `layout/spineBusEdges.ts:43` («Children below the parent are the primary
  case (org-matrix)») + `rowTreeLayout.computeOrgRowTreeLayout` (Rust Ploeg) — це саме «батько-орг → діти-орг»
  шина. Staff-ярус 3 її НЕ використовує (власна розкладка рядом).
- **`siblingOrgGroups`** (`layout/siblingOrgGroups.ts:49`) — пунктирна рамка навколо сусідніх орг (GoJS matrix
  parity): готовий кандидат на обгортку групи підпорядкованих.

## 4. Інтерпретація «деревоподібно, на різних рівнях»
Три рівні вертикалі (SPEC) лишаються, але міняється **семантика ребер і топологія яруса 3**:
- **Рівень N (внутрішній скоуп current org):** посади + департаменти-рамки; ребра `admin` (посада→посада).
- **Рівень N+1 (поза скоупом):** підпорядковані орг як **діти в дереві**, батько = обгортка/орг-вузол current.
- Ребро N→N+1 — **не admin-ребро посади**, а **org-зв'язок**; «база відокремлює зʼєднання» = різний вид/
  джерело ребра для внутрішнього і міжорганізаційного. Інваріант: `min(y підпорядкованих) >
  max(низ рамок відділів) + gap` — підпорядковані завжди нижче ВСІХ відділів, не поряд.

## 5. Кандидат-архітектури (на дискусію)
- **D1 — лишити head→org-card, лише центрувати ряд ярусу 3 під віссю.** Найдешевше. НЕ виконує «відокремлювати
  зʼєднання»: ребро все ще від картки голови крізь відділи. Закриває лише вісь (S6).
- **D2 — org-зв'язок від ОБГОРТКИ current org (її нижній центр) до карток-дітей, шина (`spineBus`), діти —
  дерево-ряд, центрований під віссю.** Відповідає «поза скоупом внутрішнього дерева» дослівно і відокремлює
  ребра. **Ціна/ризик:** ребро потребує меж обгортки як кінцевої точки, а межі обгортки зараз рахуються у
  **рендері** (`staffZoneBounds.enrichStaffTierBands`, `DiagramRenderer.ts:713`), а не в лейауті → лейаут-ребро
  залежить від render-даних = саме той розсинхрон калькуляції, якого власник боїться (T126/ADR-0002: «одне
  джерело якоря»). Потрібно, щоб межі обгортки (а отже кінцева точка ребра) мали ОДНУ точку обчислення.
- **D3 — один спільний батьківський вузол «org-root» над [відділи, підпорядковані] як діти різних рівнів у
  єдиному дереві** (відділи — внутрішні діти на рівні N, підпорядковані — діти рівня N+1 через ту ж шину).
  Найближче до «деревоподібно», але змішує посадний і оргнівий графи в одному layout-проході (ризик для
  орг-блокового лейауту й TDD-покриття).
- **Попередня схильність аналізу: D2**, за умови єдиної точки обчислення меж обгортки (тоді D2 збігається з
  вимогою №3/ADR-0002). D1 — мінімум-кроку; D3 — дорожче, відкладати.

## 6. Наслідки для вже відкритого
- **S6 (тест осі) розширюється:** ярус-3 центрований під віссю; інваріант рівнів (`y` підпорядкованих > низ відділів).
- **S2 переозначено** (див. §2): база + модифікатори {fill для lead, chip для current}; subordinate = база.
- **Нова підзадача S8:** деревоподібний ярус 3 (D1/D2/D3 після рішення) + org-ребро відокремлене від admin-ребра.
- **ADR-0002** стосується: «точка під'єднання» тепер і для ОБГОРТКИ (не лише картки) — розширити.
- **T126:** межі обгортки як єдине джерело (і для рендеру, і для ребра) — прямий кейс анти-desync.

## 7. Відкриті питання (до власника / критика)
1. Підпорядкована орг — це **компактна org-картка** (згорнута) чи **обгортка навколо своєї штатки** (розгорнута
   «in place», `maxExpandedOrgCards`)? «База» для неї — рамка чого?
2. Батько в дереві для підпорядкованих — **голова current** (як зараз, але відокремлене ребро) чи
   **обгортка current org**? («Поза скоупом внутрішнього дерева» → схоже на обгортку, але семантика відносин
   у даних — `parentOrgId`, а не посада.)
3. Lead = «база + фон»: чіп «Керівна організація» лишається чи фон його замінює?
4. Групи підпорядкованих орг (SPEC «групи org») — рамка `siblingOrgGroups` як обгортка рівня N+1?
5. Чи прийнятно, що ярус 3 стає складнішим за «оглядовий» (SPEC:259) — тобто дерево з шиною, а не ряд?

## 8. СИНТЕЗ ДИСКУСІЇ (аналіз vs критик `_org-wrappers-critic-dg17.md`) — Dg17

### Де критик ПРАВИЙ і аналіз виправлено
- **Факти §3 — усі підтверджені** (`canvasLayout.ts:174,217,247-250`, `staffEdgeGeometry.ts:367-376`,
  `StaffZonesView.ts:92,96`, `SPEC:259`). Нове від критика: `role:'leading'` не резолвиться і `'subordinate'`
  взагалі немає в типі (`staffZoneAccent.ts:30,39,42`) → **дві з трьох обгорток власника сьогодні без стилю**.
- **Моє обґрунтування D2 («межі в рендері → desync») — ПЕРЕБІЛЬШЕНЕ.** `worldBoundsForTier`
  (`staffZoneBounds.ts:15-110`) — чиста функція над виходом лейауту (`tier`, `positionNodes`, `orgCards`); ярус 3
  вже має власний `org-cards` бранч (`:57-89`), що обтягує картки. Реюз тієї ж функції для кінця ребра = ОДНЕ
  джерело, не новий розсинхрон. Лейаут уже пушить band ярусу 3 з `y/height` (`canvasLayout.ts:224-230`).
- **Я пропустив D4:** порахувати межі band у лейауті (викликати ту ж чисту функцію, емітити x/width/y/height у
  band) і докувати ребро до band. Дешевше за D2, desync-free за конструкцією.
- **SPEC:259 («ярус 3 оглядовий») — це БЛОКЕР СПЕКИ, а не м'яке питання.** Дерево з шиною змінює §2.2.
- **«Готова машинерія» перебільшена:** `spineBus` — лише геометрія шини; `computeOrgRowTreeLayout` — row-tree
  для org-вузлів, не для staff-вузлів ярусу 3 (входи інші). Реюз = малювання шини, не топологія.
- **S2 «рішення власника» було відкритим:** Lead мав три формулювання (T125:27 база+модифікатори; wrapper-map
  «окрема band»; тепер «база+фон»). Скасоване «окрема band» рішенням не було — виправлено в `_subtasks`.
- **Інваріант «підпорядковані нижче відділів» недостатній для «деревоподібно».** Потрібні ще: (а) діти
  центровані під віссю батька; (б) вертикальні ребра/шина, без діагоналей; (в) ребро не перетинає рамки
  відділів; (г) рамки підпорядкованих не перетинаються між собою.

### Де критик НЕПОВНИЙ (мій чесний доважок, перевірено у коді)
- **«Одне джерело реюзом» правильне лише якщо вхідні параметри теж одне джерело.** `contentPadding` =
  `departmentWrapperPadding(theme, config)` (`DiagramRenderer.ts:712`) — тема; `labelBand` =
  `this.lastZoneLabelBand` (`:722`) — **стан екземпляра рендера**, лейаут же резервує свій
  `opts.zoneLabelBand` (`canvasLayout.ts:82`). Збіг цих двох чисел **НЕ ВИМІРЯНО**. Якщо вони розходяться —
  desync реальний, але у ВХОДАХ, а не в «місці розташування функції». → Перша перевірка спеки: чи
  `lastZoneLabelBand` ≡ `opts.zoneLabelBand` і звідки береться `departmentWrapperPadding` при лейауті.
- Критик читає «відокремлювати зʼєднання» двома способами (джерело ребра / роутинг) — слушно, обидва
  читання лишаю як питання власнику, не вибираю.

### Оновлена оцінка кандидатів
| | Суть | Статус після дискусії |
|---|---|---|
| D1 | лише центрувати ряд ярусу 3 | не виконує «відокремлювати»; мінімум-крок (= S6) |
| D2 | ребро від обгортки; межі з render | обґрунтування ризику хибне; життєздатний, але див. D4 |
| **D4** | **межі band рахує лейаут (та ж чиста функція), ребро до band** | **нова схильність: дешевше, desync-free, лягає на `canvasLayout.ts:224-230`** |
| D3 | одне дерево відділи+підпорядковані | потрібне, якщо власник мав на увазі ОДНЕ дерево; найдорожче |
Вибір D2/D3/D4 залежить від відповідей власника нижче; **до відповідей нічого не фіксуємо**.

### Питання власнику, що блокують спеку (3 + 2 з критика)
1. «База відокремлює зʼєднання» = **джерело** ребра, **роутинг** (не перетинають рамки), чи обидва?
2. Структура: **одне дерево** (відділи-вузли, підпорядковані діти нижче), чи **два яруси з мостом**, і батько
   моста — **обгортка** current чи **голова** current?
3. **SPEC §2.2 / :259 змінюємо** (ярус 3 перестає бути оглядовим → дерево з шиною)?
4. Lead «база + фон»: фон **замінює** чіп «Керівна організація» чи **разом** із ним?
5. Підпорядкована орг: **компактна картка** (згорнута) чи **обгортка навколо штатки** (розгорнута in-place)?

## 9. РІШЕННЯ ВЛАСНИКА + ФАКТИ МОКАПА (Dg17, після синтезу)

### Рішення (відповіді на §8)
1. «Відокремлювати зʼєднання» = **обидва**: окреме ДЖЕРЕЛО ребра (від обгортки) І чистий РОУТИНГ (без перетинів рамок).
2. Структура = **ОДНЕ дерево** (відділи-вузли; підпорядковані — діти нижче). → D3-напрям, не «два яруси».
3. **SPEC §2.2 / :259 правимо** (ярус 3 більше не «оглядовий» за замовчуванням).
4. Lead-чіп — звірено з мокапом (нижче).
5. **Обгортка = окремий простір навколо ШТАТКИ, «як group у GoJS».** Тобто Q5 закрито: підпорядкована орг —
   це **обгортка навколо своєї штатки**, а не лише компактна картка. База — контейнер із власним простором.

### Що означає «group як у GoJS» (модель, не код)
Група GoJS = контейнер: (а) має **власний простір розкладки** для членів; (б) його межі **виводяться** з членів +
padding + смуга лейбла; (в) **вкладається** (орг ⊃ відділ ⊃ посади); (г) **згортається** до компактного представлення;
(д) **зв'язки чіпляються до групи**, не лише до членів. У репо це вже наполовину так: `layoutStaffOrgBlock` розкладає
КОЖНУ орг у локальних координатах (власний простір), `canvasLayout` лише компонує блоки; `worldBoundsForTier` виводить
межі з членів. Бракує: єдиного **контракту Group** (члени, padding, label band, межі, якір, модифікатори, згорнутість)
і ребра, що чіпляється до групи (D4: межі рахує лейаут тією ж чистою функцією).
→ **Пропозиція на дискусію (НЕ рішення):** один контракт `Group` обʼєднує S2 (орг-обгортка: база+фон/чіп), S7 (card+blob
= два рендери однієї department-групи), S8 (дерево груп) і T126 (єдине джерело меж/якоря, anti-desync).

### Факти мокапа `ШПС картка v3.html` (рядки 14-33, 91-103, 126)
- **Lead = `.porg`** (`:20`): dashed `#3a3a40`, radius 14, padding 44/20/20, **фон — діагональна штриховка**
  `repeating-linear-gradient(135deg, rgba(255,255,255,.012) 0 8px, transparent 8px 16px)`. ⚠️ Альфа **1.2%** — на
  `#0d0d0e` практично невидима; тобто «фон Lead» у мокапі ≈ ледь помітна текстура, а не заливка. Pixi не має CSS-градієнта:
  штриховка = tiling-патерн (окрема робота) або проста заливка-наближення → питання власнику.
- **Чіпа в Lead НЕМАЄ.** Лейбл — це текст: `<em>КЕРІВНА ОРГАНІЗАЦІЯ</em>` (11px, uppercase, letter-spacing .06em, `#7d7d83`)
  + `· Головний офіс` + права дія «Структура ↗» (`:21-25`). **Чип з рамкою є лише в Current** (`.org.cur>.on i`, `:18`).
  → Lead «база + фон + текстовий лейбл», не чіп. (Дія «Структура ↗» — host-chrome, поза SDK-скоупом.)
- **Current = `.org.cur`** (`:16-18`): solid `#5a5a62`, фон `#0f0f11`, orange-чіп. (Вже реалізовано Dg16.)
- **Base `.org`** (`:14`): dashed `var(--org-b)`, radius 14, padding 44/24/24. Підпорядкованих орг у мокапі **НЕМАЄ**
  (єдиний `class="org cur"`) → для 3-ї обгортки **еталона нема**, дизайн — за правилом власника (база).
- **Звʼязок Lead→Current чіпляється до ОБГОРТКИ, не до картки голови:** `.org.cur::before` (`:19`) — 2px dashed
  `#6b6b73`, `left:50%; top:-1px; height:89px` — лінія виходить із верхнього центру обгортки Current; `.plink` (`:30`).
  → **Мокап сам підтверджує «ребро від обгортки»**; зараз демо чіпляє ребро до картки голови (`canvasLayout.ts:243-250`) —
  це розбіжність з мокапом, не лише з вимогою.
- **Дерево всередині — CSS `.tree`** (`:91-103`): flex-ряд, `justify-content:center`, gap 18, з'єднувачі `li::before/after`.
