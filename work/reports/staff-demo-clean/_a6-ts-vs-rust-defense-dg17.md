# Захист позиції «a6 у TS зараз» проти тези власника «одна правда» (Dg17) — для дискусії з критиком

## 1. Теза власника (steelman, його слова)
«Якщо Rust рахує координати, а точки малювання лінків рахуються деінде — вони будуть неправильно розміщені, **не буде однієї правди**.» Тому a6 (зазори між рамками
відділів) він обрав **чекати T126**, і попросив мене захистити варіант «TS зараз». Первинна нотка: «Rust рахує координати нод → логічніше, щоб і точки відображення лінків;
всі розрахунки в одній системі; з DOM — розміри карток, canvas малює свої картки по розмірах DOM для ідентичності».

## 2. Факти (перевірені в коді, `path:line`)
- **Rust у staff-конвеєрі:** одна експортована функція `computeOrgRowTreeLayout` (`packages/core/src/lib.rs:20`). TS кличе її **на кожен орг-блок** (`layout/staff/orgBlockLayout.ts:78`) з **реальними w×h
  карток** (`:63`: «WASM tidy розводить за реальними розмірами карток»). Rust **не знає** про відділи, яруси, обгортки, ребра.
- **TS уже правит вихід Rust:** після Rust корінь перецентровується (`orgBlockLayout.ts:87-102`, «WASM layered-tidy ставить корінь у midpoint…»), відділи пакуються й зсуваються
  (`staffDeptGrouping.ts:94-98`: `x: node.x - bounds.x + region.x`), яруси компонуються й зсуваються (`canvasLayout.ts:80-84,114-118,150-152`). Тобто **«Rust — єдина правда про координати» вже НЕ так сьогодні**:
  фінальні `positionNodes` = Rust + TS-пости.
- **Точки лінків рахуються на РЕНДЕРІ, не в лейауті:** `DiagramRenderer.ts:846-851` бере **фінальні** `canvas.positionNodes`, перетворює їх у ребровий бокс (`mapPositionNodesToStaffEdgeBoxes`),
  застосовує **LOD** (`mapStaffEdgeBoxesForLod(…, options.lod)`) і правило порту (`visualEdgeBox.ts:36-49`: near/mid/far дають різні бокси) → TS `staffEdgeGeometry`. Те саме спільне з SVG-експортом
  (`visualEdgeBox.ts:91` «shared by live render + SVG export»). **Отже точка лінка = f(фінальні бокси, правило порту, LOD)** — залежить від зуму, якого лейаут не знає.
- **Єдина реальна розбіжність «правди» у цьому треку (T125, виміряна):** порт `figma-row` докувався на аватар (`box.x+20`), а картка малювалась на повну ширину (центр `box.x+150`). **Причина — правило порту
  ≠ намальована форма, а не «Rust vs TS».** Лікується оголошенням форми в стилі (`edgePort`, ADR-0002).
- **Справжній подвійний сайт обчислення сьогодні:** межі обгорток. `worldBoundsForTier` — чиста функція (`render/staffZoneBounds.ts:15-110`), але викликається **у рендері** з входами, що йдуть із рендеру:
  `contentPadding` (тема, `DiagramRenderer.ts:712`) і `labelBand` (стан екземпляра `lastZoneLabelBand`, `:722`; коментар `:645-649` визнає, що воно може відрізнятись від `staffOpts.zoneLabelBand`).

## 3. Захист (тези для атаки)
- **З1. «Одна правда» = усі геометричні числа обчислюються ОДИН раз і лише читаються споживачами (рендер, SVG-експорт, тести) — а не «обчислюються в Rust».** Мова шару на це не впливає; важить кількість місць обчислення.
- **З2. Точки лінків не можна «порахувати в Rust при лейауті» без втрати коректності:** вони залежать від LOD і правила порту (рендер-вхід). Щоб Rust їх рахував, треба передавати йому LOD і порт-правила та перераховувати на кожну зміну LOD — це не усуває
  залежності, а переносить її за WASM-межу. Правильна «одна правда» для лінків — **одна TS-функція правила порту**, спільна для live і SVG (вона вже є, `visualEdgeBox.ts`).
- **З3. a6 у TS узгоджується з цим, якщо padding один:** a6 додає `+2×deptPadding` у `staffDeptGrouping.ts` (TS, де вже живе пакування). Захист від двох чисел: padding береться з **того ж джерела**, що рендер рамки, і a4 переносить межі обгорток у вихід лейауту,
  тож рендер лише читає. Тоді лейаут і малювання **не мають окремих копій** padding.
- **З4. Вартість «чекати T126» неспівмірна:** T126 не специфіковано (spec-flow, B1-цикл, content-driven), рішення власника по ньому — «не Rust заради Rust, мета анти-desync». Блокування a6 затримує вимогу №2 нотки на невідомий строк і НЕ купує коректності,
  якщо правило «одне джерело padding» дотримано.
- **З5. T125-тест вимірює вихід, а не реалізацію:** I-T5 (рамки не перетинаються, зазор ≥ очікуваного) лишиться чинним, коли T126 колись перенесе обчислення — переписування a6 тоді дешеве (одна формула).

## 4. Слабкі місця захисту (самокритика, щоб критик не шукав довго)
- **a1 не виміряно:** чи `departmentWrapperPadding` (тема) справді досяжний з лейауту ОДНИМ параметром без перебудови; чи `lastZoneLabelBand` ≡ `zoneLabelBand` — невідомо. Якщо ні — З3 падає й власник правий.
- **Те, що TS уже правит Rust, підтримує і позицію власника:** координати вже розмазані між двома мовами — консолідація в один шар має самостійну цінність (детермінізм, відтворюваність, перф на 1M-вікнах), яку мій захист не зважує.
- **З2 стосується точок лінків, а не координат вузлів/відступів:** вимога власника про Rust-відступи (не лише лінки) захистом не покрита повністю.
- **«Переписати a6 пізніше дешево» — припущення**, не виміряне; T126 може змінити контракт меж так, що a4 теж переробляється.

## 5. Питання до критика
Атакуй захист і **steelman-ь власника**. Знайди в коді конкретні місця, де: (1) точка лінка/бокс обчислюється з координат, що розходяться з намальованими (окрім T125); (2) TS-пост-крок змінює вихід Rust так, що споживач бачить стару копію;
(3) padding/відступ береться з двох джерел. Оціни реальну ціну «Rust рахує відступи й якорі». Дай **вердикт по a6**: TS-зараз (умовно/безумовно) чи чекати T126 — з доказом.
