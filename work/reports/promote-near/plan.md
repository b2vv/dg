## 1. Розміщення

За `## Розміщення` маніфесту — **`packages/sdk`**. Rust не чіпається, межа WASM↔TS не рухається,
контракт `main ↔ worker` не змінюється.

| Файл | Що робимо |
|---|---|
| `packages/sdk/src/render/promoteMath.ts` | новий режим у `resolvePromoteIds`; сьогодні він віддає **одну** ноду |
| `packages/sdk/src/react/createReactPromoteOverlay.ts` | збір кандидатів для нового режиму |
| `packages/sdk/src/render/promoteTypes.ts` | геометрія картки в `PromoteCandidate` |
| `packages/sdk/src/OrgHierarchyDiagram.ts` | віддати геометрію картки поруч зі світовим боксом |
| `docs/USAGE.md` | новий режим, межа по зуму, що дає слот |
| тести | нижче |

## 2. Reuse-first

### Переюзуємо

| Що | Де | Чому підходить |
|---|---|---|
| Сам оверлей | `createReactPromoteOverlay` | шар, синхронізація з камерою, монтування React — усе вже є |
| Кулінг | `screenRectInView(rect, screen, pad = 32)` | вже написаний і вже викликається в `sync()` |
| Перелік кандидатів | `listPromoteCandidates()` **без аргументів** | уже віддає **всіх** зі світовими боксами |
| Поріг | `diagram.getLodLevel()` → `'near'` | рішення GATE 1: дублюємо LOD, окремої константи не заводимо |
| Ховання в Pixi | `setPromotedNodeIds` | піднята нода вже зникає з канваса |
| Дані для галуження | `PromoteSlotProps.node` | несе `ref`, сутність, **`entityType`**, `media`/`symbolUrl*` |

### Нове

| Що | Чому існуюче не підійшло |
|---|---|
| Режим `'near-visible'` | `resolvePromoteIds` сьогодні повертає **рівно одну** ноду — виділену (`promoteMath.ts:96-104`); `maxCount` там мертвий, бо масив завжди з одного елемента |
| Геометрія картки в слоті | Хост, який хоче «заповнити всю ноду» (`padding: 0`), має знати радіус скруглення й внутрішні відступи, якими малює Pixi. Зі `screenRect` він їх лише вгадує, і краї не збігатимуться |
| `maxPromoted` стає живим | Дефолт — **без стелі** (рішення GATE 1: межа по зуму). Але важіль має працювати для хоста, який знає своє залізо |

### Свідомо НЕ робимо — і це виміряно, а не вирішено на смак

| Що не робимо | Чому |
|---|---|
| **Дебаунс перерахунку під час жесту** | Стенд на 44 картки: рух коштує **8.2–8.9 мс** проти бази «тільки канвас» 8.3 мс — тобто в межах шуму, і з GPU, і без. Дебаунс лікував би те, чого нема |
| **CSS-трансформ усього шару** | Те саме вимірювання: виграшу нуль. Перша моя цифра (21 мс) виявилась артефактом `will-change: transform` у стенді |
| **Зближення стилів DOM ↔ канвас** | Поза скоупом за GATE 1. Стало можливим саме тому, що перемикання «канвас↔DOM» на кожному жесті **не буде** |

⚠️ **Межа цього виміру:** стенд не моделює **React-реконсиляцію** 44 компонентів на кожен sync —
а це найімовірніша справжня ціна. Тому дебаунс не викреслено назавжди: він повертається,
якщо приймальний рядок 6 дасть погане число.

## 3. Кроки

**К1. Режим `'near-visible'`.** `resolvePromoteIds` для нього повертає id **усіх** кандидатів,
коли `lod === 'near'`, і порожньо інакше. Дефолтний режим **не змінюється** — існуючі хости
працюють як раніше.
*Готово:* unit — на `near` віддає всіх, на `mid`/`far` порожньо, без стелі за замовчуванням.

**К2. Кандидатів бере оверлей, не резолвер.** `resolvePromoteIds` не знає списку кандидатів —
у нього на вході лише `selection`. Тому для нового режиму `sync()` бере
`listPromoteCandidates()` і фільтрує наявним `screenRectInView`.
*Готово:* unit — поза екраном нічого не піднімається; на екрані піднімається все.

**К3. `maxPromoted` починає працювати.** Дефолт — `undefined` (без стелі). Коли заданий і
кандидатів більше — лишаємо найближчих до центру екрана.
*Готово:* unit — при ліміті 5 з 44 лишається 5, і саме центральні.

**К4. Геометрія картки в слоті.** `PromoteCandidate`/`PromoteSlotProps` несуть радіус скруглення
й внутрішні відступи картки поруч зі світовим боксом.
*Готово:* e2e — DOM-картка з `padding: 0` збігається з канвасною по краях.

**К5. Демо вмикає режим** і показує три способи вмісту з прикладу користувача: зображення
`cover` на всю ноду, `contain` по центру, текстовий фолбек — галуження за `entityType`.
*Готово:* видно на вкладці; знімок у звіті.

**К6. Вимір ціни.** Кадр у спокої з повним шаром (44 картки, FullHD, **без GPU**).
*Готово:* число у звіті; **гірше 30 fps не проходить** (критерій 6 спеки).

**К7. `docs/USAGE.md`.** Режим, межа по зуму, що саме дає слот, і чесно: SVG/PNG/PDF лишаються
Pixi-only — піднята оболонка в растр не потрапляє.
*Готово:* зміна публічного API і доку — **одним комітом** (конституція).

## 4. Сайд-ефекти

1. **Канвас отримує 44 дірки.** Піднята нода ховається в Pixi. Якщо компонент хоста кине помилку,
   користувач побачить порожні місця замість карток. К5 має показати, що робиться при падінні
   компонента; як мінімум — це має бути видно, а не тихо.
2. **Черга монтувань на порозі.** Перетин 1.2 туди-сюди монтує й розмонтовує 44 React-компоненти.
   Стенд каже, що побудова 44 карток ~1 мс, але React там не було.
3. **Дефолт не змінюється.** Новий режим — опційний; хости на `'near-selection'` не помічають нічого.

## 5. План міграції

Міграції даних немає. Хост вмикає режим одним рядком; нічого не ламається, якщо не вмикати.

| Крок | Дія |
|---|---|
| 1 | Гілка `cursor/promote-near-dom`, PR у `main` |
| 2 | К1–К7 по черзі, тест перед кодом |
| 3 | `npm run test:verify` + вимір К6 у контейнері без GPU |
| 4 | CI на PR |

## 6. Rollback

| Що | Як |
|---|---|
| Поведінка | хост прибирає режим — повертається `'near-selection'`, **без релізу з нашого боку** |
| Код | revert PR; режим зникає, дефолт і так не змінювався |

Незворотного немає: ні міграції даних, ні зовнішніх ефектів, ні записаного стану.

## 7. Конституція (за `## Конституція` маніфесту)

| Рядок | Як виконано |
|---|---|
| Тести перед кодом, success **і** failure | кожен крок має тест; failure-кейси: компонент хоста кинув помилку (К5), ліміт менший за кількість кандидатів (К3), `mid`/`far` (К1) |
| KISS над рештою | дебаунс і трансформ шару **викинуті за вимірами**, а не додані «про запас» |

| Межа WASM ↔ TS | **не зачіпається** |
| Публічний API не змінюється мовчки | К7: `docs/USAGE.md` тим самим комітом |
| Pocock — тільки TS | застосовно: режим як юніон, `satisfies` замість `as` |

## 9. Межі плану

- **React не заміряний.** Усі числа — зі стенда на статичних DOM-картках. Реальна ціна може бути
  іншою, і саме К6 має це показати.
- **Вміст хоста не наш.** Chart.js чи d3 — обидва проходять бюджет (побудова 44 чартів ~1 мс);
  вибір за API та вагою бандла, не за швидкістю.
- **Стеля контекстів.** 44 канвасні чарти = 44 2D-контексти. На цьому масштабі норм; якщо поріг
  колись опустять і карток стане 200+, SVG безпечніший.
