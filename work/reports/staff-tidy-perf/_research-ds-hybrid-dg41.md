**Джерело:** `packages/core/src/staff_tidy_layout.rs` @ `0a2b1a8` + незакомічені S1 cfg(test) зміни (продакшн-частина ідентична HEAD).

## Принцип вибору (гібрид)
| Патерн доступу | Структура | Чому |
|---|---|---|
| Щільний цілочисельний ключ, гарячий цикл | **щільний `Vec`** (+ generation-штамп замість очищення) | O(1) без хешування, cache-friendly |
| Розріджений цілочисельний ключ, переважно «промахи» | **гібрид: щільний лічильник/бітсет спереду + `HashMap` позаду** | промах відсікається O(1) без хешу; точний мультисет лише на рідких влучаннях |
| Діапазонні/впорядковані запити («що в [a,b]»), дані змінюються під час обходу | **`BTreeSet`/`BTreeMap`** (бінарне дерево) | range-запит O(log n + k) |
| Діапазонні запити по **статичних** даних | **відсортований `Vec` + бінарний пошук** | те саме, що дерево, але щільніше в пам'яті |
| Точний пошук по вже відсортованих ключах | **бінарний пошук по наявному відсортованому `Vec`** | не потрібна окрема структура |
| Холодний код (layout, 0.6 ms) | лишити `HashMap` | оптимізувати нема що |
| Рядкові ключі в гарячому циклі | **інтернувати в `u32` один раз** | порівняння рядків → порівняння чисел |

Хешер: std `HashMap` = SipHash (захищений від DoS, повільний). Для цілих ключів, що лишаться (D-групування, G-бекенд), можна
свій ~20-рядковий FxHash-подібний `BuildHasher` у крейті — **без нової залежності**. Безпечно для виходу лише якщо ніде
порядок ітерації `HashMap` не впливає на результат; на зараз так (`cards` ітерується лише для лічильників/множини,
`build_grid` сортує за id) — golden це стереже.

## Чого гібриди НЕ вирішать
Реалістична сцена: 42.7 М pops за 23.7 с ≈ 1.8 М pops/с. Сайти F/G/H знижують **ціну pop** (оцінка 3–8×), A/C/D — ціну
решітки й перевірок якості. Це **необхідно, але не достатньо**: секунди, а не ≤50 ms. Кількість pops зменшують лише
зміни постановки (коридори, локальність, пучки — рішення власника).

## Новий ідентичний важіль, вартий виміру
82 cap-пошуки ≈ 20.5 М pops (≈48%). Коли пошук не вдається (cap АБО вичерпання), `astar` повертає той самий
`simp(fallback())` (`:957`). Отже, якщо **дешево довести недосяжність заздалегідь**, вихід лишається байт-ідентичним.
Кандидат: перевірка кінців — старт мусить піти вниз (`dir==0 ⇒ dj==1`, `:894`), ціль приймається лише з напрямком 2
вертикально вниз (`:883,897`). Якщо відповідний сегмент біля старту/цілі неприйнятний (`seg_usable == false`), шляху
немає → fallback одразу, O(1). **Невідомо**, скільки з 82 cap-ів саме такі — потрібен вимір (без зміни коду).
