# ROADMAP — розширюваність і полиск SDK (чернетка дискусії)

**Статус:** чернетка дискусії (2026-11-02) · гілка `feat/sdk-host-geometry-seam` · НЕ план, НЕ таски.
**Мета доку:** зібрати «дуже багато покращень» у структурований реєстр із архітектурним стрижнем,
щоб потім перетворити на spec-flow/таски в правильному порядку. Заповнюється по ходу дискусії.

## Стрижень (теза)

Перетворити SDK з «рендерера діаграми» на **розширюваний фреймворк рендеру над геометрією з ядра**:
хост підключає *презентацію* (React-компоненти зблизька, Pixi-view-фабрики здалеку) і керує
*ефектами* (hover/click/search), а поведінка однакова по обидва боки LOD.

**Інваріант, що тримає все купи (Б2, узагальнений):**
> Геометрія + layout + логіка взаємодії лишаються в ядрі (Rust / спільний TS). Назовні віддається
> тільки **презентація й стилізація ефектів** — ніколи обчислення.

## Північна зірка — ПРОСТІШЕ за GoJS (наскрізний стандарт якості)

Головна мета власника (2026-11-02): API має бути **простішим і інтуїтивнішим за GoJS**, із гарними
композиціями та легким для DI/SOLID-обгорток. Кожен R/D-пункт проходить гейт: «це простіше за GoJS?».

| Біль GoJS | Наш контр-принцип (тенет) |
|---|---|
| `$`/`GraphObject.make` — стрингова DSL-вежа вкладених білдерів | **Звичайні типізовані функції/компоненти**, композуються кодом (map/HOC/обгортки), не DSL |
| `new go.Binding("prop","field")` — стрингові рантайм-біндінги | **Чисті функції `(node,ctx)=>view`** — типобезпечні, юніт-тестовані |
| Монолітні templates (layout+стиль+поведінка разом) | **SOLID-розділення:** геометрія/layout→ядро; візуал→інжектований view; взаємодія→store |
| Окрема мутабельна `GraphLinksModel`, що воює зі стейтом фреймворку | **Immutable дані входом, події виходом**; хост володіє даними (свій store/DI) — Б2 вже так |
| Глобальний diagram із сотнями мутабельних проперті | **DI через параметри-фабрики** (constructor injection), без глобальних синглтонів/реєстрів |
| Важко обгорнути в React/DI (imperative DOM, two-way binding) | **Фреймворк-агностичне ядро + тонкі React-біндінги**; сервіси/компоненти хоста ззовні |

**Суть:** логіка — чисті функції; презентація — інжектовані компоненти/view; дані — immutable входом;
жодних стрингових DSL і глобальних мутацій. Саме це робить композиції, DI й SOLID-обгортки природними.

## Наскрізний камінь спотикання — межа LOD (React ↔ Pixi)

Зблизька малює React (DOM), здалеку — Pixi (canvas). Дві технології → два моделі компонента, два
шляхи hit-test, дві реалізації ефектів. **Консистентність через цю межу** — найважче в усіх пунктах.
Наслідок для дизайну: стан (selection / hover / highlight / found) має бути **центральним**, а шари —
його підписниками; інакше кожна фіча реалізується двічі й розходиться.

### R1 — Паритет взаємодії в Pixi (hover/click/search highlight)
- **Поточне:** click/select — обидва; search (`setFoundFocus`) + subordination (`highlightPath`) —
  вже й у Pixi; **hover-related — лише React near** (DOM `installStaffHoverHighlight`).
- **Справжня робота:** (а) hit-test hover у Pixi (pointermove → нода → `relatedStaffIds` (чиста,
  готова) → repaint акценту ноди+ліній); (б) **єдиний interaction-store** (hovered/highlighted/found),
  з якого рендерять обидва шари, щоб перехід через LOD не губив стан і не дублював логіку.
- **Рішення D1:** винести hover/highlight у центральний store (як selection) — **фундамент для R2/R3**.
- **Залежності:** нема; розблоковує решту. Кандидат №1 за порядком.

### D3-деталь — transition-шар (дискусія 2026-11-02)

**Reframe:** TransitionController сидить МІЖ геометрією і шарами; шари малюють «поточний кадр»
контролера (позиції+opacity+phase по id), не сиру геометрію. Коли анімації нема — кадр==target
(passthrough). Це вирішує «привидів на exit» (контролер тримає exit-ноди понад дані до кінця fade)
і дає одне джерело «що малювати зараз».

**Spring-модель (рішення власника):** per-канал аніматор за інтерфейсом `advance(dt)→{value,settled}`,
дві реалізації — `SpringAnimator { value, velocity, target }` (дефолт) і `TweenAnimator
{ from, target, elapsed, easing, duration }` (сиблінг). **Не «tween ⊂ spring»** — довільну криву/точну
тривалість spring не відтворює; це два сиблінги за одним інтерфейсом. Spring дефолт з ОДНІЄЇ справжньої
причини — **retarget безкоштовний** (міняємо target, velocity переноситься → без ривка), що дає живість
при постійному перенацілюванні (live-фільтр/collapse). **Застереження (виправлення 2026-11-02):** це
НЕ «бо так у React Flow» — RF spring-ядра переходів НЕ має (див. контраст нижче); обґрунтування spring
стоїть незалежно від RF. «Як у RF» було б кроком назад (tween-камера + миттєві ноди + дешеві ребра).

**Канали:** x, y, (w, h), opacity. Дискретне (текст/лічильники/колір) НЕ пружинить — snap на rebuild.

**Дві пастки:** (A) **fixed-timestep accumulator** — змінний dt робить spring frame-rate-залежним і
вибухає на великому dt (фон-таб); годинник інжектований → детерміновано в тестах. (B) **settle = поріг
rest** (|Δ|<ε, |v|<ε), не фіксований час; під штормом ретаргету — **debounce + max-time cap**.

**Re-route ліній на settle — рішення власника: (A) + max-time cap** (один дорогий A*-re-route на
rest-threshold; cap рятує від «ніколи»). Під час руху — твін кінцівок.

**Контраст із React Flow (звірено зі знанням, не з механізмом RF):** у RF НЕМА spring-ядра переходів
layout. RF: камера = d3-tween (duration/easing); рух нод = миттєвий/DIY (CSS/react-spring/d3-timer);
ребра = дешеві derived-криві (bezier/step), перераховуються щорендеру — **тому в RF немає settle/re-route
взагалі**. Наша settle-машинерія існує ТОМУ ЩО ми робимо дороге A*-роутування; RF обходить проблему,
не розвʼязує. Ми йдемо далі за RF (first-class spring-переходи + A* + Pixi-масштаб).
**A* — підтверджено як вимога (власник 2026-11-02): потрібен для гарного рендеру лінків.** Отже
settle/catch-up/(A)+cap машинерія виправдана — це ціна A*, яку свідомо платимо.
→ **«cheap edge mode»** (пряма/bezier без A*) опущено з кандидата-ядра до *опціонального вторинного*
(settle там зникає, як у RF) — не основний шлях. Для tween-сиблінга — d3-ease.

**Ергономіка spring-конфігу (під північну зірку):** один декларативний проп `animate` з прогресивним
розкриттям: `boolean | 'smooth'|'snappy'|'gentle'|'instant' (пресети) | {stiffness,damping,mass} |
{duration,easing} | {enter?,update?,exit?}`. Дискримінація за формою (є stiffness→spring, є
duration→tween). 90% = `animate:true`. DI через easing-функцію, не DSL. Per-phase у публічному API,
per-channel — внутрішньо (position=spring, opacity=tween).

**Хореографія enter/exit:** дефолт — opacity 0→1 + scale 0.9→1 in place (opacity=tween, position=spring).
Опційний полиск (не дефолт): origin-from-parent (діти «виростають»/«всмоктуються» в батька при
expand/collapse) + stagger (`stagger?: number | (node)=>delay`). Контролеру — опційні origin/destination
хуки на enter/exit (дефолт in-place).

#### Поглиблення spring-машинерії (2026-11-02, звірено з кодом packages/sdk/src/)

Звірка існуючих seam-ів (щоб контролер стояв на реальному коді, не в вакуумі):

- **Годинник уже є патерном.** `Viewport.animateTo` (Viewport.ts:173-244) — ручний RAF-tween
  (lerp + `easeOutCubic`, деф 280ms) з **інжектованим годинником** `{now, requestFrame, cancelFrame}`
  (Viewport.ts:16-23). `runPointMorph` (contourMorph.ts:116-131) — той самий патерн. **Spring-ядра
  немає ніде** (підтверджує контраст із RF — його нема й у нас, тому це справді нова машинерія).
  → **Рішення:** контролер бере ТОЙ САМИЙ інтерфейс `{now, requestFrame, cancelFrame}` — детермінований
  тест безкоштовний (прецедент `Viewport.test.ts`, `contourMorph` тести).
- **Пейнт on-demand (маніфест коду).** `autoStart:false` + `ticker.stop()`, «a diagram nobody is
  touching must cost nothing» (PixiHost.ts:297-298); `requestPaint()` коалесить у 1 RAF (PixiHost.ts:260-268).
  → **Рішення:** контролер кличе `requestPaint()` щокадру свого життя і **зупиняється на settle** — інакше
  втрачається «0 cost idle». Жодного безперервного RAF-loop; RAF живе лише поки є незасетлені аніматори.
- **dt-акумулятора НЕМАЄ.** Обидва наявні tween рахують `elapsed = now()-start` щокадру (ок для bounded
  tween, НЕ для spring — spring frame-rate-залежний і вибухає на великому dt). → **Рішення (пастка A):**
  fixed-timestep accumulator — **справді нова** частина; `dt = 1/60`, кламп акумулятора (напр. ≤0.1s → ≤6
  кроків/кадр, решту snap) закриває «фон-таб вибух» конкретним числом.
- **Камера і ноди — один годинник НЕ потрібен (ревізія).** Пейнт-коалесер (1 RAF) уже є точкою зведення:
  камера (свій tween, без змін) і spring-контролер (свій accumulator-loop) **незалежно** кличуть
  `requestPaint` → один `app.render()`. Простіше, ніж уніфікувати годинники.
- **Node identity є, D3-diff — ні.** `SceneRegistry` все id-keyed (`nodeEntityKey(kind,id)` = `person:p1`,
  SceneRegistry.ts:54), АЛЕ реєстр **clear-иться й перебудовується щокадру** (promote-set навмисно
  переживає). Формального enter/update/exit diff **немає**. → **Рішення:** контролер — **єдиний компонент,
  що тримає персистентний keyed-стан аніматорів МІЖ rebuild-ами** (решта rebuild-иться). Саме тому він
  володіє exit-привидами: diff keyset prev↔new по `kind:id`; новий→enter, зниклий→exit (тримає до fade),
  спільний→retarget.

**Node-події як побічний продукт D3-diff — ВИРІШЕНО (owner 2026-11-05, варіант C).** Хост
(`cassiopeia-admin-ui`) атомарних мутацій нод НЕ шле: SDK отримує лише повний знімок через `setData`, а
правки хост реплеїть у себе (стек жестів, host ADR-0067). Тому окреме API `addNode/removeNode/updateNode` —
YAGNI (варіант B відкинуто). Натомість SDK **сам** віддає події «додано / прибрано / змінено» за `kind:id`,
обчислені з різниці попереднього й нового знімка — **тим самим** diff-ом keyset, що вже потрібен
D3-контролеру (див. «Node identity є, D3-diff — ні» нижче). Одна дифузія, дві користі: переходи й події.
Не будувати окремо до D3. **Revisit-тригер:** хост переходить зі знімків на атомарні правки — тоді
повертатись до варіанта B. Джерело: аудит межі `work/reports/library-boundary-audit/_wip-review.md`.

**Форма «кадру» (вихід контролера):** `Map<id, { x, y, w, h, scale, opacity, phase }>`,
`phase ∈ {entering, updating, exiting, idle}`. Джерело підтверджено: `buildStaffChromeGeometry` уже годує
І Pixi, І React near-view (staffChromeGeometry.ts:65) — контролер інтерполює бокси ДО цього споживача,
обидва шари читають інтерпольований кадр однаково. Views — чисті painter-и, «the view never re-routes»
(StaffEdgesView.ts:55-56), тож інтерполяція не ламає їхній контракт.

**Канали й аніматори (уточнено):** position(x,y)=**spring**; `opacity`=**tween** (spring овершутить <0/>1 —
брудна alpha); `scale` (enter 0.9→1)=spring. **🔴 Розвилка 4 — w/h:** spring (плавна зміна box при
collapse/expand, але per-frame reflow тексту) vs **snap** (розмір стрибає, дешевше). **ВИРІШЕНО (owner):
SNAP w/h** (пружинить лише position + scale-enter) — зміна тексту й так дискретна, scale дає живість enter
без reflow. **Revisit-тригер:** якщо snap-resize читається надто різко / треба плавна зміна контейнера →
повернутись до spring w/h (не «назавжди»).

**🔴 Розвилка 6 — числа debounce/cap:** reroute-debounce (тиша перед дорогим A*, напр. 120ms) + max-time
cap (форс reroute якщо не settle, напр. 2s). Санні дефолти, але owner-go на конкретні числа.

**🔴 Розвилка 7 — spring-пресети.** Під північну зірку: рядки для 90% (`'smooth'|'snappy'|'gentle'|
'instant'`) + об'єкт для power-user. Під-розвилка: виражати як сирі `{stiffness,damping,mass}` (фізика,
як react-spring) чи перцептивні `{duration, bounce}` (Framer Motion — інтуїтивніше, ближче до північної
зірки). **ВИРІШЕНО (owner): ОБИДВІ форми (discriminated union)** — API приймає і `{duration,bounce}`, і
`{stiffness,damping,mass}`; дискримінація за формою (є `bounce`/`duration`→перцептивно, є `stiffness`→
фізика) + рядки-пресети. Дефолт-пресети мапляться у перцептивну форму: instant=0 · gentle={0.6s,0.15} ·
**smooth(деф)={0.4s,0.1}** · snappy={0.25s,0.25}. Числа фіналізувати емпірично.

**🔴 Розвилка 8 — stagger.** `stagger?: number | (node)=>delay`. Порядок «наступності»: по глибині дерева,
по sibling-index, чи DFS? **ВИРІШЕНО (owner): ripple від джерела зміни** — брижі по graph-distance від
розгорнутої ноди/фільтр-матчу; fallback глибина для bulk-load без джерела. Привʼязує рух до дії юзера.
Застосування: enter — прямий порядок, exit — реверс. Delay = аніматор тримає origin до delay. (Доказово
підкріплено — див. «Гарні лінії» P6: staggering, привʼязаний до семантики зміни, покращує трекінг.)

### R2 — React-шар до рівня React Flow DX + зовнішні компоненти
- **Поточне:** зовнішній `component`/`backdrop` уже є (promote-overlay).
- **Уточнити:** «як React Flow» ≠ «все в DOM» — це **категорійна помилка** для нашого масштабу
  (React Flow тримає всі ноди в DOM; наша ставка — Rust-геометрія + Pixi для тисяч нод). Отже
  паритет = React-Flow-рівень **DX/плавності для near-зрізу**, не «весь граф у React».
- **Справжня робота:** (а) багатший контракт інжекції (більше слотів/хуків/типізованих props);
  (б) **анімація переходів layout** — ноди плавно їдуть у нові позиції при зміні даних (нове, велике).
- **Рішення D3 (анімації):** хто інтерполює? Ядро дає old+new геометрію, TS твінить? Окремий підпроєкт.

### R3 — Pixi: зовнішні view-фабрики побудови + плавність
- **Пастка:** Pixi — не React, туди не передаси React-компонент. Але передаси `DisplayObject` або
  функцію, що його будує (ідея власника 2026-11-02).
- **Механізм — два рівні того самого шва:**
  1. Простий: `(node, ctx) => DisplayObject` — повертає `Graphics`/`Container` з даних ноди + контексту.
  2. Масштабований (retained, як наші внутрішні view + React-reconciliation):
     ```ts
     createNodeView(node, ctx): { root: Container; update(node, ctx): void; destroy(): void }
     ```
     SDK пулить за id і кличе `update` замість перестворення — інакше перф-обрив на тисячах нод
     (рівно те, чому Pixi тримає retained-обʼєкти, а React робить reconciliation, не re-mount).
  Внутрішні `StaffPersonView`/`OrgEdgesView` — уже retained-view; винести як публічну фабрику = шов R3.
- **Два інваріанти (бережуть Б2-принцип):** (а) хост повертає візуал у **локальних** координатах;
  **розміщення/трансформ робить SDK** з геометрії ядра — хост не рахує позицій. (б) тип повернення —
  `DisplayObject`/`Container` (загальніший за `Graphics`: graphics+text+sprite компонуються).

### R4 — Зум: колесо + кнопка (дискусія + web-дослідження + ux-review, 2026-11-02)

**Поточне (Viewport.ts):** ctrl/⌘+wheel → зум до курсора (trackpad-pinch теж); shift+wheel →
горизонт-пан; просте колесо → вертик-пан; кнопка `zoomBy` → центр, БЕЗ анімації; нема клавіатурного
зуму; кламп 0.15–4.

**Дослідження (джерела в сесії):** консенсусу «колесо=зум» vs «модифікатор» НЕМА (розкол за
аудиторією) → **конфіг, не хардкод**. yFiles: дефолт колесо=зум, Ctrl=вертик-пан, Shift=горизонт-пан,
конфігуровно. Зум-до-курсора — норма; IN і OUT однаково (баг Obsidian: in=курсор/out=центр). Pinch=ctrl+wheel
(W3C). Mapbox: ctrl→Meta на Mac через конфлікт. A11y: модифікатор сам по собі не a11y-win.

**UX-ревʼю — ранжовані ризики (3 обовʼязкові незалежно від дефолту):**
1. **Mac ctrl+wheel ↔ системний accessibility-зум (ctrl+scroll)** — колізія. Фікс: на Mac пріоритет **⌘(meta)**.
2. **SDK ковтає shift/жести (preventDefault) → ламає shift-івент хоста.** Фікс: мапа жестів із **opt-out**.
3. **Дискаверабіліті модифікатора** (юзер не знає про ctrl). Фікс: hint-оверлей (Google-Maps-стиль) + видимі кнопки +/−.
4. Дефолт проти GoJS-памʼяті (Jakob's Law) → для dg-swap дефолт `wheelBehavior:'zoom'`.
5. A11y: нема клавіатурного зуму (`Ctrl +/−`) + кнопки мають бути фокусовні. (major, не blocker — кнопкова альт.)
6. Кнопка-зум без анімації → анімувати через `animateTo`. (minor)
**OK:** зум-до-курсора IN/OUT консистентний ✅; pinch ✅; кнопка-до-центру ✅; кламп ✅.

**Рішення (дизайн):** `wheel: { behavior: 'zoom-modifier'(деф) | 'zoom' | 'pan',
gestures: { zoom:'ctrl'|'meta'|'none', panHorizontal: false(деф) | 'shift', … } }` (opt-out) + Mac→meta +
hint + клавіатурний зум + анімована кнопка.

**ВИПРАВЛЕННЯ (легенда порталу, 2026-11-02):** портал показує «Ctrl+скрол — зміна масштабу» + «Shift-клік
або рамка — мультивибір». Отже: (а) дефолт для цього хоста = **`zoom-modifier`** (портал УЖЕ модифікаторний,
натренував на Ctrl) — попередня здогадка «dg-swap→'zoom'» знята; (б) **Shift належить ВИБОРУ, не wheel-пану**
→ `panHorizontal` дефолт **false** (не shift), opt-out лишає Shift хосту; (в) легенда порталу = та сама
discoverability-афорданс (MAJOR 3) — SDK має давати СТАБІЛЬНИЙ контракт жестів, щоб легенда не брехала.

### R11 — Правила взаємодії ліній з обгортками (owner додав 2026-11-02)

**Owner-рішення:** усі прямокутні обгортки (grid-collapsed сиблінги T113, ШПС staff-chrome Б2,
груп/департамент-контейнери, будь-який node-box) трактуються **уніфіковано** як obstacle-регіони для
роутера. Не спецкейси по типу — один список перешкод.

**Grounded:** obstacles у коді ВЖЕ = кожна картка на canvas (staffEdgeGeometry.ts:334-335) + `frames`/
`zones` у вході роутера (staffRouterV2.ts `StaffRoutingInput`). Тож «обгортки як перешкоди» = **розширення
того самого списку** прямокутниками обгорток, частково вже є через `frames` (StaffFrameBox).

**Декомпозиція (рекомендації):**
- **(a) Obstacle-модель:** кожна обгортка → прямокутник у множину перешкод, нарівні з node-box. Один
  плоский список; routing лишається в Rust-ядрі (інваріант тримається).
- **(b) Докінг кінцівок:** endpoint = нода АБО обгортка. До expanded-ноди — edgePort як зараз (ADR-0002,
  avatar-dock). До **collapsed-grid** — док до **краю обгортки** (ноди всередині не адресуються, поки
  згорнуті). Edge-port на прямокутнику обгортки.
- **(c) Clearance:** перешкоди роздуваються на маржу (`shapeBufferDistance`-аналог — індустрійна норма,
  libavoid/JointJS) — коридор, щоб лінії не терлись об борт. Одна константа (**F11.2**).
- **(d) Self-exclusion (коректність):** власні кінцівки лінії та **весь ланцюг предків-обгорток**
  виключаються з перешкод для ЦІЄЇ лінії — інакше лінія зсередини не вийде зі свого контейнера. Класичний
  готч obstacle-routing (**F11.4** — не смак, коректність).
- **(e) Nesting:** обгортки вкладаються (департамент ⊃ grid ⊃ ноди); плоский список обходить вкладеність
  автоматично за умови (d).
- **(f) D3-звʼязок:** під час переходу обгортки анімуються → множина перешкод **часозмінна**. Перешкоди
  **семплюються на settle** (не щокадру), reroute раз на settle проти фінальної геометрії; під час руху —
  твін кінцівок, транзитивний кліп обгорток прийнятний (in-flight).
- **(g) Ядро vs хост:** obstacle-обрахунок + routing = Rust-ядро; хост-surface лише стиль намальованої
  полілінії (колір/товщина/дэш), не шлях. Підтверджує інваріант.

**🔴 Розвилки R11:**
- **F11.1 — ВИРІШЕНО (owner): fan / впорядковані порти** (не бандл). Доказ (Holten HEB): бандлінг зменшує

#### F11.5-поглиблення — інкрементальний роутер (grounded, owner-go на напрям)

**Код:** seam `resolveStaffRouting` (staffRouterV2.ts:53-91) — єдина точка live+SVG. ДВА бек-енди:
Rust/WASM grid-A* (`routing:'astar'`, staffLiveGeometry.ts:352) і TS orthogonal `buildStaffEdgeSegments`
(staffEdgeGeometry.ts:439); оптимізований obstacle-index (sorted + `lowerBound`) — у TS-шляху
(staffEdgeGeometry.ts:357-365); obstacles = всі картки + `frames`.

1. **Affected set = stored-dependents(old) ∪ spatial-hits(new).** Ребро зачеплене якщо (a) кінцівка
   зрушила, (b) перешкода, від якої залежав роут, змінилась, або **(c) перешкода вʼїхала в його коридор**
   на новій позиції — (c) критична для коректності: нову позицію перешкоди тестувати проти bbox УСІХ
   ребер (дешево через sorted index), не лише збережених залежних. Обидва напрями.
2. **Dependency-трекінг** (per-edge обставини останнього роуту) живе в **персистентному стані між
   rebuild-ами = той самий дім, що й D3-контролер** (єдиний, хто переживає rebuild і вже диференціює
   keyset по `kind:id`). → F11.5 чіпляється до D3: контролер віддає роутеру **changeset**, не повну сцену.
3. **Персистентний obstacle-index** (зараз rebuild per call) — живе між викликами, патчиться на зміну.
4. **Fallback на повний reroute** при великому changeset (глобальний релейаут). Інкремент виграє для
   ЛОКАЛЬНИХ правок (drag, collapse гілки, live-фільтр) — саме D3-кейси.
5. **Звʼязок із settle:** на settle changeset = ноди/обгортки з фінальною геометрією ≠ до переходу;
   collapse однієї гілки → жменя ребер. **Ось що робить «один reroute на settle» дешевим.**
   Вартість локальної правки ≈ O(affected_edges × log obstacles).

**Розвилки — ВИРІШЕНО (owner 2026-11-02):** **G1 → просторова over-approximation** (bbox/коридор; зайві
reroute, ніколи хибний роут); **G4 → D3-контролер годує changeset** (одна дифузія, без подвоєння); **G3**
поріг fallback (% зрушених нод) — санний дефолт, тюнити емпірично.

**G2 — ВИРІШЕНО (owner 2026-11-02): спершу КОНСОЛІДАЦІЯ.** Звірка коду спростувала премису «наш роутер»
(однина): у рантаймі **три гілки**, **два Rust-роутери** + TS:
- alpha → Rust **mockup grid-A*** (`route_astar`, staffLiveGeometry.ts:370);
- не-alpha genuine-tree → Rust **`compute_staff_geometry`** (ортогональний, A* opt-in; core staff_router.rs);
- не-alpha matrix/headless → **TS** `buildStaffEdgeSegments`; **SVG export ЗАВЖДИ TS** (svgExport.ts:295).

Вибір — за формою сцени, не WASM-fallback. Rust нині має **нуль персистентності** (pass-through повної сцени
щовиклику, сітка/occ з нуля — lib.rs:87/101, staff_mockup_layout.rs:1176-1253; grep static/thread_local/
once_cell порожній). TS obstacle-index — TS-only, Rust його не бачить. Тож інкремент у Rust = **greenfield
стан-робота** (новий stateful WASM-API), не «підкрутити index». dg31-пам'ять («A* у Rust = рантайм») —
частково стара / про alpha-напрям.

→ **Інкрементальність передбачає ОДИН роутер; код має три. Owner: спершу звести на один Rust-шлях, потім F11.5.**

#### 🔴 Вимір-гейт перед консолідацією — WASM vs TS (owner-питання 2026-11-02)

Власник спитав: чи є виграш рахувати в Rust/WASM проти TS? Звірка репо (докладно — живі ноти):

- **У репо НЕМАЄ виміряної перф-підстави Rust проти TS.** ADR-0002 обрав Rust заради **«одне джерело
  істини / одна система координат»** (усунення розходження координат, 0002:12-13,:24) — correctness/
  архітектура, **не перф**. Рішення — мандат власника (O-9/O-15 «Велика міграція в Rust», 0002:7).
- **Вартість WASM-межі на 1M-вікнах явно НЕ ВИМІРЯНА** (0002:36, T126 R10); дешевший TS-варіант
  відкинуто вольово й **залишено запасним «якщо ціна межі неприйнятна»** (0002:28).
- Знамените «855ms» = TS-баг O(n²), **виправлений у TS** (staffEdgeGeometry.ts:332-338) — доказ за
  TS-оптимізацію, не за Rust.
- Повна сцена серіалізується serde через межу **щовиклику** (lib.rs:86-96) — WASM-несприятливий патерн.
- External: A* favors WASM (1.5–7× numeric kernel) + no-GC jitter-виграш, АЛЕ full-scene marshaling їсть
  виграш. **F11.5 інкремент б'є саме по межі** (малий changeset, стан у linear memory) → важіль, що РОБИТЬ
  Rust-ставку виправданою. Або ні — поки не виміряно.
- Обидві реалізації (layout+routing TS vs Rust) + golden існують, АЛЕ golden порівнює координати, не час;
  **перф-паритет-тесту TS-vs-Rust і criterion-бенчів НЕМАЄ.**

**Наслідок:** консолідація (К4 знести TS) = зняти фолбек, який ADR свідомо тримає, поглибивши **невиміряну**
ставку. **Рекомендація: вимір ПЕРЕД консолідацією** — перф-паритет TS vs Rust (ms на спільному сценарії) +
вартість marshaling на 1M-вікні, з оглядом на F11.5. Харнес є; дешево проти роботи, яку гейтить; це рівно
вимір, що ADR сам називає відсутнім.

**ВИРІШЕНО (owner 2026-11-02): «Міряти, але TS не знімати».** Уточнена консолідація:
- **Вимір-спайк НАЙПЕРШЕ:** перф-паритет TS vs Rust (ms, спільний сценарій) + marshaling на 1M-вікні, з
  оглядом на F11.5. Дешево; гейтить решту; дає дані замість блогів.
- **К1–К3:** Rust = єдиний **активний** роутер (tree+matrix+export); **TS ЗАЛИШАЄТЬСЯ** за перемикачем
  як фолбек. **К4 (видалити TS) ВІДКЛАДЕНО**, гейтиться виміром. TS-фолбек = записаний ADR-0002 відкат.
- **F11.5** чіпляється до активного Rust-роутера; TS-фолбек інкременту не потребує (дормантний escape hatch).
- Премиса «один роутер»: у кодбазі лишаються два, але активний рантайм-шлях один (Rust) — персистентний
  стан живе в ньому, цього достатньо.

**Оновлений порядок:** (1) вимір-спайк → (2) консолідація К1→К2→К3→golden (TS retained, К4 відкладено) →
(3) F11.5 інкремент. **D3 spring-машинерія ортогональна — паралельно будь-коли.**

### D1-деталь — межа interaction vs emphasis (step-back-review 2026-11-02)

Попередня 5-польна `InteractionState` змішувала дві відповідальності — виправлено:

| Зріз | Поля | Власник | Лайфцикл |
|---|---|---|---|
| **Interaction** (що юзер торкає) | `selected`, `hovered` (потім `focused`) | pointer/keyboard | selection може жити |
| **Emphasis** (що акцентовано/приглушено) | `found`, `highlight` | search / команда хоста | `setData` чистить |

- **`found`** — НЕ в interaction-store: результат пошуку, власник — search (вже `setFoundFocus`;
  `setData` чистить). Спільний рендер-наслідок (приглушення) ≠ спільна відповідальність.
- **`highlight`** — emphasis, і здебільшого **похідне**: авто (hover→related) = селектор
  `f(hovered,mode)`, не збережене поле (зберігати похідне = десинк); хост-driven (`highlightPath`)
  = запис у emphasis-бакет.
- **`focused`** — **прибрано зараз** (передчасна абстракція: a11y/keyboard-навігації в коді нема).
  Коли зʼявиться a11y-таска — імовірно окреме поле (фокус≠вибір≠hover), але семантику визначає ВОНА.
- Підсумок: D1-store = `{ selected, hovered }`. Emphasis `{ found, highlight }` — окремий зріз, свій
  власник. Обидва годують рендер (обидва шари підписані), але це два власники, не один блоб.

## Якорі доставки до host — коли можна тягнути код (owner 2026-11-03)

Шар доставки поверх порядку: **відмітки зрілості**, на яких host може тягнути шматок коду.
**Принцип:** host тягне ЛИШЕ на анкері з зеленим гейтом; **між анкерами SDK може бути внутрішньо
неузгоджений** (напів-злитий A*, TS у процесі зняття) — тягнути там заборонено. Кожен анкер береже
Б2-інваріант (геометрія/логіка в ядрі; host споживає вихід/презентацію, не рахує). Анкер = **git-tag +
semver-бамп**, щоб host пінив точку.

| Анкер | Що готово | Host-вплив | Гейт на «тягнути» | semver |
|---|---|---|---|---|
| **A0** | вимір-вердикт WASM vs TS | **НЕ pull** — внутрішнє go/no-go на Rust; no-go → варіант 3 (TS) | вимір-спайк зроблено | — |
| **A1** | консолідація: merge A* + Rust-matrix + Rust-export, TS retained | **тихий pull**, вихід ідентичний (host-перевірка: власний golden/скріншоти незмінні) | golden-паритет зелений + усе за наявним USAGE API | patch |
| **A2** | F11.5 інкремент | **тихий pull**, perf; API не змінюється | incremental-тести + perf-бюджет зелені | patch |
| **A3** | D3 spring + проп `animate` | **опт-ін** — нова публічна поверхня (USAGE.md §нова) | D3-тести + USAGE задокументовано | minor |

**A3 дефолт — ВИРІШЕНО (owner): `animate` opt-in OFF.** Перший pull D3 нічого візуально не змінює (нуль-ризик
регресії host-golden); host вмикає анімації свідомо, коли готовий. (Північна зірка «90%=animate:true»
лишається як ergonomics пропа, але не як дефолт при першому постачанні.)

**A1 — застереження:** design-позиція «тихий pull» тримається, лише якщо golden-паритет підтверджує
ідентичний вихід. Якщо golden покаже зсув — A1 стає **видимим** для host (не тихим), і host мусить
погодити зміну перед pull.

**Прив'язка до порядку:** A0 ⟵ вимір-спайк · A1 ⟵ консолідація К1–К3+golden · A2 ⟵ F11.5 · A3 ⟵ D3.
D3 (A3) ортогональний — може дозріти й постачатись паралельно з A1/A2.
