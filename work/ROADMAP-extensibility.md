# ROADMAP — розширюваність і полиск SDK (чернетка дискусії)

**Статус:** чернетка дискусії (2026-11-02) · гілка `feat/sdk-host-geometry-seam` · НЕ план, НЕ таски.
**Мета доку:** зібрати «дуже багато покращень» у структурований реєстр із архітектурним стрижнем,
щоб потім перетворити на spec-flow/таски в правильному порядку. Заповнюється по ходу дискусії.

---

## Стрижень (теза)

Перетворити SDK з «рендерера діаграми» на **розширюваний фреймворк рендеру над геометрією з ядра**:
хост підключає *презентацію* (React-компоненти зблизька, Pixi-view-фабрики здалеку) і керує
*ефектами* (hover/click/search), а поведінка однакова по обидва боки LOD.

**Інваріант, що тримає все купи (Б2, узагальнений):**
> Геометрія + layout + логіка взаємодії лишаються в ядрі (Rust / спільний TS). Назовні віддається
> тільки **презентація й стилізація ефектів** — ніколи обчислення.

## Північна зірка — ПРОСТІШЕ за GoJS (наскрізний стандарт якості)

Головна мета власника (2026-11-02): API має бути **простішим і інтуїтивнішим за GoJS**, із гарними
композиціями та легким для DI/SOLID-обгорток. Кожен R/D-пункт проходить гейт: «це простіше за GoJS?».

| Біль GoJS | Наш контр-принцип (тенет) |
|---|---|
| `$`/`GraphObject.make` — стрингова DSL-вежа вкладених білдерів | **Звичайні типізовані функції/компоненти**, композуються кодом (map/HOC/обгортки), не DSL |
| `new go.Binding("prop","field")` — стрингові рантайм-біндінги | **Чисті функції `(node,ctx)=>view`** — типобезпечні, юніт-тестовані |
| Монолітні templates (layout+стиль+поведінка разом) | **SOLID-розділення:** геометрія/layout→ядро; візуал→інжектований view; взаємодія→store |
| Окрема мутабельна `GraphLinksModel`, що воює зі стейтом фреймворку | **Immutable дані входом, події виходом**; хост володіє даними (свій store/DI) — Б2 вже так |
| Глобальний diagram із сотнями мутабельних проперті | **DI через параметри-фабрики** (constructor injection), без глобальних синглтонів/реєстрів |
| Важко обгорнути в React/DI (imperative DOM, two-way binding) | **Фреймворк-агностичне ядро + тонкі React-біндінги**; сервіси/компоненти хоста ззовні |

**Суть:** логіка — чисті функції; презентація — інжектовані компоненти/view; дані — immutable входом;
жодних стрингових DSL і глобальних мутацій. Саме це робить композиції, DI й SOLID-обгортки природними.

## Наскрізний камінь спотикання — межа LOD (React ↔ Pixi)

Зблизька малює React (DOM), здалеку — Pixi (canvas). Дві технології → два моделі компонента, два
шляхи hit-test, дві реалізації ефектів. **Консистентність через цю межу** — найважче в усіх пунктах.
Наслідок для дизайну: стан (selection / hover / highlight / found) має бути **центральним**, а шари —
його підписниками; інакше кожна фіча реалізується двічі й розходиться.

## Реєстр покращень

> R1–R3 названі власником 2026-11-02. Решту («дуже багато») дописуємо по ходу — див. «Беклог для заповнення».

### R1 — Паритет взаємодії в Pixi (hover/click/search highlight)
- **Поточне:** click/select — обидва; search (`setFoundFocus`) + subordination (`highlightPath`) —
  вже й у Pixi; **hover-related — лише React near** (DOM `installStaffHoverHighlight`).
- **Справжня робота:** (а) hit-test hover у Pixi (pointermove → нода → `relatedStaffIds` (чиста,
  готова) → repaint акценту ноди+ліній); (б) **єдиний interaction-store** (hovered/highlighted/found),
  з якого рендерять обидва шари, щоб перехід через LOD не губив стан і не дублював логіку.
- **Рішення D1:** винести hover/highlight у центральний store (як selection) — **фундамент для R2/R3**.
- **Залежності:** нема; розблоковує решту. Кандидат №1 за порядком.

### D3-деталь — transition-шар (дискусія 2026-11-02)

**Reframe:** TransitionController сидить МІЖ геометрією і шарами; шари малюють «поточний кадр»
контролера (позиції+opacity+phase по id), не сиру геометрію. Коли анімації нема — кадр==target
(passthrough). Це вирішує «привидів на exit» (контролер тримає exit-ноди понад дані до кінця fade)
і дає одне джерело «що малювати зараз».

**Spring-модель (рішення власника):** per-канал аніматор за інтерфейсом `advance(dt)→{value,settled}`,
дві реалізації — `SpringAnimator { value, velocity, target }` (дефолт) і `TweenAnimator
{ from, target, elapsed, easing, duration }` (сиблінг). **Не «tween ⊂ spring»** — довільну криву/точну
тривалість spring не відтворює; це два сиблінги за одним інтерфейсом. Spring дефолт з ОДНІЄЇ справжньої
причини — **retarget безкоштовний** (міняємо target, velocity переноситься → без ривка), що дає живість
при постійному перенацілюванні (live-фільтр/collapse). **Застереження (виправлення 2026-11-02):** це
НЕ «бо так у React Flow» — RF spring-ядра переходів НЕ має (див. контраст нижче); обґрунтування spring
стоїть незалежно від RF. «Як у RF» було б кроком назад (tween-камера + миттєві ноди + дешеві ребра).

**Канали:** x, y, (w, h), opacity. Дискретне (текст/лічильники/колір) НЕ пружинить — snap на rebuild.

**Дві пастки:** (A) **fixed-timestep accumulator** — змінний dt робить spring frame-rate-залежним і
вибухає на великому dt (фон-таб); годинник інжектований → детерміновано в тестах. (B) **settle = поріг
rest** (|Δ|<ε, |v|<ε), не фіксований час; під штормом ретаргету — **debounce + max-time cap**.

**Re-route ліній на settle — рішення власника: (A) + max-time cap** (один дорогий A*-re-route на
rest-threshold; cap рятує від «ніколи»). Під час руху — твін кінцівок.

**Контраст із React Flow (звірено зі знанням, не з механізмом RF):** у RF НЕМА spring-ядра переходів
layout. RF: камера = d3-tween (duration/easing); рух нод = миттєвий/DIY (CSS/react-spring/d3-timer);
ребра = дешеві derived-криві (bezier/step), перераховуються щорендеру — **тому в RF немає settle/re-route
взагалі**. Наша settle-машинерія існує ТОМУ ЩО ми робимо дороге A*-роутування; RF обходить проблему,
не розвʼязує. Ми йдемо далі за RF (first-class spring-переходи + A* + Pixi-масштаб).
**A* — підтверджено як вимога (власник 2026-11-02): потрібен для гарного рендеру лінків.** Отже
settle/catch-up/(A)+cap машинерія виправдана — це ціна A*, яку свідомо платимо.
→ **«cheap edge mode»** (пряма/bezier без A*) опущено з кандидата-ядра до *опціонального вторинного*
(settle там зникає, як у RF) — не основний шлях. Для tween-сиблінга — d3-ease.

**Ергономіка spring-конфігу (під північну зірку):** один декларативний проп `animate` з прогресивним
розкриттям: `boolean | 'smooth'|'snappy'|'gentle'|'instant' (пресети) | {stiffness,damping,mass} |
{duration,easing} | {enter?,update?,exit?}`. Дискримінація за формою (є stiffness→spring, є
duration→tween). 90% = `animate:true`. DI через easing-функцію, не DSL. Per-phase у публічному API,
per-channel — внутрішньо (position=spring, opacity=tween).

**Хореографія enter/exit:** дефолт — opacity 0→1 + scale 0.9→1 in place (opacity=tween, position=spring).
Опційний полиск (не дефолт): origin-from-parent (діти «виростають»/«всмоктуються» в батька при
expand/collapse) + stagger (`stagger?: number | (node)=>delay`). Контролеру — опційні origin/destination
хуки на enter/exit (дефолт in-place).

### R2 — React-шар до рівня React Flow DX + зовнішні компоненти
- **Поточне:** зовнішній `component`/`backdrop` уже є (promote-overlay).
- **Уточнити:** «як React Flow» ≠ «все в DOM» — це **категорійна помилка** для нашого масштабу
  (React Flow тримає всі ноди в DOM; наша ставка — Rust-геометрія + Pixi для тисяч нод). Отже
  паритет = React-Flow-рівень **DX/плавності для near-зрізу**, не «весь граф у React».
- **Справжня робота:** (а) багатший контракт інжекції (більше слотів/хуків/типізованих props);
  (б) **анімація переходів layout** — ноди плавно їдуть у нові позиції при зміні даних (нове, велике).
- **Рішення D3 (анімації):** хто інтерполює? Ядро дає old+new геометрію, TS твінить? Окремий підпроєкт.

### R3 — Pixi: зовнішні view-фабрики побудови + плавність
- **Пастка:** Pixi — не React, туди не передаси React-компонент. Але передаси `DisplayObject` або
  функцію, що його будує (ідея власника 2026-11-02).
- **Механізм — два рівні того самого шва:**
  1. Простий: `(node, ctx) => DisplayObject` — повертає `Graphics`/`Container` з даних ноди + контексту.
  2. Масштабований (retained, як наші внутрішні view + React-reconciliation):
     ```ts
     createNodeView(node, ctx): { root: Container; update(node, ctx): void; destroy(): void }
     ```
     SDK пулить за id і кличе `update` замість перестворення — інакше перф-обрив на тисячах нод
     (рівно те, чому Pixi тримає retained-обʼєкти, а React робить reconciliation, не re-mount).
  Внутрішні `StaffPersonView`/`OrgEdgesView` — уже retained-view; винести як публічну фабрику = шов R3.
- **Два інваріанти (бережуть Б2-принцип):** (а) хост повертає візуал у **локальних** координатах;
  **розміщення/трансформ робить SDK** з геометрії ядра — хост не рахує позицій. (б) тип повернення —
  `DisplayObject`/`Container` (загальніший за `Graphics`: graphics+text+sprite компонуються).
- **Рішення D2:** свідомо прийняти **дві моделі інжекції** (React-компонент near / Pixi-view-фабрика
  far), природні кожній технології, замість ілюзії однієї. Приймаємо й голу функцію, і фабрику
  create/update/destroy (простота / масштаб) — симетрично React-шару.
- **Плавність:** culling/batching/texture-atlas/коалесинг (частина є) — виміряти перед тюнінгом.

### R4 — Зум: колесо + кнопка (дискусія + web-дослідження + ux-review, 2026-11-02)

**Поточне (Viewport.ts):** ctrl/⌘+wheel → зум до курсора (trackpad-pinch теж); shift+wheel →
горизонт-пан; просте колесо → вертик-пан; кнопка `zoomBy` → центр, БЕЗ анімації; нема клавіатурного
зуму; кламп 0.15–4.

**Дослідження (джерела в сесії):** консенсусу «колесо=зум» vs «модифікатор» НЕМА (розкол за
аудиторією) → **конфіг, не хардкод**. yFiles: дефолт колесо=зум, Ctrl=вертик-пан, Shift=горизонт-пан,
конфігуровно. Зум-до-курсора — норма; IN і OUT однаково (баг Obsidian: in=курсор/out=центр). Pinch=ctrl+wheel
(W3C). Mapbox: ctrl→Meta на Mac через конфлікт. A11y: модифікатор сам по собі не a11y-win.

**UX-ревʼю — ранжовані ризики (3 обовʼязкові незалежно від дефолту):**
1. **Mac ctrl+wheel ↔ системний accessibility-зум (ctrl+scroll)** — колізія. Фікс: на Mac пріоритет **⌘(meta)**.
2. **SDK ковтає shift/жести (preventDefault) → ламає shift-івент хоста.** Фікс: мапа жестів із **opt-out**.
3. **Дискаверабіліті модифікатора** (юзер не знає про ctrl). Фікс: hint-оверлей (Google-Maps-стиль) + видимі кнопки +/−.
4. Дефолт проти GoJS-памʼяті (Jakob's Law) → для dg-swap дефолт `wheelBehavior:'zoom'`.
5. A11y: нема клавіатурного зуму (`Ctrl +/−`) + кнопки мають бути фокусовні. (major, не blocker — кнопкова альт.)
6. Кнопка-зум без анімації → анімувати через `animateTo`. (minor)
**OK:** зум-до-курсора IN/OUT консистентний ✅; pinch ✅; кнопка-до-центру ✅; кламп ✅.

**Рішення (дизайн):** `wheel: { behavior: 'zoom-modifier'(деф) | 'zoom' | 'pan',
gestures: { zoom:'ctrl'|'meta'|'none', panHorizontal: false(деф) | 'shift', … } }` (opt-out) + Mac→meta +
hint + клавіатурний зум + анімована кнопка.

**ВИПРАВЛЕННЯ (легенда порталу, 2026-11-02):** портал показує «Ctrl+скрол — зміна масштабу» + «Shift-клік
або рамка — мультивибір». Отже: (а) дефолт для цього хоста = **`zoom-modifier`** (портал УЖЕ модифікаторний,
натренував на Ctrl) — попередня здогадка «dg-swap→'zoom'» знята; (б) **Shift належить ВИБОРУ, не wheel-пану**
→ `panHorizontal` дефолт **false** (не shift), opt-out лишає Shift хосту; (в) легенда порталу = та сама
discoverability-афорданс (MAJOR 3) — SDK має давати СТАБІЛЬНИЙ контракт жестів, щоб легенда не брехала.

### R5 — Мультивибір (shift-клік + marquee) — під D1/селекція
З легенди порталу: Shift = мультивибір. **shift-клік** → toggle у `selected:Set<id>` (selectionStore є);
**рамка (rubber-band)** → ноди, чий **box** перетинає прямокутник, hit-test **за геометрією ядра** (принцип

північну зірку: виділення — чиста логіка в ядрі, презентація гумки — інжектована.

- **D3 — анімаційна машинерія переходів layout:** де живе інтерполяція, що емітить ядро. **Перше** (рішення власника).

- **D2 — дві моделі інжекції презентації** (React-компонент / Pixi-view-фабрика) чи спроба уніфікації.

### D1-деталь — межа interaction vs emphasis (step-back-review 2026-11-02)

Попередня 5-польна `InteractionState` змішувала дві відповідальності — виправлено:

| Зріз | Поля | Власник | Лайфцикл |
|---|---|---|---|
| **Interaction** (що юзер торкає) | `selected`, `hovered` (потім `focused`) | pointer/keyboard | selection може жити |
| **Emphasis** (що акцентовано/приглушено) | `found`, `highlight` | search / команда хоста | `setData` чистить |

- **`found`** — НЕ в interaction-store: результат пошуку, власник — search (вже `setFoundFocus`;
  `setData` чистить). Спільний рендер-наслідок (приглушення) ≠ спільна відповідальність.
- **`highlight`** — emphasis, і здебільшого **похідне**: авто (hover→related) = селектор
  `f(hovered,mode)`, не збережене поле (зберігати похідне = десинк); хост-driven (`highlightPath`)
  = запис у emphasis-бакет.
- **`focused`** — **прибрано зараз** (передчасна абстракція: a11y/keyboard-навігації в коді нема).
  Коли зʼявиться a11y-таска — імовірно окреме поле (фокус≠вибір≠hover), але семантику визначає ВОНА.
- Підсумок: D1-store = `{ selected, hovered }`. Emphasis `{ found, highlight }` — окремий зріз, свій
  власник. Обидва годують рендер (обидва шари підписані), але це два власники, не один блоб.

## Порядок (рішення власника 2026-11-02)
**D3 (анімація) → D1 (interaction-store).** D3 і D1 **ортогональні** (твін позицій при зміні даних
не залежить від спільного стану hover/highlight), тож порядок — продуктовий вибір (візуальний ефект
