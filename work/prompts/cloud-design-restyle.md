# Промпт для хмарного агента: переробка стилів за візуальними еталонами

**Призначення:** віддати хмарному агенту (design) задачу привести стилі діаграми у
відповідність до візуальних еталонів і **поточних** вимог проєкту.
**Як користуватись:** скопіювати все нижче від лінії — це самодостатній промпт.
**Оновлювати:** коли змінюється схема стилів (`render/types.ts`) або набір еталонів.

---

Ти працюєш у репозиторії **`dg`** — Org Hierarchy SDK: діаграма оргструктури, яку малює
**Pixi.js 8** на канвасі. Це npm-workspaces монорепо: `packages/core` (Rust→WASM, контури),
`packages/sdk` (бібліотека), `packages/demo` (Rsbuild-демо, публікується на GitHub Pages).

Твоя задача — **привести стилі до візуальних еталонів**, не зламавши того, що вже працює.

## 0. Перше, що зробити: назвати еталон вголос

⚠️ У репо є **кілька** наборів зображень, і вони **не рівноцінні**. Перш ніж щось міняти,
переліч, що знайшов, і **явно скажи, який набір береш за джерело правди**:

| Де | Що це | Чи це еталон |
|---|---|---|
| `work/tasks/node-compare/*.png` | 28 файлів: 7 зразків × 4 види (`-diagram`, `-isolated`, `-side-by-side`, `-overlay`) + `README.md` зі знахідками від 2026-08-23 | **Це порівняння**, не еталон: обидві половини намальовані нашим кодом. Показує **розходження між нашим же рендером у діаграмі й ізольовано** |
| `e2e/mockups.spec.ts-snapshots/*.png` | 5 бейзлайнів Playwright | **Це зліпок поточного стану**, не мета. Вони фіксують, що є, а не що має бути |
| зовнішні макети (Figma / GoJS) | згадані в коментарях коду з номерами фреймів, напр. `Frame 1264:8121` у `mockupStyles.ts:11` | 🔴 **Ось це — справжній еталон**, але самих зображень у репо **немає** |

**Тому:** якщо тобі не передали окремо зображення-макети, **не вгадуй, як має виглядати**.
Скажи прямо, що еталонних макетів у репо немає, і **попроси їх**. Робота «за бейзлайнами»
означає підганяти код під його ж поточний вивід — це не переробка стилів, а фіксація статус-кво.

Що ти **можеш** зробити без макетів і що є справжньою цінністю:
- знайти **внутрішні розходження**, які видно з `-overlay.png` (двоїння тексту, зсув бейджа,
  різні LOD у двох половинах) — це дефекти незалежно від макета;
- звірити стилі з **числами, які вже записані в коментарях коду** (розміри фреймів, відступи,
  кеглі) — там зафіксовано наміри дизайну, і код може від них розходитись;
- знайти **суперечності між трьома наборами стилів** і невикористані/мертві ключі.

## 1. Де живуть стилі

| Файл | Що це | Розмір |
|---|---|---|
| `packages/demo/src/scenarios/mockupStyles.ts` | **три набори значень**: `MOCKUP_FIGMA_STYLES`, `MOCKUP_MAGNETIC_STYLES`, `MOCKUP_GOJS_STYLES`; `MOCKUP_DARK_STYLES` — псевдонім FIGMA | 222 рядки |

**Кольори — числа Pixi (`0x222222`), не CSS-рядки.** Це не косметична різниця: рядок туди
покласти можна, і воно зламається тихо.

## 1.5. Правила відображення — коротко, але це домен, а не оформлення

Без цього ти правитимеш кольори наосліп. Усе нижче виведене з коду; якорі вказані.

### Головне правило — смуги LOD

Вигляд ноди залежить **не від стилю, а від зуму** (`render/lod.ts:11-24`):

| Зум | Смуга | Посада | Організація |
|---|---|---|---|
| `< 0.45` | `far` | **крапка** в центрі боксу (`personVisualGeometry.ts:42-50`) | без символу, без тексту (`OrganizationNode.ts:246,315,338`) |
| `0.45–1.2` | `mid` | горизонтальна **смуга**, вертикально по центру (`:33-41`) | картка без підпису групи |
| `≥ 1.2` | `near` | **повна картка** (`:30-32`) | повна картка + підпис групи (`OrganizationNode.ts:416`) |

🔴 Стиль, підібраний лише на `near`, ламає дві інші смуги. Кожну правку перевіряй на всіх трьох.

### Посада (seat) — що малюється, залежить від даних

| Дані | Вигляд |
|---|---|
| `status: 'filled' \| 'vacant' \| 'acting'` | вакантна показує `(вакансія)` (`orgCardChrome.ts:21`), крім `hideVacantLabel` |
| `isTemporary` | маркер за `tempMarkerStyle`: `'badge'` — пігулка «Т» у куті, `'hourglass'` — гліф після імені; ім'я перемикається на `temporaryNameColor`, інакше `permanentNameColor` |
| `pending` | пісочний годинник справа вгорі — 🔴 **це інша ознака, ніж `isTemporary`**, і плутати їх не можна (`personCardContent.ts:163-174`) |
| `isKeyPosition` | брендова рамка + колір імені (`brandColor`) |
| `isHead` | керівна посада org; **рівно одна** на організацію |
| `detached` | приглушена рамка. ⚠️ Прапорець **додатковий**: лейаут сам виводить «відірвану» посаду, якщо вона в org, не `isHead` і не має адмінбатька в `reportLines` (`data/types.ts:105-109`) |
| `periodStart` / `periodEnd` / `periodLabel` | чип періоду; глушиться `hidePeriodOnCard` |
| `childrenCount` / `allDescendantCount` | смуга лічильників, формат `N [M]` (`orgCardChrome.ts:13-16`) |
| фото: `person.photoUrl` або `media` (тематичне) | якщо немає — плитка-заглушка, колір виводиться з хешу імені (`avatarColorFromName`) |
| `personLayout` | шаблон картки: `auto` · `figma-row` · `gojs-row` · `gojs-portrait` (`render/types.ts:104-107`) |
| `backgroundAlpha: 0` | **картка без рамки** — Figma staff: плитка аватара + текст, без корпусу |

### Організація

| Дані | Вигляд |
|---|---|
| `name` + `groupIds` | назва завжди; підпис групи **лише на `near`** |
| `media` (тематичне) | символ/емблема; розмір `symbolSize` або `symbolWidth`/`symbolHeight`; є окремий збільшений варіант «без підпису» |
| лічильники | `childrenCount [allDescendantCount]`, інакше `filledCount [vacantCount]` — формат `N [M]` (`orgCardChrome.ts:4-10`) |
| `collapsed` | піддерево сховане |
| `orgCardLayout` | `horizontal` (легасі) або `gojs-vertical` (символ → назва → код) |
| `entityType` | тип сутності від хоста (напр. `group`) — впливає на те, що показувати |

### Обгортки, які теж мають вигляд

Посади групуються в **підрозділи** — або органічний контур (WASM), або прямокутна картка
(`departmentStyle`), — і в **зони штату** з іменованими смугами. Їхні стилі
(`DepartmentCardStyle`, `StaffZoneStyle`) — теж твоя зона відповідальності.

## 3. Чого НЕ робити — межі задачі

- ❌ **Не змінюй `packages/sdk/src/render/types.ts`, щоб «підігнати» під нове значення**, поки не
  впевнився, що потрібного ключа справді немає. Розширення схеми — це зміна **публічного API
  SDK**, вона тягне за собою `docs/USAGE.md` і окремий цикл. Якщо ключ таки потрібен — скажи це
  окремо й обґрунтуй, замість тихо додати.
- ❌ **Не чіпай зближення DOM-карток із канвасними.** Над канвасом є React-оверлей
  (`packages/sdk/src/react/createReactPromoteOverlay.ts`), який на близькому зумі підіймає
  картки в DOM. Узгодження їхніх стилів із канвасними — **свідомо окрема задача**, винесена за
  скоуп рішенням власника проєкту. Не тягни її сюди.
- ❌ **Не міняй пороги LOD** (`farMax`/`midMax`) заради того, щоб «стало схоже». Якщо схожість
  досягається лише зміною порога — це знахідка, про яку треба сказати, а не правка.
- ❌ **Не перегенеровуй бейзлайни `e2e/*-snapshots/` локально.** Вони зняті на раннері CI
  (`-linux.png`), і локальний рендер від них відрізняється **завжди**. Локальна перегенерація
  дасть диф, який виглядає як зміна дизайну, а насправді є зміною середовища.
- ❌ **Демо публічне** (GitHub Pages). Фікстури лишаються цивільними: жодних реальних людей,
  організацій чи будь-чого, що не можна показати назовні.

## 4. Порядок роботи

1. **Інвентаризація.** Перелічи всі три набори стилів по ключах у таблиці: ключ · FIGMA ·
   MAGNETIC · GOJS · чи є в схемі `types.ts` · чи використовується в рендері.
   Тут одразу спливе мертве й суперечливе.
2. **Звірка з намірами.** У коментарях `mockupStyles.ts` записані числа з макетів (розміри
   фреймів, відступи, кеглі, номери фреймів). Звір їх зі значеннями поруч. Розходження
   коментаря й значення — дефект **завжди**, незалежно від того, хто правий.
3. **Читання накладок.** `work/tasks/node-compare/*-overlay.png` — подвійний текст, зсунутий
   бейдж, різна геометрія. Кожну знахідку прив'яжи до `шлях:рядок`.
4. **Правки — по одній.** Кожна правка = одне спостережуване покращення + причина.
5. **Перевірка** (див. §5).
6. **Звіт** (див. §6).

## 5. Як перевірятись

```bash
npm run lint          # oxlint
npm run typecheck     # tsc + build:types
npm test              # rstest, ~733 тести
npm run compare:nodes # перегенерувати пари node-compare
npm run test:e2e      # Playwright (бейзлайни — з CI, локально відрізнятимуться)
```

Живий перегляд зразків без обв'язки діаграми: демо на `/?node-compare=1`.

**Мінімум перед тим, як віддавати роботу:** `lint`, `typecheck`, `test` — зелені. Якщо
`test:e2e` червоний через бейзлайни — **скажи це явно** й назви, які саме знімки розійшлись;
не перезаписуй їх.

## 6. Що віддати

Один файл — `work/reports/design-restyle/report.md`. Шість секцій, порожню не видаляй, а пиши
«не застосовно, бо…»:

1. **Що зроблено** — правки з `шлях:рядок` і причиною кожної.
2. **Таблиця інвентаризації стилів** (з §4.1).
3. **Неочевидне** — розходження коментарів і значень, мертві ключі, суперечності між наборами.
   Кожне з якорем.
4. **Скріни** — до/після для кожної видимої зміни.
5. **Проходка** — що бачить людина на кожній вкладці після правок.
6. **Ризики й обмеження** — що не закрито, що лишилось здогадом, де потрібні макети.

## 7. Правила, які важать більше за швидкість

- **Не вигадуй значень.** Якщо для ключа немає ні макета, ні числа в коментарі, ні вимоги —
  не став «на око». Назви його в §6.6 як такий, що потребує рішення дизайнера.
- **Не видавай статус-кво за мету.** Підганяння коду під його ж поточний вивід — не переробка.
- **Одна правка — одне спостережуване покращення.** Правку, яку не можна побачити, поясни
  словами або не роби.
- **Зламав тест — не переписуй тест під новий вивід**, поки не пояснив, чому старе очікування
  було неправильним. Якщо старе було правильним — правка твоя, а не тесту.
