## 1. Мета
Привести staff-сцену до мокапа `shps-card-v3.html` **структурно**: три невидимі namespace (lead / current / subordinate) одна під одною без перетинів; у них — видимі
обгортки організацій (база + модифікатори) з обгортками відділів усередині; підпорядковані — **композиційно** під current-блоком (виглядає деревом, з'єднані шиною від обгортки);
міжорганізаційні зв'язки чіпляються до **обгорток**, як у мокапі.

## 2. ГЛОСАРІЙ — три різні за природою сутності (рішення власника, Dg17)
| Сутність | Видима? | Роль | Скільки |
|---|---|---|---|
| **namespace** | **ні** (невидимий регіон) | тримає порядок і непересічність шарів по вертикалі; місце, де лежать обгортки | рівно **3**: `lead`, `current`, `subordinate` |
| **обгортка організації** (org wrapper) | так | рамка-card навколо штатки однієї організації; база + модифікатори | **N у namespace** (1 у lead, 1 у current, N у subordinate) |
| **обгортка відділу** (department wrapper) | так | рамка навколо посад відділу; режими `card`/`blob` (S7 — окрема розвідка) | N усередині org wrapper |
- Кожна обгортка організації — **base**; **lead = base + фон (штриховка)**, **current = base + чіп «Поточна організація»**, **subordinate = base**.
- **Нащадки підпорядкованих** (підпорядковані підпорядкованих, будь-якої глибини) **теж лежать у namespace 3**, не створюють нових namespace.
- Не плутати: namespace ≠ обгортка (різні прямокутники, різна природа); обгортка організації ≠ обгортка відділу.

## 6. Інваріанти (тестовані; допуск ±1 px де не сказано інше)
- **I-N1** namespaces впорядковані й **не перетинаються**: `lead.bottom + gap ≤ current.top`, `current.bottom + gap ≤ subordinate.top`, де gap ≥ розростання band на `pad + labelBand` (критик: I-Z1 не гарантований, tierGap=36 може бути менше).
- **I-N2** кожна обгортка організації ⊂ свій namespace (namespace ≠ обгортка, тож інваріант змістовний).
- **I-T1** усі підпорядковані строго нижче **усіх** рамок відділів current: `min(y підпорядкованих) > max(низ рамок відділів) + gap`.
- **I-T2** діти центровані під віссю батька (±1); **I-T3** міжорганізаційні ребра лише вертикальні/шина; **I-T4** ребро не перетинає рамок відділів; **I-T5** рамки сусідніх обгорток/відділів не перетинаються й мають зазор.
- **I-A1** вісь: центр-X lead-обгортки == current-обгортки == центр підпорядкованих; симетрично для `dx≤0`; ярус-3 теж.
- **I-A2 (O-46)** вирівнювання по верху: `y(верх картки кореня БЕЗ відділу) == y(верх картки першого ряду відділу того ж рівня)` (±1); зміщення = «шапка + верхній відступ» обгортки відділу з **того самого джерела** (без другого числа).
- **I-R1 (новий, D-11)** регрес: геометрія лейауту ВСІХ інших staff-сцен (mockup-staff-figma, staff-tree, v2-router, variant-b…) порівняна з baseline; розбіжності — або явно прийняті (список), або фікс.

## 7a. РІШЕННЯ ВЛАСНИКА по §7 (Dg17, відповідь на п.1-6)

## 7b. РІШЕННЯ ВЛАСНИКА (Dg17, друга відповідь) — модель взаємодій і форма результату
- **§7.1 ЗАКРИТО: ЛАМАЄМО.** Обґрунтування: хост цей SDK не споживає (`AGENTS.md`, «Read §5 of the briefing's verdict… it does not»), версія 0.6.0. → `tiers` **замінюється** на `namespaces` без compat-вигляду; усі споживачі (`cross-tier`/`tiers`: `svgExport.ts`, `StaffEdgesView.ts`, `staffZoneBounds.ts`, `DiagramRenderer.ts`, `e2eBridge.ts`, тести) оновлюються **в одній зміні**.

- **§7.5 МОДЕЛЬ ВЗАЄМОДІЙ (чотири жести, власник):**
  1. **Клік по картці посади** → **подія хосту** (хост відкриває sidebar; у події приходить дата). SDK нічого не розкриває. *Є:* `onPersonClick` → `onNodeClick(node)` (`OrgHierarchyDiagram.ts:907-913`).

  4. **«Drill-to-focus» = перехід до знайденої посади**, а не зміна поточної організації: перенести камеру до посади, **розкрити приховане, якщо посада була прихована**, виділити знайдену **рамкою + плашкою «Знайдено»** (як у мокапі). ⚠️ **Переозначає SPEC:240-250** (там drill = `focusStaffOrg` робить орг новою поточною).

У SDK: **тьмяніння ВЖЕ є** (`setFoundFocus` `OrgHierarchyDiagram.ts:1606`, `DiagramRenderer.ts:517` `foundDimAlpha ?? 0.38`); **плашки/рамки НЕМА ніде** (рядка «Знайдено» немає в `packages`); `focusNode` **не розкриває** приховане — лише `applySelection` + `panToNode` (`:1754-1763`).
- **Нові відкриті питання:** (7) клік по картці організації — **лише** розгортання чи **також** подія хосту `onNodeClick`? ## 7e. ДЕБАТИ a6: «TS зараз» vs «чекати T126» (Dg17) → `_a6-ts-vs-rust-defense-dg17.md` + `_a6-debate-critic-dg17.md`
**Теза власника:** «якщо Rust рахує координати, а точки лінків деінде — не буде однієї правди». **Результат (критик, факти звірені мною в коді):** **діагноз власника ЕМПІРИЧНО ПРАВИЛЬНИЙ (знайдено чинну розбіжність). Критик радить інший рецепт, ніж Rust — це ПОРАДА; мандат власника (D-13) лишається.**
- **Знайдена «друга правда» в коді (поза T125):** padding обгорток рахується **двома формулами**. Живий рендер: `departmentWrapperPadding(theme, config)` (`DiagramRenderer.ts:1220-1228`; для `card` = `card.padding + (labelFontSize+6)` → для ШПС 16+14+6 = **36**). SVG-експорт: **завжди формула контурів** `contourButtonGroupMargin(config.paddingCells ?? 0, DEPT_STROKE_W)` (`svgExport.ts:223`) = `max(6, stroke/2+4)+pad·8` ≈ **6** (якщо штрих ≤ 4; значення `DEPT_STROKE_W` з `defaultNodeTheme` `:96` — **не перевірено**), і бере константи з `defaultNodeTheme`, **не з теми хоста**. `labelBand` в експорті **не передається** (`:214-224`). Коментар `:222` «Same rule as the canvas» — **неправдивий для `card`**. Різниця для ШПС ≈ **30 px**. **Це чинний дефект SVG-експорту ШПС-сцени** (рамка зони), не припущення.
- **Паритет ТОЧОК лінків між live і SVG ЄСТЬ** (обидва кличуть `mapStaffEdgeBoxesForLod(mapPositionNodesToStaffEdgeBoxes(...))`, `DiagramRenderer.ts:846-850` / `svgExport.ts:296-299`). Розбіжність лише у **відступах обгорток**, не в якорях.
- **Оцінка критика (ПОРАДА, не рішення; власник обрав «велику міграцію в Rust», O-15) — «Rust рахує відступи й якорі» — ціна висока:** довелося б переписати `staffDeptGrouping`, пакування ярусів, overlap-nudge, вісь; ламає стек-ноту `AGENTS.md`; а точки лінків залежать від LOD, якого Rust не знає (`visualEdgeBox.ts:25-49`). Власний арх-аналіз T126 вже показав: координати в одному world-просторі.
- **Висновок КРИТИКА по a6 (ПОРАДА; власник обрав «чекати T126», O-33 — це рішення ЧИННЕ):** умова «TS, якщо одне джерело padding» — **хибна бінарність: передумова сьогодні НЕ виконана**. «Чекати T126» — **відхилити** критиком (нуль коректності, T126 заблоковано). **Третій шлях: a6 ПІСЛЯ a4**, де a4 робить межі обгорток частиною виходу лейауту з **єдиним padding/labelBand, який читають І рендер, І svgExport**. Це вже закладений порядок a4→a6.
- **Що це міняє:** (1) **a1 розширюється** — виміряти live-padding vs SVG-padding для ШПС (px) і чи пропуск `labelBand` в експорті — баг рамки зони; (2) **критерій готовності a4:** `svgExport` **не має власної формули** padding/labelBand, читає з виходу лейауту; **паритет-тест live vs SVG** на `card`-сцені; (3) формулювання «одна правда» стає суворішим: **одне ДЖЕРЕЛО у виході лейауту** (одне місце + один шар), а не лише «обчислено один раз».
**Стан a6:** ⛔ **ЧЕКАЄ T126 — рішення власника (O-33, O-34).** «Третій шлях» (TS після a4) — лише порада критика, не прийнята.
