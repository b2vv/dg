## Вимоги власника (2026-10-27, рукописна нота Dg17)

Додані прямим запитом власника; транскрипт:

1. **Нод-обгортки мають 3 вигляди (типи зон):**
   1. **Головна / Lead** — керівна організація (`role:'leading'`);
   2. **Організація** — базова обгортка організації (НЕ «поточна організація» як окремий тип!).
      **Уточнення власника:** «поточна» — це **та сама обгортка організації + ЧІП** «Поточна організація»
      (а не інший тип обгортки). Тобто current = Організація-обгортка з доданим чіпом/акцентом (Dg16 вже
      має `currentAccent` + чіп — це модифікатор, не окремий вигляд).
   3. **Департамент** — рамка-зона відділу.
   → зараз зони малюються `StaffZonesView` (орг) і `DepartmentCardView` (відділ); типи обгорток треба
   довести до мокапа як **база + модифікатори** (чіп Lead / чіп Поточна), а не три незалежні гілки.
   Перегук з «департаменти ≠ мокап» нижче.

2. **Відступи між нодами — врахувати внутрішні відступи обгорток департаментів**, щоб були відступи
   **між** обгортками департаментів (рамки сусідніх відділів не торкаються / мають зазор). Зараз
   dept-рамки можуть лягати впритул; потрібен padding обгортки + gap між обгортками на лейауті.

3. **Rust рахує координати нод → логічніше, щоб і точки відображення лінків рахував Rust** — усі
   розрахунки в ОДНІЙ системі координат. З DOM отримуємо розміри (рендерених) карток; canvas малює
   свої картки **по розмірах DOM — для ІДЕНТИЧНОСТІ** (canvas-картка = DOM-картка піксель-у-піксель).
   → Це **цільовий напрям [ADR-0002]** (`docs/adr/0002-edge-dock-point-is-declared-by-the-node.md`):
   варіанти 3 (якір із rust-контуру) + 4 (розмір із рендереної картки) разом. `edgePort:'center'` Dg17 —
   проміжний крок у TS; повний контракт = якір і координати з Rust, розмір картки з DOM, порт споживає обидва.

### Підхід до побудови (напрям власника, Dg17)
- Діаграму по мокапу будувати через **підхід «креслення» + `/design-pass`** (скіл `design-pass`:
  обмеження → дизайн-план → браузерна звірка → правки). Не ad-hoc, а від креслення/мокапа.
- Для відображень — **більше render-налаштувань** (винести у config те, що зараз зашите).
- **Відступи між нодами рахує Rust** (а не лише TS-лейаут) — щоб побудова була правильною «в одній системі».
- **Внутрішні відступи в обгортках** (padding зон/департаментів) — врахувати і в лейауті, і в рендері.

## Факт (ВИМІРЯНО Dg17 через e2e-bridge+DOM, діагноз Dg16 спростовано)

Вимір (демо `?e2e=1&tab=staff-shps`, zoom 1.3 near, React-картки; числа, не JPEG):
- `getAnchors()`: голови керівної (`per-sydorenko`) і поточної (`shps-head`) — **обидві** world x=844,
  width=**300** → cell-центр world **994** (screen 720). Вісь ярусів вирівняна (фікс Dg15 ок).
- DOM React-картки обох голів: x=525, w=390 (=300×1.3), cx=720 → видима картка займає **повний cell 300**
  і центрована. (Діагноз Dg16 «картка 248 ≠ cell 300» — **ХИБНИЙ**: тут картка 300.)
- Намальований cross-tier лінк — на screen ≈**550** (world ≈864), по **ЛІВОМУ краю** картки, не центру.

**Корінь (код + число збіглося):** `DiagramRenderer:846` → `mapPositionNodesToStaffEdgeBoxes(…, theme.person)`
→ `visualPersonEdgeBox` (`render/visualEdgeBox.ts:36-47`): для layout **`figma-row`** на **near-LOD**
бокс ребра стає **аватар-плиткою** (`tileX = avatar.cx − size/2`). `figmaRowAvatar.cx = 20`, size=40
(`personLayout.ts:29-38`) → порт-центр = `box.x + 20` = 864 world = screen 551 — **ТОЧНИЙ** збіг зі
спостереженим. Коментар коду: «Chrome-less seat: edges dock on the tile» — навмисне для chrome-less
figma-row, але ShpsStaffCard — повна картка, а мокап `.plink` веде через **центр**. Зсув = **130px world**.

**Межа бага (виміряно читанням `visualEdgeBox.ts` + `personVisualGeometry.ts`):** центрування порту є на
**mid/far** (смуга на всю ширину / точка по центру) і на **gojs-row/near**. Off-center **лише на
near-LOD + figma-row**. НЕ виміряно візуально: intra-department head→підлеглі лінки (той самий код-шлях,
очікувано теж avatar-dock) і far-LOD Pixi (очікувано центровано).

## Відкрите рішення власника — куди докувати edge-порт figma-row/near

Старі кандидати (а cell=card / б card на повну cell / в якір з рендереної картки / г rust-контур) цілили
в ХИБНИЙ корінь (cell-vs-card width) → **зняті**. Реальна розвилка:

- **I** cross-tier ребра докувати на **центр** картки (intra-dept лишити на аватарі?) — вузько.
- **II** прапор стилю `edgePort: 'center' | 'avatar'` для figma-row; ShpsStaffCard → `center`.
- **III** ShpsStaffCard не резолвити у figma-row для портів (інший layout-шлях).

Контракт порту figma-row — головний кандидат на **ADR-0002**. **Ризик регресії:** перевірити, чи якась
наявна сцена/тест покладається на avatar-dock (chrome-less figma-row seats).

## 🔴 Критика T125 (Dg17, незалежний gate-reviewer) → `_t125-critique-dg17.md`

**Вердикт: GATE ЧЕРВОНИЙ — 3 блокери, усі у вимозі №3.** Вимоги №1, №2, design-pass — здійсненні з
точковим рефактором, але недовизначені. По вимозі №3 **кодувати не можна, поки власник не розв'яже**.

**BLOCKING:**
- **B1. Цикл DOM↔Rust + інвертована стрілка.** DOM-картка (`ShpsStaffCard`) існує ЛИШЕ на near-LOD
  (promote ≥1.2); на far/mid малює Pixi — DOM-картки НЕМА, звідки «розмір DOM»? Ба більше, наявна стрілка
  ЗВОРОТНЯ бажаній: `ShpsStaffCard.ts:6-9` — DOM-картка копіює розмір канви ×`viewport.scale`, а не канва з DOM.
  Повний ланцюг вимоги = цикл (Rust→DOM→вимір→Rust-якір→canvas); хто розриває на 1-му кадрі й на far — не визначено.
- **B2. Вимога №3 = саме ВІДХИЛЕНІ варіанти ADR-0002.** `docs/adr/0002-*.md:43-51` відхилив варіант 3
  (якір з rust-контуру) і варіант 4 (якір з рендереної картки). Вимога №3 замовляє «3+4 разом». Маємо
  **accepted ADR проти прямого замовлення власника в тій самій задачі** — суперечність, яку треба зняти
  (переглянути ADR АБО переформулювати вимогу).
- **B3. «Відступи рахує Rust» суперечить архітектурі.** Rust WASM експортує рівно `computeOrgRowTreeLayout`
  (`packages/core/src/lib.rs:20`); gaps/margin/nodeWidth — ВХІДНІ параметри з TS (`layoutBridge.ts:30-52`).
  Усе спейсингове рішення — TS (`canvasLayout.ts`, `orgBlockLayout.ts:78-157`, `staffDeptGrouping.ts:68-103`).
  Перенести відступи в Rust = переписати більшість staff-лейауту, що суперечить стек-ноті AGENTS.md
  («core — contours + row-tree; canvas paint is TS»). Обсяг великий, межі не задані.

**NON-BLOCKING:** N1 Lead-модифікатор відсутній (`staffZoneAccent` має лише `currentOrgChipAccent`) — чи
Lead теж база+чіп?; N2 зазор між dept-рамками реальна прогалина (`staffDeptGrouping.ts:82-102` рознесе сідання,
але `DepartmentCardView.ts:43-59` малює padding назовні → рамки з'їдають зазор); N3 edgePort стане мертвим,
якщо B1/B2 реалізують — межа зняття не задана; N4 «більше render-налаштувань» = scope creep без критеріїв;
N5 вісь-тесту досі НЕМА (`staffLayout.test.ts:278,285` — лише існування), dx≤0/ярус-3 не покриті; N6 design-pass
накриває лише DOM-пів-стеку (far-LOD Pixi Graphics не має CSS-поверхні для «дизайн-план → стилі»).

### ✅ РІШЕННЯ ВЛАСНИКА по червоному gate (Dg17)
Обрано **«велика міграція в Rust»**: лейаут-координати + якорі лінків + відступи між нодами переносяться
в Rust (одна система координат), ADR-0002 переглядається, архітектура змінюється. → Вимога №3 виокремлена

публічну поверхню й стек-контракт) + рефреш CTO-RESEARCH. **B1 (звідки розмір на far-LOD / хто розриває
цикл) мусить бути розв'язаний у спеці T126 ПЕРЕД кодом.** T125 лишає собі вимоги №1, №2 і візуальні пункти.
