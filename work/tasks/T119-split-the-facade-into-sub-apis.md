# T119 — рознести фасад на інтерфейси й класи, що працюють з об'єктом

**Пріоритет:** P2 · **Статус:** 🔵 не почато — **пропозиція користувача 2026-09-08, підперта
виміром; потребує `spec-flow`, бо ламає публічний API**
**Джерело:** [T106](./T106-deepen-facades-drop-shallow-wrappers.md) §Вимір — він показав, що далі
фасад не зменшити рефакторингом, і уперся саме в це питання.

## Пропозиція

Замість одного класу на 65 публічних методів — **інтерфейси** й класи, що їх реалізують,
віддані як під-об'єкти: `diagram.camera.setZoom()`, `diagram.search.all()` тощо.

## 🔑 Прецедент уже в цьому коді, і він публічний

`diagram.media` — рівно ця форма: інтерфейс `DiagramMediaFacade` (`media/types.ts:30`),
реалізований класом `MediaService`, відданий геттером (`OrgHierarchyDiagram.ts:474`).
Тобто це не нова архітектура, а **поширення наявної**.

## Чим вимір підпирає пропозицію

| Що виміряно | Значення |
|---|---|
| публічних методів | **65** |
| з них чіпають **≤2** члени `this` | **46** |
| найпоширеніші залежності | `data` (25/65), `host` (16), `render` (13), `viewState` (11) |

**46 із 65 методів тонкі** — тобто поверхня справді розділювана. Це протилежність тому, що
вимір T106 показав про `renderNow`: той чіпає **25** різних членів і виносу не піддається.

⚠️ **Групування за іменами, яке я спробував першим, виявилось ненадійним** (`expandOrg`
потрапив у «камеру» через кривий регекс) — тому в цій задачі його **немає**. Групи треба
виводити з **графа залежностей**, а не з назв: для кожного методу вже є множина `this.*`,
яку він чіпає, і кластери слід рахувати по ній.

## 🔴 Ціна: це ламальна зміна публічного API

`docs/USAGE.md` описує ці методи як контракт, тож `diagram.setZoom()` → `diagram.camera.setZoom()`
ламає кожен виклик хоста. Отже **вище порога**, повний `spec-flow`, запис у CHANGELOG, ймовірно
мажорний бамп.

✅ **І саме тому це варто робити ЗАРАЗ, якщо робити взагалі.** Архітектурний факт №5 брифінгу:
**у SDK немає жодного споживача** — хост і далі на GoJS. Вартість ламання API ніколи не буде
нижчою, ніж поки його ніхто не викликає. Через рік це буде міграція чужого коду.

## Що вирішити до плану

1. **Чи розділяти взагалі**, чи лишити пласкі 65 методів як свідому простоту. Плаский API легше
   відкривати з автодоповнення; згрупований легше тримати.
2. **Скільки груп і за яким критерієм** — виводити з графа залежностей, не з назв.
3. **Сумісність:** лишати старі методи як `@deprecated` делегати (тобто **обгортки**, проти яких
   T106) чи ламати одразу. З нулем споживачів другий варіант чесніший.
4. Чи стають під-об'єкти **тестовими швами** — тобто чи кожен володіє власним станом, чи всі
   однаково тягнуть `data`/`host`. Якщо друге, це переїзд, а не поглиблення, і задачу треба
   закрити як непотрібну.
