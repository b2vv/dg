# T84 — Render-on-demand: перестати малювати нерухому картинку 60 разів на секунду

**Пріоритет:** P1 · **Статус:** ✅ виконано (2026-08-27) — `9bc54b1`
**Примітка (2026-09-01):** заголовок казав «не почато». Ticker вимкнено (`autoStart: false`),
усе, що рухає пікселі, просить `requestPaint`. Виправлено під час перезбору брифінгу.
**Підстава:** `work/reports/zero-client/report.md` §1 — простійна вкладка палить ~1.2 ядра.
**Файли:** `packages/sdk/src/render/PixiHost.ts`, `packages/sdk/src/render/Viewport.ts`,
`packages/sdk/src/render/personInteractions.ts`, `packages/sdk/src/OrgHierarchyDiagram.ts`

## Факт

П'ять секунд, коли ніхто не торкається діаграми:

| | CPU за 5 с |
|---|---|
| як зараз | **6068 мс** ≈ 1.2 ядра |
| із заглушеними кадрами | **0 мс** |

Друге число — доказ атрибуції: перехопив `requestAnimationFrame` на **готовій** діаграмі й
перестав пускати кадри; 5007 → 0. Тобто це не сцена, не WASM і не WebGL, а **цикл рендеру**.

Причина: `app.init({…})` у `PixiHost.ts:124` іде **без** `autoStart: false`, тож Pixi тримає
власний тікер. При цьому рендер на вимогу в нас **уже є** — `createRenderCoalesce`
(`OrgHierarchyDiagram.ts:141`) перебудовує сцену на кожну зміну. Тікер лише перемальовує те саме.

**Ціна:** 10 вкладок, де люди просто читають діаграму, з'їдають ~12 ядер. Це, а не «WebGL
повільний», дало 4 fps у контенційному тесті.

## Чому це не однорядкова правка

`renderer.render()` на `OrgHierarchyDiagram.ts:365` — це **наш** білдер сцени, а не Pixi-паінт.
`autoStart: false` без явного `app.render()` = чорний екран.

Але місць, які треба покрити, менше, ніж здавалось — вони згруповані:

| Що змінює картинку | Точка проходу |
|---|---|
| перебудова сцени | `renderNow()` — уже єдина |
| пан і зум | **`Viewport.apply()`** (`Viewport.ts:429`) — єдина для всіх жестів, уже має `onChange` |
| анімація камери | твін на `requestAnimationFrame` (`Viewport.ts:196`) — малює покадрово, поки йде |
| драг картки | `node.position.set(...)` (`personInteractions.ts:166,182,187`) |
| підписи зон | `text.position.set(...)` (`StaffZonesView.ts:80`) |

Тобто це «прокинути `requestPaint()` у п'ять місць», а не «переписати рендер».

## Що робимо

1. `autoStart: false` у `app.init` + `app.ticker.stop()`.
2. `requestPaint()` у `PixiHost` — коалесить виклики в **один** `app.render()` на кадр
   (інакше драг дасть кілька паінтів на подію).
3. Викликати його з п'яти точок таблиці вище.
4. На час анімацій (твін камери, майбутній морфінг контурів) — тікер **запускається** і
   зупиняється по завершенню. Півзаходи тут гірші за обидва варіанти: анімація на
   `requestPaint` смикатиметься.

## Готово, коли

- [ ] Тест на простій: діаграма готова, 3 секунди без дій → **нуль** паінтів
      (лічильник на `app.render`, не на fps).
- [ ] Тест на кожну з п'яти точок: дія → рівно один паінт (не нуль, не три).
- [ ] e2e зелений; візуальні бейзлайни не змінились.
- [ ] Анімація камери лишається плавною — перевірено вимірюванням fps під час твіну, не оком.

## Що це дає разом із T83

| | 10 сесій без GPU |
|---|---|
| зараз | 4 fps, відкриття 12.3 с, ~1.2 ядра на кожну простійну вкладку |
| тільки T84 | 13 fps, відкриття 2.4 с, простій → 0 |
| T83 + T84 | 121 fps, відкриття 0.3 с, простій → 0 |

T84 корисний і сам по собі, **на будь-якому залізі**: зараз ноутбук гріє вентилятор на
нерухомій діаграмі.
