# T135 — експорт діаграми має знімати те, що на екрані (alpha-шлях, React-хром, near-картки)

**Пріоритет:** P2 · **Статус:** 🔵 не почато · **потребує `spec-flow`**
**Джерело:** діаграма взаємодії, знахідка D3 (`work/reports/library-boundary-audit/host-interaction-diagram.md`);
рішення власника 2026-11-05: логіка D3 — у бібліотеці.

## Факт (з коду, на стенді не перевірено)

- Хост експортує сирим `canvas.toBlob` (`dg-tree-diagram.engine.ts` `exportPng`): лише видимий кадр, без
  HTML-карток і без SVG-хрому, який малює сам хост.
- Перехід хоста на SDK `export()` (`OrgHierarchyDiagram.ts:2449`) **цього не закриває**:
  - хост вмикає `render.staffReactChrome: true`; на near/mid Pixi тоді **не малює** рамки відділів/org і
    лінії — їх малює React-backdrop хоста (`render/DiagramRenderer.ts:760-767`). PNG/PDF знімають Pixi-сцену
    (`app.stage`), тож на цих зумах файл, імовірно, без рамок і ліній;
  - `export()` знімає промоут (`OrgHierarchyDiagram.ts` `export`), тож у файлі Pixi-картки, а не HTML-шаблон хоста;
  - SVG-експорт будується з TS-геометрії, не з alpha-розкладки, якою живе екран
    (`work/ROADMAP-extensibility.md` К2: «SVG export ЗАВЖДИ TS», `export/svgExport.ts`).

## Мета

Хост викликає один метод бібліотеки й отримує файл, що відповідає екрану: та сама розкладка й маршрути,
рамки, лінії, картки — незалежно від того, хто малює їх на екрані (Pixi чи React-шар).

## Відкриті питання для spec-flow

1. Що вважати «як на екрані» для near-карток: Pixi-картка (є в SDK) чи шаблон хоста (HTML)? Растеризація HTML —
   окрема складність; для шаблонів T130 це може мати іншу відповідь, ніж зараз.
2. Хром у файлі: SDK малює його в експорті сам з `getStaffChromeGeometry()` (одна геометрія — Б2), навіть коли
   на екрані його малює React?
3. SVG на alpha-шляху: перейти на ту саму геометрію, що й екран (пов'язано з консолідацією К1–К2 роадмапу)?
4. Обсяг: увесь дерево-знімок чи поточний кадр — що потрібно хосту?
