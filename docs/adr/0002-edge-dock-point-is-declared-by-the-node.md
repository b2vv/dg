# Геометрію staff-сцени — координати, пакування, обгортки, namespaces, вісь і точки лінків — рахує Rust в одній системі координат; нода лише оголошує форму

Переписано в Dg17 під мандат власника (попередня версія вважала «одне джерело якоря» TS-справою й відхиляла `rust`-варіанти; власник це відхилив — O-34).
Дослівні слова власника: [`_owner-requirements-ledger-dg17.md`](../../work/reports/staff-demo-clean/_owner-requirements-ledger-dg17.md) (O-9, O-10, O-11, O-15, O-33, O-38). Реалізація — [T126](../../work/tasks/T126-staff-layout-anchors-spacing-into-rust.md).

## Проблема (виміряна)
Одна величина — «де ребро чіпляється до ноди» і «скільки місця навколо ноди» — сьогодні обчислюється в кількох місцях, і вони розходяться:
- **Порт `figma-row` на near-LOD** докувався на аватар-плитку (`render/visualEdgeBox.ts:36-47`, `box.x + 20`), хоча картка малюється на повну ширину (центр `box.x + 150`); виміряно в браузері як ~130px розбіжності (T125).
- **Padding обгорток рахується двома формулами:** live `departmentWrapperPadding` (`render/DiagramRenderer.ts:1220-1228`, для ШПС ≈36) і SVG-експорт `contourButtonGroupMargin(…, DEPT_STROKE_W)` (`export/svgExport.ts:223`, ≈6, без `labelBand`); коментар «Same rule as the canvas» там неправдивий для `card`.
- **TS правит вихід Rust:** перецентровування кореня (`layout/staff/orgBlockLayout.ts:87-102`), пакування й зсув регіонів відділів (`staffDeptGrouping.ts:68-105`), зсуви ярусів (`canvasLayout.ts:80-84,150-152`); Rust (`packages/core/src/lib.rs:20`) рахує лише row-tree одного орг-блоку.
- **Точки лінків рахує рендер із LOD** (`DiagramRenderer.ts:846-851` → `visualEdgeBox.ts:25-49` → `staffEdgeGeometry.ts`), тож лейаут про них не знає.
Результат: «немає однієї правди» (O-33) — не метафора, а дві різні формули для однієї величини й координати, правлені двічі.

## Рішення
**Геометрію рахує одне місце — Rust, в одній системі координат.** Rust рахує: координати нод; **пакування відділів і обгорток** з їхніми внутрішніми відступами; **композицію ярусів, namespaces і вісь**; **межі обгорток і namespaces**; **точки лінків** і відступи між нодами. Усі споживачі (live-рендер, SVG-експорт, тести) **лише читають** результат — власних формул padding/якоря не мають.
Розміри карток — **з DOM** (content-driven, O-16.1), canvas малює свої картки за тими самими розмірами (ідентичність, O-10); режим **`/debug`** порівнює canvas і DOM, розбіжність — **баг** (O-16.2).
**Нода оголошує форму, а не координату:** `PersonNodeStyle.edgePort: 'center' | 'avatar'` (`render/types.ts`, T125) лишається — тепер як **вхід** правила порту в єдине обчислення. T125-фікс (`visualEdgeBox.ts:68-69`) — чинна проміжна TS-реалізація до приходу Rust-обчислення.

## Розглянуті варіанти
**1. Rust рахує все перелічене — обрано власником** (O-9, O-11, O-15 «Велика міграція в Rust», O-33, O-38). Єдине джерело геометрії; усуває обидві виміряні розбіжності за конструкцією.

**2. Кожен шар рахує своє — відхилено.** Саме це й дало виміряні розбіжності (порт ↔ картка; padding live ↔ SVG).

**3. Один TS-сайт якоря, Rust лишається row-tree — відхилено власником** (O-34, O-16.3). Це була рекомендація арх-аналізу й критика (`_arch-review-req3-dg17.md`, `_arch-critic-req3-dg17.md`): **дешевша**, не чіпає стек-ноту `AGENTS.md` і не додає WASM-межі. Відхилено, бо власник вимагає одну систему координат у Rust; цей варіант лишається **аргументом для порівняння в спеці R1**, якщо виміри (перф WASM-межі) покажуть неприйнятну ціну варіанта 1.

**4. DOM — авторитет розміру (вхід у варіант 1) — обрано як частину варіанта 1.** Розмір картки вимірюється в DOM і подається в Rust; це відкриває цикл DOM↔Rust (нижче).

## Наслідки — і головні з них незручні
🔴 **Це велика міграція, а не фікс.** Rust сьогодні рахує одну функцію на орг-блок; пакування відділів, композиція ярусів, вісь, межі обгорток і (частково) маршрути лінків — TS. Перенесення змінює стек-ноту `AGENTS.md` («core — contours + row-tree; canvas paint is TS») — вона оновлюється разом із цим ADR (T126 R9). Для `packages/core` **нема документованого Rust-стандарту** (`AGENTS.md`) — спека R1 мусить його задати.
🔴 **Точки лінків залежать від LOD**, якого лейаут не знає (`visualEdgeBox.ts:25-49`). **Не вирішено:** LOD і правило порту — вхід у Rust (перерахунок при зміні LOD) чи Rust віддає точки для всіх LOD одразу; і чи «точки лінків» — це лише порти-якорі, чи повні маршрути з обходом рамок (`staffEdgeGeometry.ts:433+`) — **T126 Q-3, рішення власника**.
🔴 **Цикл DOM↔Rust:** content-driven висота + DOM-джерело + Rust-лейаут; на першому кадрі DOM не змонтований, на far/mid DOM-картки нема. **Не вирішено:** механізм розриву (headless-вимір без позиції, кеш виміру, фолбек-розмір) — **T126 R2**.
🟠 **Вартість WASM-межі на 1M-вікнах не виміряна** (T126 R10). Якщо вона неприйнятна, варіант 3 повертається як порівняльна альтернатива.
🟠 **Поки T126 не виконано, співіснують дві правди:** TS-проміжні реалізації (`edgePort`, `canvasLayout` пост-центрування `dx>0`, TS-padding) і Rust-ціль. Тому **T127a-a6 і геометричні a1/a3/a4/a5 чекають T126**, а baseline лейауту всіх сцен (T126 R0) — передумова, бо без нього регрес не довести.
🟡 **Форму результату ламаємо** (O-30): хост цей SDK не споживає (`AGENTS.md`); усі споживачі `tiers`/`StaffTierBand` оновлюються в одній зміні.

## Що це рішення **не** вирішує (спека T126)
Межу входів/виходів Rust (R1), розрив циклу (R2), LOD для точок лінків і обсяг «точок лінків» (Q-3), API результату, Rust-стандарт, перф-поріг, як SVG-експорт споживає межі. Це **рішення спеки**, не цього ADR; ADR фіксує напрям власника й виміряні причини.
React@near / Pixi@far лишається задокументованим у `SPEC §5.1` / `USAGE §12-13`.
