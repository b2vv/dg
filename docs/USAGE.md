# Використання `@org-hierarchy/sdk`

Практичний гайд: як підключити, чим годувати, які ручки крутити й що воно поверне.
Це **не** специфікація (алгоритми — [`work/SPEC.md`](../work/SPEC.md)) і не вимоги
([`docs/REQUIREMENTS.md`](./REQUIREMENTS.md)). Тут — API, хелпери й приклади.

---

## 1. Що це і чого воно не робить

Embeddable browser SDK для організаційних і штатних діаграм: **host дає дані в пам'ять**,
SDK розкладає, малює на Pixi-канвасі й експортує.

Він **не** ходить у мережу, **не** знає вашого бекенду і **не** зберігає нічого сам.
Drag/expand повертаються вам через колбеки — записувати їх кудись ваша справа.

---

## 2. Встановлення й збірка

```bash
npm i @org-hierarchy/sdk
```

- `pixi.js` — рантайм-залежність SDK, ставиться автоматично.
- `react` / `react-dom` ≥ 18 — **optional peer**: потрібні лише для входу `@org-hierarchy/sdk/react`.
- Node ≥ 20.

**Розробка в цьому репо:** WASM-артефакт не лежить у git. Перед першим прогоном тестів або демо:

```bash
npm run build:wasm    # wasm-pack → packages/sdk/src/wasm/pkg (потрібен rustc ≥ 1.86)
```

Без нього contour-тести SDK не стартують ([TD05](../work/tech-debt/TD05-wasm-pkg-in-repo.md)).

Входи пакета: `.` (усе основне), `./react`, `./worker`, `./mappers`.

## 3. Мінімальний старт

```ts
import { OrgHierarchyDiagram, emptyDiagramData } from '@org-hierarchy/sdk';

const data = {
  ...emptyDiagramData(),
  organizations: [{ id: 'org1', name: 'Cedar Lake', groupIds: [] }],
  persons: [{ id: 'per1', fullName: 'Ada Byron' }],
  positions: [
    { id: 'pos1', organizationId: 'org1', title: 'Head', personId: 'per1', isHead: true },
    { id: 'pos2', organizationId: 'org1', title: 'Engineer' },       // вакансія: без personId
  ],
  reportLines: [{ fromId: 'pos1', toId: 'pos2', kind: 'admin' }],
};

const diagram = await OrgHierarchyDiagram.create(document.getElementById('canvas')!, {
  data,
  theme: 'auto',                 // 'light' | 'dark' | 'auto'
  staffCurrentOrgId: 'org1',     // без нього SDK вгадає головну org сам
});

// ...
diagram.destroy();               // обов'язково: звільняє Pixi, воркери й текстури
```

`emptyDiagramData()` дає всі обов'язкові порожні масиви — беріть його за основу, щоб не забути поле.

## 4. Дані

Канон — `DiagramData` у [`packages/sdk/src/data/types.ts`](../packages/sdk/src/data/types.ts):

| Поле | Що це |
|---|---|
| `organizations` | вузли орг-дерева (`parentOrgId`, `collapsed`, `groupIds`) |
| `groups` | підписи-групи над орг-картками |
| `departments` | відділи; саме за ними малюються контури |
| `persons` | люди (`fullName`, `photoUrl` / `media`) |
| `positions` | **посади** — головна сутність штатки |
| `reportLines` | звʼязки `admin` / `matrix` / `dotted` між посадами |
| `orgLinks` | звʼязки між організаціями (опційно) |

Три речі, на яких найчастіше спотикаються:

1. **Посада ≠ людина.** `DiagramPosition.personId` необовʼязковий: без нього це вакансія, і вона
   малюється інакше. Одна посада — одне призначення.
2. **`departmentId` необовʼязковий.** Посада без відділу вважається **чужою** для будь-якого
   контуру — вона не «порожнє місце», контур її обходить.
3. **Координати мають три способи** (`gridCell`, `layoutX`/`layoutY`, `layoutCoords`). Контури
   малюються **лише** для авторських `gridCell`; без них SDK скаже про це в діагностиці, а не
   намалює криве.

## 5. Мапери: ваші дані → `DiagramData`

Якщо у вас плаский список рядків — є готовий мапер:

```ts
import { OrgHierarchyDiagram, flatRowsToDiagram, type FlatDiagramRow } from '@org-hierarchy/sdk';

const rows: FlatDiagramRow[] = [
  { id: 'org1', kind: 'organization', label: 'Cedar Lake' },
  { id: 'pos1', kind: 'position', label: 'Head', organizationId: 'org1', personId: 'per1' },
  { id: 'per1', kind: 'person', label: 'Ada Byron' },
];

await OrgHierarchyDiagram.create(el, { data: rows, mappers: { toDiagram: flatRowsToDiagram } });
```

Свій мапер — той самий контракт:

```ts
const mappers = {
  toDiagram: async (raw: MyPayload) => toDiagramData(raw),   // обовʼязковий
  normalize: async (d) => d,                                  // опційний пост-крок
  append: async (chunk: MyChunk) => ({ positions: [...] }),   // для стрімінгу, див. §11
};
```

## 6. Конфігурація

Усе — другим аргументом `create()` (`OrgHierarchyConfig`):

| Ключ | Навіщо |
|---|---|
| `theme` | `'light' \| 'dark' \| 'auto'` |
| `styles` | часткове перевизначення `NodeTheme` (кольори, розміри карток, edge-стиль) |
| `render` | `RenderConfig`: `cellWidth/cellHeight`, `paddingCells`, `smoothIterations`, `magnetRadius`, `minContourMembers`, `corridorCells`, `departmentStyle`, **`contourEngine`**, `staffZoneChrome` |
| `staffLayout` | геометрія штатки: `nodeWidth/Height`, `refCellWidth/Height`, `horizontalGap`, `verticalGap`, `tierGap`, `margin`, `maxExpandedPositions` |
| `orgLayout` | геометрія орг-дерева + `orgEdgeStyle` |
| `staffCurrentOrgId` | яка org у центрі (ярус 2) |
| `useWorker`, `workerPoolSize`, `workerFactory` | воркери під contour/search/map |
| `lodThresholds` | межі far/mid/near |
| `renderer` | **`'auto'` (default) \| `'webgl'` \| `'canvas'`** — який рушій малює сцену (нижче) |
| `callbacks` | див. §9 |

### `renderer` — на чому малювати

Потрібне тим, хто ставить бібліотеку на машини **без GPU** (тонкі й нульові клієнти, RDP-сесії,
термінали). Там браузер віддає WebGL через програмну емуляцію, і важка сцена стає непридатною для
роботи; та сама сцена на Canvas2D лишається плавною. На машині з апаратним GPU різниці між
рушіями ми не виміряли.

Чому це важить — вимір. Той самий датасет (`Staff · 1M`), той самий жест панорамування,
headless Chromium із програмним растеризатором:

| що передали | що отримали | кадр p50 | fps |
|---|---|---|---|
| `'canvas'` | canvas | 15,0 · 18,9 мс | **60** |
| `'auto'` (до фолбеку) | **webgl** | 122,3 · 169,5 мс | **8** |

**Потрібна визначеність — передавайте `renderer: 'canvas'` явно.** Не тому, що `'auto'` погано
вгадує, а тому, що явне значення взагалі не вгадує.

| Значення | Що робить | Кому |
|---|---|---|
| `'auto'` (default) | впізнає відомі програмні растеризатори за іменем і йде на Canvas2D; інакше пробує WebGL, потім Canvas2D | усім за замовчуванням |
| `'canvas'` | одразу Canvas2D, WebGL не пробується й імені ніхто не питає | **гарантія** для парку терміналів |
| `'webgl'` | прибиває WebGL; програмний контекст приймається; детект не запускається | відтворити баг на конкретному рушії |

#### Як `'auto'` вирішує

Дві сходинки, перша з відповіддю зупиняє другу:

1. **Явний вибір хоста** сильніший за все — якщо ви передали `'canvas'` або `'webgl'`, нічого
   не питається.
2. **Ім'я рушія.** SDK бере тимчасовий WebGL-контекст (у DOM він не потрапляє) і читає
   `UNMASKED_RENDERER_WEBGL`. Контекст звільняється через `WEBGL_lose_context`, **якщо браузер
   це розширення дає**; якщо ні — він живе до збирача сміття, і саме тому читання відбувається
   один раз на сторінку. Якщо ім'я містить відомий програмний растеризатор — `SwiftShader`,
   `llvmpipe`, `softpipe`, `Microsoft Basic Render Driver`, `Software Adapter`,
   `Apple Software Renderer` — сцена малюється на Canvas2D, і причина йде в діагностику
   з **назвою** впізнаного рушія.

Усе інше лишає поведінку без змін. «Усе інше» — це не лише апаратний GPU: браузери з
посиленою приватністю (Firefox із `resistFingerprinting`, Brave, WebKit) ім'я **маскують**, і
для них SDK нічого не вигадує.

🔴 **Це впізнавання за списком імен, а не гарантія.** Список кінцевий і старіє; растеризатор,
якого ми не знаємо, лишиться на WebGL. Ціна помилки навмисно однобічна: SDK **ніколи** не
переводить на Canvas2D машину, рушій якої не впізнав, — краще не спрацювати, ніж забрати WebGL
у того, в кого справний GPU.

```ts
const diagram = await OrgHierarchyDiagram.create(el, { data, renderer: 'canvas' });
diagram.getRendererKind();   // 'webgl' | 'canvas' | null (null до монтування й після destroy)
```

🔴 **Друга половина `'auto'` — best-effort, не обіцянка.** Коли ім'я нічого не сказало, рішення
ухвалює браузер через `failIfMajorPerformanceCaveat`, і він непослідовний: той самий Chromium
відмовив у програмному WebGL на macOS (`--use-gl=swiftshader`) і **видав** його в
Linux-контейнері з тим же SwiftShader. Firefox без GPU відмовляє у WebGL узагалі — там фолбек
спрацьовує сам. Потрібна визначеність — ставте `'canvas'` явно.

⚠️ **`'webgl'` там, де WebGL недоступний, — це помилка, а не тихий фолбек.** `create()`
відхиляється з повідомленням, яке називає задане значення. Так і задумано: інакше значення не
годилося б для того єдиного, заради чого існує, — зафіксувати рушій.

⚠️ **Заблоковані драйвери теж поїдуть на канвас.** Якщо браузер вніс GPU у власний blacklist,
`'auto'` вважатиме WebGL непридатним. За нашими вимірами це не втрата швидкодії.

**`contourEngine`** — той самий контур двома різними геометріями:

- `'button-group'` (**default**) — TS: злиття сусідніх клітин відділу + AABB з виїмками під чужі картки;
- `'cell-flood'` — Rust flood поблочно (G1–G8).

**SVG малює тим самим рушієм, що й канвас.** PNG/PDF знімаються з живого канвасу, тож вірні за
будь-якого рушія. Якщо flood не може відпрацювати (немає авторських `gridCell`, WASM недоступний),
шар відділів у SVG лишається **порожнім — рівно як на екрані**, а причина йде в діагностику: SDK
ніколи не підставляє рушій, якого канвас не використав.

## 7. Два сімейства сцен

**Організації.** Усі `collapsed` → matrix (розріджена сітка). Хоч одна розгорнута → row-tree.
Перемикається саме даними, не прапорцем:

```ts
await diagram.expandOrg('org-5');     // розкриває і всіх предків
await diagram.collapseOrg('org-5');
await diagram.setOrgsCollapsed(['a', 'b'], true);   // масово, один рендер
await diagram.collapseAllOrgs();
diagram.getOrgMode();                 // 'matrix' | 'row-tree'
```

### Матриця згорнутих сиблінгів (T113)

Правило розкладки **локальне й рекурсивне**: будь-який набір братів, **усі** члени якого
згорнуті і яких **більше одного**, лягає сіткою `ceil(√n)`, а не одним рядом — на кожному рівні,
незалежно від решти діаграми. Раніше сітка була лише тоді, коли згорнуто **всю** діаграму; це
той самий вигляд у тому окремому випадку й **інший** там, де вузол розгорнутий, а його діти ні.

Порядок у сітці — `matrixOrder`, якщо він є в **усіх** членів набору; інакше порядок із даних
цілком. Частково заповнений `matrixOrder` ігнорується, а не змішується: два джерела порядку
дають результат, якого не пояснити.

⚠️ **`getOrgMode()` і `onOrgModeChange` кажуть про ДІАГРАМУ, а не про набір.** Їхнє значення не
змінилось і не стало вужчим: `'row-tree'` означає «є хоч одна розгорнута організація», і це
правда навіть тоді, коли всередині дерева кілька наборів лягли сітками. Тобто на питання «зараз
деревом чи сіткою загалом» ви й далі отримуєте чесну відповідь — але **режиму окремого набору**
ці два не повідомляють і ніколи не повідомляли. Якщо вам потрібно знати, що конкретний набір
намальовано сіткою, дивіться на `matrixRow`/`matrixCol` у вузлах розкладки.

Сітка з **двох** членів виглядає як звичайний ряд — `ceil(√2) = 2` колонки. Це властивість
формули, не дефект: видима зміна починається з трьох.

**Штатка — три яруси**: керуюча org → поточна (`staffCurrentOrgId`) → підлеглі картки.

```ts
await diagram.focusStaffOrg('org-42');        // drill: змінити ярус 2
await diagram.toggleStaffOrgExpand('org-7');  // розкрити картку ярусу 3 на місці
await diagram.togglePositionExpand('pos-9');  // піддерево посади
await diagram.expandToDepth({ depth: 2 });    // обходить maxExpandedPositions
await diagram.collapsePositionSubtree('pos-9');
```

## 8. Робота з вузлами

```ts
// пошук: підрядок по імені/посаді/назві org
const hits = await diagram.search('ada');     // SearchResult[] { node, label, score }

// пошук ПОЗА вікном — коли хост тримає більше даних, ніж діаграма
// Окремий метод, а не ширший search(): «що на екрані» і «що є в даних» —
// різні питання з різними режимами відмови.
const found = await diagram.searchAll('ada', 0);
// { hits, total, hasMore, source: 'window' | 'host', unavailable?, unresolved? }

// фокус: розкрити шлях, вибрати, підвести камеру
await diagram.revealPath(hits[0].node.id);
await diagram.focusNode('pos-9');             // false, якщо id невідомий

// вибір
diagram.getSelection();                       // NodeRef | null
diagram.getSelections();                      // весь набір
await diagram.select({ kind: 'position', id: 'pos-9' });
await diagram.selectMany([...]);
await diagram.toggleSelection(ref);
await diagram.clearSelection();

// камера
diagram.fitView(48, { animate: true });
diagram.panTo(x, y);
diagram.zoomBy(1.25);
diagram.setZoom(1);
diagram.resetView();
diagram.getViewport();                        // { x, y, scale }
diagram.getLodLevel();                        // 'far' | 'mid' | 'near'
```

## 9. Колбеки

```ts
await OrgHierarchyDiagram.create(el, {
  data,
  callbacks: {
    onNodeClick: (node) => {},
    onNodeDoubleClick: (node) => {},
    onSelectionChange: (nodes) => {},
    onOrgModeChange: (mode) => {},              // 'matrix' | 'row-tree'
    onLayoutChange: (patch) => {},              // drag / reorder / expand — це ваш «зберегти»
    onPositionExpandChange: (state) => {},
    onDataMapped: ({ orgs, persons, positions, ms }) => {},
    onLayoutDiagnostics: (messages) => {},      // див. §12
    onViewportChange: (t, meta) => {},          // камера/ресайз — див. §11
    onContextMenu: (request) => request.items,  // повернути false → меню не показувати
    onContextMenuAction: (item, request) => {},
    onSeatCollision: async (request) => ({ kind: 'swap' }),  // див. нижче; null = скасувати
  },
});
```

`onLayoutChange` — єдиний канал персистентності. SDK нікуди не пише.

### Drop на зайняту клітину: посунути, поміняти або спитати (T111)

Коли посаду перетягують на клітину, де вже хтось сидить, SDK **не створює накладання** і **не
відмовляє мовчки**. Рішення приймається так:

| Ситуація | Що відбувається |
|---|---|
| напрямок визначений, клітина за сусідом вільна | сусіда **посунуто** туди, мовчки |
| напрямок визначений, посунути нікуди | посади **міняються місцями**, мовчки |
| напрямок неоднозначний (діагональ) або в клітині вже двоє | **питає** через `onSeatCollision` |
| відпустили там, де взяли | нічого не змінюється |

Ланцюга немає: якщо сусідові нікуди — це обмін, а не штовхання далі.

**Обидві посади їдуть однією транзакцією.** Патч `position-move` несе `displacedPositionId` —
id того, кого зачепило:

```ts
onLayoutChange: (patch) => {
  if (patch.type === 'position-move' && patch.displacedPositionId) {
    // Дві зміни, одна дія користувача. Якщо у вас поштучне збереження —
    // це два запити; якщо є undo — це має бути ОДИН його крок.
  }
},
```

⚠️ **«Одна транзакція» — це про SDK, і тільки про нього.** Патч приходить один, і в даних обидві
посади міняються разом або жодна. Що станеться далі, SDK **не припускає**: якщо ви зберігаєте
поштучно, це два послідовні запити, і другий може впасти після успішного першого. Тоді на сервері
лишиться половина обміну — стан, якого не було на екрані. Атомарність по той бік колбека —
ваша відповідальність: або транзакція на бекенді, або компенсація, або свідомий partial-persist,
у якому незбережене лишається в чернетці й ретраїться.

**`onSeatCollision` — необов'язковий.** Не передали → SDK **відмовляє** (кидає
`OrgHierarchyError`, дані не змінені). Це навмисна політика, а не заглушка: там, де автомат
відповіді не має, SDK не вгадує за користувача — він віддає рішення тому, хто має право його
ухвалити, а без такого адресата зупиняється.

Якщо модалка на кожному перетягу вам не підходить — а в масовому редагуванні з undo вона швидко
стає ненависною, і «зробити, давши відкотити» там зручніше, — це **теж робиться колбеком**, лише
тривіальним:

```ts
onSeatCollision: async () => ({ kind: 'swap' }),   // ніколи не питати, завжди міняти місцями
```

```ts
onSeatCollision: async ({ positionId, target, occupantId, pushTargets }) => {
  // Малює хост. Поверніть null, щоб скасувати переміщення.
  return { kind: 'swap' };                    // або { kind: 'push', to: pushTargets[0] }
},
```

⚠️ `push` мусить називати клітину **з `pushTargets`** — вигадана буде відхилена.
Поки питання відкрите, другий такий drop теж відхиляється, а після відповіді рішення
**перераховується**: якщо дані змінились, поки діалог був відкритий, переміщення відхиляється
замість застосування застарілої відповіді.

🔴 **Організації поводяться інакше — і це навмисно.** Drop на зайняту клітину **матриці
організацій** не посуває й не міняє місцями: мешканця **викидають** із матриці, а хост дізнається
про це через `ejectedOrgId` у патчі `matrix-cell`. Причина в тому, що для організації «поза
сіткою» — осмислений стан, а для посади його немає. Якщо ви обробляєте обидва — це два різні
контракти, не один.

### Керівну посаду переставити не можна (T117)

`reparentPosition` відхиляє посаду з `isHead: true` — корінь структури не переїжджає під чужого
керівника. Відмова приходить типом `OrgHierarchyError` і словом `root` у повідомленні; дані
лишаються незмінними, патча немає.

```ts
await diagram.reparentPosition(headId, someManagerId);  // ← відхилено: root
await diagram.reparentPosition(someSeatId, headId);     // ← ✅ звичайна справа
```

⚠️ **Гвардія стоїть на тій посаді, яку рухають, і ні на чому іншому.** Зробити керівну посаду
чиїмось начальником — нормальний сценарій, найчастіший з усіх; заборонено саме **її** переміщення.
Плутати ці дві речі дорого: гвардія «на обидва боки» зламала б підпорядкування першому керівнику.

Та сама відповідь приходить і в превʼю перетягу: картку кореня можна взяти, але жодна ціль не
підсвітиться зеленим — перевірка одна на превʼю й на коміт, тож drop не може пообіцяти того,
чого не зробить.

⚠️ **Відмова тепер помітна.** Раніше `reparentPosition` гасив `OrgHierarchyError` мовчки — проміс
резолвився так, ніби зміну застосовано. Тепер він **відхиляється** на всіх п'яти причинах
(`root`, `self`, `cycle`, `unchanged`, `unknown`), як і решта мутаторів. Якщо ви його викликаєте
напряму — обгортайте, інакше дістанете unhandled rejection.

### Коли саме приходить `onLayoutChange` (змінено T104)

**Патч надсилається після кадру, який його намалював, а не до нього.** Тобто якщо ви його
отримали — зміна вже на екрані й уже в даних. Раніше було навпаки: колбек ішов першим, і коли
рендер після нього падав, хост лишався поінформованим про зміну, якої немає, без жодного
повідомлення про скасування.

Що це означає на практиці:

| Ситуація | Що отримує хост |
|---|---|
| зміна намальована | `onLayoutChange(patch)` — **на кадр пізніше**, ніж раніше |
| рендер упав | патча **немає**; метод-мутатор **відхиляється**; окремо йде `onRenderFailed` |
| вашу зміну відкотили, поки вона чекала кадру | патча **немає**; метод відхиляється з `'never reached the screen and was not applied'` |

⚠️ **Оптимістичний UI на цьому колбеку сповільниться.** Якщо ви малювали свій стан одразу по
`onLayoutChange`, тепер це станеться після кадру діаграми. Взамін ви більше ніколи не побачите
патч про зміну, якої не сталося.

⚠️ **Мутатори тепер можуть відхилятись** — `reparentPosition`, `movePersonToCell`, `shiftBlock`,
`reorderOrg`, `placeOrgAtMatrixCell`. Обгортайте їх, якщо не хочете unhandled rejection.

**Відкіт даних робиться лише тоді, коли поверх вашої зміни ніхто не написав.** Якщо інша мутація
встигла лягти зверху й намалюватись — виграє намальоване, а ваш метод просто відхиляється.
Правило одне: **дані діаграми дорівнюють останньому намальованому кадру**.

## 10. Експорт і друк

```ts
const svg  = await diagram.export({ format: 'svg', scope: 'full' });          // string
const png  = await diagram.export({ format: 'png', scale: 2 });               // Blob
const pdf  = await diagram.export({ format: 'pdf', scope: 'subtree', subtreeRootId: 'org-3' });
await diagram.print();                                                        // SVG → вікно друку
```

- `scope`: `'viewport' | 'full' | 'subtree'`.
- PNG/PDF беруться з Pixi-фреймбуфера → **потрібен змонтований канвас**; без нього кидається `ExportError`.
- SVG перебудовує шляхи заново, тож не залежить від того, що зараз у вʼюпорті.
- Чому картинка може виявитись не такою, як очікували, — через діагностику:

```ts
await diagram.export({ format: 'svg', onDiagnostic: (m) => console.warn(m) });
// без onDiagnostic те саме йде в console.warn — мовчки нічого не зникає
```

Сюди потрапляють лише **реальні** причини: сцена без cell-transform (сітка без staff-фокуса),
недоступний WASM, збій окремого org-блоку. Порожній шар через `minContourMembers` — не привід
для повідомлення: це налаштування, а не збій.

## 11. Великі дані

SDK адресує великі набори, але **не малює їх усі**. Робочий підхід — вікно:

```ts
// 1. початкові дані — лише те, що видно
const diagram = await OrgHierarchyDiagram.create(el, { data: firstWindow, workerPoolSize: 4 });

// 2. дозавантаження чанками; індекс пошуку доростає інкрементально
await diagram.appendData(nextChunk, { append: async (c) => mapChunk(c) });

// 3. повна заміна — коли вікно поїхало далеко
await diagram.setData(newWindow);
```

### Вікно, що їде за камерою

Щоб вікно рухалось саме, а не лише по явній дії, слухайте камеру:

```ts
callbacks: {
  onViewportChange(transform, { settled, reason }) {
    // Викликається не частіше разу на кадр, поки камера рухається, і ще раз —
    // з `settled: true` — коли вона зупинилась на `viewportSettleMs` (дефолт 150).
    if (!settled) return checkReserve(transform);   // запас закінчується?
    void diagram.setData(buildWindowAround(transform));
  },
}
```

### Хто виграє, коли `setData` викликано двічі поспіль (змінено T103)

Приклад вище — `void diagram.setData(...)` на кожен рух камери — навмисно **не** чекає
завершення. Отже виклики накладаються, і правило тепер таке:

**Виграє останній запит, а не той, чий маппер виявився швидшим.** Раніше `setData` писав дані
одразу після `await` на ваші маппери, тож повільніший **старший** виклик лягав поверх новішого;
пошуковий індекс діставався тому, хто завершився останнім, і найновіші дані могли опинитися в
парі зі **старішим індексом**.

| Ситуація | Що отримує хост |
|---|---|
| ваш `setData` — найновіший | застосовано; дані **й** індекс комітяться разом |
| поки ви мапили **або поки будувався індекс**, прийшов новіший `setData` | нічого не застосовано; проміс **резолвиться тихо**; `onDataMapped` і `onOrgModeChange` від вас **не шлються** |
| `appendData`, що почався до новішого `setData` | чанк **не** зливається; так само тихо |

⚠️ **Витіснений виклик резолвиться, а не відхиляється** — і це навмисно. Обігнати старий виклик
новішим це **робота механізму**, а не збій, тож `void diagram.setData(...)` із прикладу вище
лишається безпечним і не потребує `.catch`. Мовчить він при цьому повністю: колбеки від
витісненого виклику не йдуть, бо хост не має чути про дані, яких у нього немає.

**Як дізнатись, який виклик переміг:** `onDataMapped` приходить лише від того, що застосувався.

**Дані й індекс міняються разом.** Немає моменту, у якому `getData()` уже віддає новий стан, а
`search()` ще відповідає по старому: обидва комітяться без `await` між ними. Це окрема гарантія
від «виграє останній» — послідовність визначає, **чий** індекс усиновлять, а атомарність — **коли**.

⚠️ **`setData` скасовує чанки, що були в дорозі.** Він означає «ось увесь стан», і чанк, який
приїхав раніше, до цього стану не належить. `appendData` при цьому **не** скасовує інші
`appendData` — стрім накопичується, як і раніше.

⚠️ **Роботу мапера ми не перериваємо** — лише не застосовуємо результат. Якщо ваш `toDiagram`
дорогий, скасовуйте його самі; SDK не має для цього каналу.

`reason` розрізняє дві події, і це не косметика: `'resize'` приходить із **незміненою**
трансформою — змінилось лише те, скільки вміщається. Хост, який дивиться тільки на трансформу,
лишить голу смугу вздовж нового краю й ніколи її не заповнить.

- `appendData` дедуплікує за `id` (patch виграє) і **зливає** індекс пошуку замість перебудови;
  якщо чанк **оновлює** вже відому сутність — індекс перебудується, інакше лишився б дубль.
- `useWorker: true` (default у браузері) виносить contour і побудову індексу з main thread.
- `getWorkerPool()` віддає пул, якщо ви його замовили через `workerPoolSize`.
- Демо-таби `100k orgs` і `Staff · 1M` показують цю механіку разом із чесним підписом
  «вікно N з M».

## 12. Діагностика — SDK не мовчить

```ts
diagram.getLayoutDiagnostics();   // readonly string[] з останнього рендеру
```

Перший рядок списку — **рушій, який намалював сцену**: `Renderer: canvas (requested: auto)`.
Він присутній, доки діаграма змонтована (до `destroy()`), тож у цьому вікні список не буває
порожнім. Якщо ви показуєте діагностику як попередження, фільтруйте його за префіксом
`'Renderer: '` — префікс стабільний і є частиною контракту.
Це відповідь на «чому в мене картинка інша, ніж у колеги» без профайлера. Якщо хост передав
значення `renderer`, якого ми не знаємо, поруч буде рядок про те, що застосовано замість нього.

Далі — все, що інакше виглядало б як «нічого не намалювалось»: посади без `gridCell`
у blob-режимі, flood без cell-transform, пропущені expand'и. Те саме прилітає в
`onLayoutDiagnostics` після кожного рендеру — виводьте його хоч у консоль, це найдешевший спосіб
зрозуміти порожній екран.

## 13. React-хелпери (опційно)

```ts
import {
  createReactContextMenuHost, DefaultReactContextMenu,
  createReactPromoteOverlay, DefaultPromoteCard,
  createTestAnchorOverlay,
} from '@org-hierarchy/sdk/react';

const menu = createReactContextMenuHost({ diagram, mount: el, component: DefaultReactContextMenu });
const promote = createReactPromoteOverlay({ diagram, mount: el, mode: 'near-selection', component: DefaultPromoteCard });
const anchors = createTestAnchorOverlay({ diagram, mount: el, interactive: true });  // DOM-якорі для e2e

menu.close(); promote.dispose(); anchors.dispose();
```

Ядро працює без React — це надбудова, а не залежність.

⚠️ Promote-оверлей — це HTML **над** канвасом: у SVG/PNG/PDF він не потрапляє — **це стосується
й режиму `near-visible`**: піднята оболонка в растр не йде, у експорт потрапляє канвасна картка.

### Режим `'near-visible'` — підняти всі видимі картки

```ts
const promote = createReactPromoteOverlay({
  diagram,
  mount: el,
  mode: 'near-visible',
  component: MyCard,
  shouldPromote: (node) => node.ref.kind === 'position',  // необов'язково
  maxPromoted: 40,                                        // необов'язково
  settleMs: 150,                                          // необов'язково
  onSlotError: (id, err) => console.warn('картка впала', id, err),
});
```

**Межа — зум, а не кількість.** Картки піднімаються в HTML на LOD `near` (зум ≥ 1.2) і на
жодному іншому. Це навмисно **не** обмеження «не більше N карток»: на більшому екрані на тому
самому зумі їх видно більше, і це очікувана поведінка. Дефолт — **без стелі**.

| Опція | Дефолт | Що робить |
|---|---|---|
| `shouldPromote(node)` | усі кандидати | хост виключає ноду з підйому. Нода, для якої `false`, лишається **намальованою на канвасі** — порожньої оболонки в DOM не з'являється |
| `maxPromoted` | без стелі | стеля кількості; лишаються найближчі до **центру екрана** |
| `settleMs` | `150` | скільки камера має стояти, перш ніж позиції перерахуються. Під час руху шар їде **одним CSS-трансформом**, картки не перераховуються |
| `onSlotError(id, err)` | — | компонент картки кинув. Картку знято, нода **повернулась на канвас**; вона більше не піднімається до кінця життя оверлея |

**Позадіапазонний `maxPromoted`.** `0` — не піднімається жодна нода (усі лишаються канвасними).
Не скінченне число або від'ємне — **стеля знімається**, тобто поведінка дефолту. Дробове
округлюється вниз. Помилки хост не отримає: порожній шар важче діагностувати, ніж робочу фічу.

**Картка з фокусом не депромоутиться.** Якщо всередині піднятої картки стоїть фокус (інпут,
відкрите меню), вона лишається в DOM, навіть коли виїхала за екран, — інакше зникали б фокус
і незбережений ввід. Вона займає одне з місць `maxPromoted`, а не додаткове.

**Що діаграма віддає оверлею** (знадобиться, якщо пишете власний шар замість нашого):
`diagram.listPromoteBoxes()` — геометрія нод **без** резолву даних; `listPromoteCandidates(ids)` —
дані лише для названих; `getPromoteChrome(kind)` — рамка ноди у **світових** одиницях;
`getScreenSize()` — розмір поверхні з `ResizeObserver` діаграми (не читайте `clientWidth` на
кадрі); `getPromotedNodeIds()` — що зараз **не малює** Pixi.

**Слот несе геометрію ноди, яку заміщає** — `chrome.borderRadius`, `chrome.borderWidth`,
`chrome.paddingX/Y` (відступи є в організацій, у посад немає). Значення в **екранних** px,
уже помножені на поточний зум, тож картка збігається з канвасною на будь-якому масштабі.

**Змінити стелю в рантаймі** — `promote.setMaxPromoted(n)`; `undefined` знімає її.

**Один оверлей на діаграму.** Два `createReactPromoteOverlay` на одній діаграмі не
підтримуються: вони поділяють `setPromotedNodeIds`, і другий перезапише перший.

⚠️ **Зняття режиму помилки не дає.** Повернувши `mode` на `'near-selection'`, ви **не**
отримаєте попередження — поведінка тихо повернеться до підйому **виділеної** ноди. Якщо після
зміни режиму на екрані одна картка замість багатьох, це не збій.

## 14. Тест-шов: як e2e дістають вузол на канві

Канва не має DOM на вузол, тож звичайне `getByTestId` по картці не працює — малює її Pixi, а не
браузер. SDK дає на це дві відповіді, і **починати треба з першої**.

### Спосіб 1 (рекомендований) — DOM-якорі поверх канви

`createTestAnchorOverlay` з [§13](#13-react-хелпери-опційно) вішає на кожен **видимий** вузол
невидиму кнопку з `data-testid="node-<testId>"`, позиціоновану в CSS-пікселях і пересинхронізовану
на кожен рух камери:

```ts
import { createTestAnchorOverlay } from '@org-hierarchy/sdk/react';

const anchors = createTestAnchorOverlay({ diagram, mount: el, interactive: true });
// у тесті:
await page.getByTestId('node-ceo').click();
```

Це дешевше за координати не лише в написанні: Playwright сам чекає на стабільність елемента й
б'є в його центр, тож зникає цілий клас помилок «клік влучив у сусідню картку, бо камера ще
їхала». `interactive: true` вмикає кліки й контекстне меню на якорях; без нього це чисті
цілі для пошуку, які не перехоплюють події.

🔴 **`interactive: true` — тільки під гейтом середовища.** У цьому режимі якорі стають
невидимими клікабельними кнопками **поверх карток** (`opacity: 0.001`, `pointer-events: auto`).
У проді це означає, що кліки користувача дістануться оверлею, а не діаграмі. SDK не гейтить це
сам і не буде: він не знає вашого бандлера, а читати `import.meta.env` у бібліотеці — зашити
припущення про чужу збірку. Зразок гейта — наше демо: оверлей монтується лише при `?e2e=1`
(`packages/demo/src/app/App.ts:600`). Сам по собі оверлей інертний, поки його не змонтували,
тож небезпечний саме цей прапорець, а не наявність хелпера в бандлі.

⚠️ Якорі є лише для того, що **в кадрі** — оверлей свідомо не малює те, що за межами `mount`.
Щоб дістати вузол, якого не видно, спершу приведіть його в кадр (`focusByTestId` нижче).

### Спосіб 2 — координати, коли DOM не підходить

Шість методів фасаду дають те саме сирими даними. Беріть їх, якщо ви не на React-надбудові або
вам треба саме піксель (наприклад, drag через `page.mouse`).

| Метод | Що робить |
|---|---|
| `listTestAnchors()` | усі вузли з рендера: `{ testId, kind, ref, world }` |
| `resolveTestId(raw)` | стабільний testId → `NodeRef \| null`; приймає й форму з префіксом `node-` |
| `focusByTestId(raw)` | розкриває згорнутого предка, відкриває шлях, виділяє і панорамує; невідомий id → `false` |
| `getCanvas()` | сам `<canvas>` — потрібен, щоб перевести координати в сторінкові |
| `getZoom()` | поточний масштаб |
| `setViewport({ x, y, scale })` | поставити камеру детерміновано, замість «поскролити й сподіватись» |

🔴 **`world` — це сценові координати, не піксель на екрані.** Ім'я поля не метафора: числа
приходять зі сцени без перетворення, і `page.mouse.click(anchor.world.x, anchor.world.y)`
влучить кудись не туди на будь-якому масштабі, крім `scale === 1` при нульовому зсуві.

Перетворення експортоване з кореня — переводьте самі й **не пишіть свою арифметику**:

```ts
import { worldBoxToScreen } from '@org-hierarchy/sdk';

const rect = worldBoxToScreen(anchor.world, diagram.getViewport());   // CSS-пікселі відносно канви
const canvas = diagram.getCanvas()!.getBoundingClientRect();          // канва відносно сторінки

await page.mouse.click(
  canvas.left + rect.left + rect.width / 2,
  canvas.top + rect.top + rect.height / 2,
);
```

### Чого тут поки немає

**Окремої точки експандера.** `listTestAnchors` віддає бокс картки цілком, а кнопка
розгортання — це елемент усередині неї, чий кут залежить від режиму сцени. Обчислити її
ззовні з боксу вузла **не можна**, тож «клікнути саме по експандеру, а не по картці»
координатами зараз не виражається. Якщо вам це потрібно — розкривайте через API
(`expandOrg`, `focusByTestId`), а не через клік по пікселю.

## 15. Обмеження, про які краще знати заздалегідь

- **Кілька діаграм на сторінці — можна.** Кожна тримає власні воркери (пошук, пул) і звільняє їх
  на `destroy()`. Глобальні `configureContourWorker` / `configureSearchWorker` лишились для хостів,
  які кличуть модульні функції напряму, — але вони **процес-широкі**: якщо потрібна ізоляція,
  беріть `createContourWorkerClient()` / `createSearchWorkerClient()`.
- **`initialExpand` відкриває дерево до першого кадру.** `create(el, { initialExpand: { rootOrgId } })`
  розкриває названу org і її предків, решту згортає: **три** рівні, якщо над нею є керуюча
  організація, **два**, якщо вона сама корінь. Без `rootOrgId` «нашими» вважаються всі корені.
  ⚠️ **Не передати опцію — підтримуваний стан:** тоді `collapsed` із даних лишається **недоторканим**.
  Прапорці це контракт хоста, і забирати їх без запиту означало б змінити сцени, які вже працюють.
  Робиться **до** першого рендера — `revealPath` теж уміє розкривати, але вже поверх намальованого
  кадру, тобто зі стрибком.
- **`initialExpand.revealNodeId` — глибоке посилання.** URL, що називає організацію, приводить на
  неї вже розкритою: шлях відкрито, камера на цілі, **діти цілі лишаються згорнутими**. Приймає
  також id персони чи посади — вони мапляться в org, яка їх тримає.
  Ціль, якої в даних немає (застаріле посилання, id із набору, який замінив `setData`), — це
  **звичайний результат, а не помилка**: лишається мінімум від `rootOrgId`, а причина приходить у
  `onInitialExpand({ revealedOrgId: null, reason })`.
  📌 Гонки тут немає **за побудовою**: усе відбувається всередині `create()`, поки в хоста ще
  немає посилання на діаграму, тож ані `collapseAllOrgs`, ані `setData`, ані `destroy()` не можуть
  вклинитись.
- ⚠️ **Відмова рендера має власний канал.** `onRenderFailed({ reason, cause })` каже, що сцена
  **не намальована** — це не те саме, що `onLayoutDiagnostics`, який пояснює сцену, яка
  намальована (порожній шар контурів, пропущений expand). Питати пізніше — `getLastRenderFailure()`.
  Помилка **і повідомляється каналом, і кидається далі**: викликач, який змінив стан перед
  рендером, мусить знати, чи відкочувати, і опитування замість кидка — це шлях до діаграми, яка
  описує дерево, якого не малювала.
- **Після `destroy()` діаграма мовчить**: `search()` повертає `[]`, `searchAll()` — порожню
  сторінку з `source: 'window'`, повторний `destroy()` безпечний.
- **`searchAll()` без колбека `searchBeyondWindow` — це `search()` плюс число.** Не передати
  колбек — підтримуваний стан, а не деградація: `source` буде `'window'`, `unavailable` не буде.
- ⚠️ **Відмова хоста ≠ «нікого не знайдено».** Якщо `searchBeyondWindow` кинув або повернув не
  сторінку (`{ hits, total, hasMore }`), результат несе `unavailable` з причиною, а локальні
  збіги лишаються на місці. Показувати це користувачеві як «збігів немає» — означає видати
  поламаний бекенд за порожні дані.
- **Сторінка — рівно `SEARCH_PAGE_SIZE` (20).** Обидві сторони мусять збігатись у цьому числі,
  тож воно експортоване, а не узгоджується на виклик.
- **`total` — це всі збіги в даних, не розмір сторінки.** Довжина масиву дати цього числа не може,
  і саме тому `searchAll` повертає обʼєкт, а `search()` лишився масивом.
- **Немає HTTP-клієнта, персистентності й undo.**
- **Порожній шар відділів — можливий стан**, а не помилка: якщо flood не відпрацював, SVG
  повторює екран, включно з відсутністю контурів (§6, §10).
- **Promote-оверлей поза експортом** (§13).
- **Мільйон посад — це адресний простір, а не намальована сцена**: вікно матеріалізується, решта
  живе як індекс.
- **Рушій не змінюється після монтування.** Щоб перемкнути `renderer`, потрібне перемонтування —
  і, якщо на сторінці вже монтувалась діаграма з іншим значенням, **перезавантаження сторінки**:
  Pixi кешує вердикт «чи є придатний WebGL» на весь час життя сторінки, і кеш не зважає на те,
  що наступна діаграма просила інше.
- **Дві діаграми з різними `renderer`, змонтовані одночасно**, дають недетермінований результат
  для тієї, що на `'auto'`: вердикт диктує та, що першою дійшла до ініціалізації рушія, а не та,
  яку першою покликали. Монтуйте послідовно, якщо це важливо. `'canvas'` від цього не залежить —
  він WebGL не питає взагалі.
  ↳ **Відколи `'auto'` впізнає рушій за іменем, цей недетермінізм звузився.** Коли ім'я впізнане
  як програмне, `'auto'` просить одразу Canvas2D — а на цьому шляху Pixi свою перевірку WebGL
  не виконує й глобального вердикту не записує. Тобто демотована діаграма більше не диктує
  вибір сусідці. Коли ім'я не впізнане, все лишається як описано вище.
- **Ім'я рушія читається один раз на сторінку.** Скільки б діаграм ви не змонтували, тимчасовий
  WebGL-контекст для читання береться один. Наслідок: якщо середовище змінилось під час життя
  сторінки, перечитування не буде — потрібне перезавантаження.

## 16. Що тут публічне, а що просто видно

Кореневий барель `@org-hierarchy/sdk` віддає **252** імені (заміряно парсером самого гейта
`scripts/barrelSurface.mjs`). Публічна поверхня — не вони, а те,
що описує цей документ; решта експортована для зручності складання й **не є контрактом**.

**Публічне — це категорії нижче, і кожна описана у своєму розділі:**

| Дані діаграми | [§4](#4-дані) |
| Мапери ваших даних | [§5](#5-мапери-ваші-дані--diagramdata) |
| Робота з вузлами, пошук, меню | [§8](#8-робота-з-вузлами) |
| Колбеки | [§9](#9-колбеки) |

| Великі дані | [§11](#11-великі-дані) |

**Решта кореневих експортів — внутрішні.** Вони працюють, вони не зникнуть завтра без причини,
але на них не варто спиратись: рендерер, геометрія, воркер-мости й адаптери міняються разом із
реалізацією, і зміна в них не вважається ламальною. Якщо вам знадобилось щось звідти — це
привід відкрити issue, а не привід імпортувати.

⚠️ **Це стосується й типів.** Тип, імпортований із кореня й не згаданий у цьому документі,
теж внутрішній — навіть якщо ваш код на ньому компілюється сьогодні.

### `OrgHierarchyError` — помилку можна ловити типом

Клас експортований із кореня, тож гвардія глибини й перевірки метрик ловляться `instanceof`,
а не порівнянням рядка:

```ts
import { OrgHierarchyError } from '@org-hierarchy/sdk';

try {
  await diagram.setData(data);
} catch (err) {
  if (err instanceof OrgHierarchyError) {
    // дерево глибше за стелю, або метрика поза діапазоном
  }
}
```

⚠️ **Через воркер тип не виживає.** `computeOrgRowTreeLayoutInWorker` віддає звичайний `Error`:
межа воркера переносить лише текст повідомлення, тож і прототип, і `name` губляться по дорозі.
`instanceof` там не спрацює — це властивість `postMessage`, не наша.

### Що поїхало з кореня

`resetContourWasmForTests` і `setContourWasmLoaderForTests` більше **не** експортуються: вони
міняли WASM-loader і кеш на весь процес, тож один споживач впливав на всі діаграми застосунку.
Всередині SDK вони лишились у своєму модулі.

⚠️ **Прямої заміни для хоста немає.** Підпакета `./contour` в `exports` немає, а опції інжекту
loader'а в `OrgHierarchyConfig` теж немає — тож хост, який глушив цим WASM у власних тестах,
шва більше не має. Потрібен — відкрийте issue: це вирішується підтриманою опцією, а не
поверненням двох функцій у корінь.
